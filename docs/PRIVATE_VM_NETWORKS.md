Status: owner-scoped membership, atomic route/address storage, generation-pinned transport and production source gateway wiring are implemented. Same-node and two-daemon-node private TCP/DNS, plus two-daemon-node private IPv4 UDP through the maximum 65,507-byte payload, are verified from actual Internet-disabled KVM guests on an owned host. The comparison is **Partial**; full network parity still requires the runtime and lifecycle gates below.

The [isolated cluster test suite](benchmarks/2026-10-03/private-network-membership/README.md) passes 94 tests, including five new membership/authorization tests. ## Existing constraints

Each sandbox uses a separate userspace gateway and the default guest address `10.0.2.15` (`crates/hv2-net/src/gateway/mod.rs`). Connecting to that address cannot identify another VM. Gateway `Resolver` and `Dialer` traits provide extension points, but ordinary reserved-address policy runs before dialing. A configured SOCKS proxy also bypasses the custom dialer. Neither hook alone implements an isolated network.

`SandboxRecord.owner_id` is trusted creator identity; `metadata` is caller-supplied. Tags can select peers only within a trusted owner boundary. A metadata filter must never grant access across owners or to ownerless legacy guests.

## Proposed delivery sequence

| Component | Required behavior | Acceptance evidence |
| --- | --- | --- |
| Membership | Explicit network membership, scoped by trusted owner and network ID; validate tags and bounded membership counts | Memory and Redis agreement; forged owner fields and legacy ownerless guests refused |
| Address registry | Allocate synthetic private destinations atomically; bind each address to owner, network, sandbox ID and generation | Concurrent allocation, deletion and address reuse cannot redirect a stale capability to a new guest |
| Guest DNS | Resolve a documented private namespace locally; no host resolver fallback for that namespace | Exact member resolution; other networks and owners cannot enumerate or resolve peers |
| Gateway routing | Classify private destinations before ordinary egress policy; private traffic bypasses Internet SOCKS and secret substitution | Internet-disabled guests communicate with authorized peers while ordinary egress remains refused |
| Destination transport | Reuse authenticated node transport and guest proxy plumbing; destination independently checks source identity and current membership | Same-node and cross-node TCP payload checks; forged claims and direct unauthenticated node requests refused |
| Lifecycle | Persist explicit membership through pause/resume and migration; define fork inheritance; exclude uncertain registration from discoverable membership | Pause, recovery, migration, fork and deletion fixtures preserve isolation and bound stale records |
| Revocation | Close existing private streams on removal or owner/network mismatch; prevent new connections immediately | Open-stream revocation and concurrent delete/reconnect checks |
| Capacity and audit | Bound per-VM streams and lookup work; record source/destination IDs and network without bearer secrets | Saturation, cancellation, store outage and cleanup checks |

Start with TCP and an explicit API/CLI contract. Track UDP separately: the current guest gateway drops UDP other than DNS, so native public UDP support does not establish private guest-to-guest UDP support. Do not describe TCP delivery as a complete private network.

## Membership API

This endpoint configures membership. Authenticated mTLS cluster daemons with guest networking enabled use the tags for authorized private TCP/DNS; full network delivery still has the runtime and lifecycle gates below. It requires an authenticated operator with sandbox scope and a configured creator principal matching the VM owner. Observer and inventory keys cannot use it. Client owner headers do not establish identity.

`GET /sandboxes/{id}/private-networks` returns only `revision` and sorted `tags`. An untouched VM returns `{"revision":null,"tags":[]}`. A removed membership returns an empty tag list with its retained revision.

`PUT /sandboxes/{id}/private-networks` accepts strict JSON within 4 KiB:

```json
{"expectedRevision":null,"revision":"e9a3b635-11de-41bb-a5f8-777be375dd9d","tags":["team"]}
```

Generate a fresh canonical UUID v4 revision for each operation. Use the revision returned by GET as `expectedRevision`; null expects no previous membership row. Tags require lowercase DNS labels, with at most eight distinct tags. An empty tag list explicitly removes membership. Tags are required; omission is refused.

Success returns HTTP 200 with the persisted revision/tags. HTTP 409 means the revision or VM incarnation changed: read current state before preparing a fresh operation. HTTP 403 refuses another or unassigned owner; 404 identifies a missing VM. Store errors and five-second operation timeouts return 503. After an uncertain response, retry the exact payload and revision; exact replay succeeds while that state remains current. A fresh revision or changed payload is a different operation. Removal does not delete the revision, so an earlier creation request cannot revive it.

## Atomic route authorization

The [paired endpoint snapshot contract](benchmarks/2026-10-03/private-route-atomic-snapshot/README.md) passes in MemoryStore and owned Redis, with 98 cluster tests passing on final sources. Route lookup reads both VM records and both memberships atomically. It excludes missing/removed membership, mismatched owners and stale node or VM start timestamps. A destination can recheck a previously issued claim against a fresh snapshot; rejoining a tag or migrating changes the generation and invalidates the old claim.

A snapshot is connection context, not a credential. The destination must authenticate the source separately, load a fresh snapshot, check node liveness and actual local pending registration, then open the guest port. Source-side forwarding must reject its own pending registration before dialing. Neither this shared-store view nor a caller-provided boolean proves remote local-registration state. Existing-stream revocation and receiving-node tunnel integration remain unfinished.

## Receiving-node TCP route

The [receiving-node implementation](benchmarks/2026-10-03/private-receiving-node/README.md) compiles and passes 61 daemon tests and 99 cluster tests, with owned Redis enabled for the cluster contracts. It uses a cluster-authenticated mutual-TLS, bodyless HTTP/1.1 upgrade at `/sandboxes/{sandboxID}/private-ports/{port}/tcp`. Private route context is bounded and path-bound; lookup rechecks both current memberships, placement, node liveness and actual local guest registration. The destination lifecycle lock covers opening/registration, with authorization repeated before acceptance.

Cross-node source labels currently use the existing shared-credential cluster trust; they are not bound to distinct source-node certificates. Source gateway code must derive context from its own VM and refuse pending local publication before dialing. The route cannot treat guest-supplied headers as identity.

The implementation includes 128 node-wide private connection slots, stream cancellation guards and an authorization monitor. Runtime private payloads, half-close, revocation timing, lookup outage, lifecycle cancellation and capacity cleanup remain to be verified with owned KVM fixtures. Source guest gateway dialing, DNS and address allocation remain unfinished, so the comparison still marks VM-to-VM tag networking absent.

## Private address ledger

The [address ledger](benchmarks/2026-10-04/private-address-ledger/README.md) provides atomic, bounded allocation tied to a source incarnation and both endpoint membership generations. Concurrent requests for the same binding share one address. Rejoining creates a different address, and old addresses cannot authorize against the new generation. Entries are retained and never reassigned within the ledger; snapshots restore the same mappings. The complete cluster suite passes 109 tests with owned Redis, zero failures and one ignored.

Address persistence is not yet wired to Redis or VM lifecycle state. A newly allocated address must not be exposed before durable atomic ledger publication, and rollback to an older ledger must be refused. The production router must retain the claim generations through connector setup. These integration and crash-recovery gates remain unfinished, as do guest DNS and KVM guest-to-guest proof.
