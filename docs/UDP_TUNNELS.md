# UDP tunnels

`hm sandbox vm udp SANDBOX_ID --port 5353 --listen 127.0.0.1:0 --max-peers 64` publishes a loopback UDP listener and prints its address as JSON. Set HV2_SANDBOX_URL and HV2_API_KEY for the authenticated control-plane endpoint. The guest needs the current agent supporting ForwardUdp. Remote control-plane access should use configured TLS and the CLI's --api-ca-cert option for private trust roots.

Each local source address/port gets its own guest loopback UDP socket. IPv4 uses an HTTP/1.1 `hv2-udp/1` upgrade. Add `--guest-ipv6` to select guest `::1` over `hv2-udp6/1`; it never falls back to IPv4. Add `--listen '[::1]:0'` to select a local IPv6 listener independently. The transport uses a big-endian two-byte length followed by the datagram, preserving empty payloads and limiting each to 65,507 bytes. This is UDP over a stream tunnel, not native public UDP exposure; stream ordering can add head-of-line delay.

Peer count defaults to 64 and accepts 1–1024. Each session queues eight datagrams; excess queued messages and peers are dropped. Sessions close on transport failure, outbound inactivity or receive deadlines. Ctrl-C aborts and joins CLI tasks. Guest UDP socket setup acknowledgement does not prove a service is listening. Guest destinations are loopback only: IPv4 by default, or IPv6 with `--guest-ipv6`. Both families retain the 65,507-byte frame payload limit.

[Local latency characterization](benchmarks/2026-10-03/udp-latency/README.md) records two 100-sample runs with exact 64-byte replies. CLI P50 is about 0.96–0.97 ms and P99 varies from 1.53–2.44 ms. This is a development-build sequential fixture, not sustained throughput, fleet P99 or a competitor comparison.

[Real idle recovery](benchmarks/2026-10-03/udp-idle-recovery/README.md) verifies that sessions idle beyond their deadline release CLI peer slots and allow existing/new peers to reconnect. Exact expiry timing and sustained churn remain unverified.

[Two-peer HTTPS/mTLS characterization](benchmarks/2026-10-03/udp-concurrent-latency/README.md) verifies 1,000 measured replies per peer in two fresh runs. P50 is 1.06–1.09 ms and P99 1.49–1.56 ms. Short closed-loop completion rates are 1,612–1,705 round trips/second, not sustained capacity or a competitor win.

The CLI now emits complete frames with one write call. A [matched ABBA comparison](benchmarks/2026-10-03/udp-combined-write/README.md) measured about 20% higher local two-peer completion rate, with no consistent median-latency improvement. This is a development-build fixture result, not fleet capacity or competitor superiority.

A [matched 4 KiB follow-up](benchmarks/2026-10-03/udp-combined-write-4k/README.md) measured 15.4% higher average local completion rate with the same binaries. Median latency remained mixed; sustained workloads and resource tradeoffs remain unverified.

An [eight-peer 4 KiB comparison](benchmarks/2026-10-03/udp-eight-peer-4k/README.md) measured 10.5% higher average completion rate, with a 5.1% increase in the mean of per-peer sample medians. P99 is mixed. Combined writes therefore have a measured latency tradeoff under this workload; they do not improve every performance metric. The archived ABBA runner supports reproducible comparisons across 2–64 peers.

[Peer capacity recovery](benchmarks/2026-10-03/udp-peer-recovery/README.md) now releases task bookkeeping for successful, panicked and cancelled sessions. Injected failures verify slot release; a real CLI protocol fixture verifies existing/new source reconnection after upstream EOF with a one-peer cap. The revised binary passes eight-peer HTTPS/mTLS/Redis/KVM correctness checks. Earlier matched performance results concern preserved binaries predating this cleanup change; its performance overhead remains unmeasured.

A [matched development-build comparison of the recovery fix](benchmarks/2026-10-03/udp-peer-recovery-performance/README.md) measured 5.6% lower average eight-peer 4 KiB completion rate and 6.5% higher mean per-peer sample medians. The fix retains its verified correctness benefit, but this measured regression needs release-build evaluation and profiling; no revised-binary performance win is claimed.

The [matched release-CLI comparison](benchmarks/2026-10-03/udp-peer-recovery-release/README.md) measured 1.3% lower average eight-peer 4 KiB completion rate and 0.7% higher mean per-peer sample medians after cleanup. The remaining service stack used fixed development builds. Release EOF recovery passes, but the release profile uses `panic = "abort"`: panic-injection cleanup evidence applies to unwinding builds, and a release panic terminates the process. The small sampled regression does not establish equivalence or production overhead.

A [single-map cleanup experiment](benchmarks/2026-10-03/udp-single-map-deferred/README.md) passed correctness but measured 1.2% lower local release completion rate versus the retained two-map recovery binary, with nearly unchanged medians and variable tails. It was deferred and the verified implementation restored; fewer maps were not treated as proof of a resource/performance improvement.

Native public exposure remains incomplete.

A [lockfile audit](benchmarks/2026-10-03/udp-root-lock-alignment/README.md) shows identical parsed dependencies and aligns exact root lockfile/workspace manifest bytes; offline locked compilation passes. The accepted-core boundary remains, and the whole root worktree is not verified. Native public UDP exposure and competitor performance remain unverified.

A [matched guest-family comparison](benchmarks/2026-10-03/udp-ipv6-family-performance/README.md) uses the same binaries and IPv4 local peers, changing only IPv4 versus IPv6 guest selection. Average eight-peer 4 KiB rates are 3,916.1 versus 3,912.3 round trips/sec (IPv6 -0.10%); latency directions are mixed. This is short local configuration characterization, not proof of equivalence or a competitor win.
