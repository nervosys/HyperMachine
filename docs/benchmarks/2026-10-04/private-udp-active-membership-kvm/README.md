# Established guest UDP membership revocation

**41 checks pass** on two owned daemon nodes sharing one WSL host. An Internet-disabled source KVM guest establishes a connected UDP socket through the production Ethernet/private-router/mTLS path to a target KVM guest. The owned static client sends uniquely sequenced exact 64-byte datagrams on that same socket, confirms an initial exact echo, and remains active while the fixture removes membership. Separate cases remove the target and source membership.

After the membership API returns, the fixture writes a guest-local marker. The client allows a three-second marker-relative grace, then requires three consecutive unsuccessful sends/receives while continuing to use the original socket. Both phases pass. Target has nine successful grace-period replies; source has eight. No reply arrives for the three post-grace attempts in either phase. This is a bounded functional observation, not precise revocation latency, an EOF guarantee, or an SLA. No response or connected UDP refusal errors count as refusal. A negative local echo control keeps responding after the same marker: the client exits 5 rather than reporting revocation, demonstrating that the marker alone cannot pass this gate.

New numeric UDP attempts are refused while membership is removed. Rejoining each member retains old-address refusal, supplies a different binding through fresh DNS and restores exact empty/13/1,280/65,507-byte datagrams. Owner binding isolation, target stale-address recovery, receiving UDP framing/authentication, TCP/DNS membership closure and source pause/resume checks also pass. Zero guests remain and all tracked daemon/control/Redis/CLI/gateway processes are reaped.

Production sources and the frozen dev daemon are unchanged from the maximum-payload evidence. All 139 permitted root/isolate source pairs, accepted isolated core hashes and runtime input hashes are revalidated. Protected root core files were not read or built. The derived owned client image preserves the accepted base/production agent and independently rebuilds byte-identically. Only the owned C client and checker change. The existing daemon build evidence is in `../private-udp-max-source-guest-kvm/`.

Two failed fixture attempts are retained and excluded from success evidence: the first fails guest background launch with HTTP 500; detaching wrapper descriptors allows launch to proceed. The second reaches target revocation but rejects repeated readiness JSON from a client output bug. The corrected client emits readiness once, and the final fresh image/run passes both phases. No production defect is inferred from those fixture failures. Failed attempts do not emit success reports.
