# Private receiving IPv4 UDP

`GET /sandboxes/{id}/private-ports/{port}/udp` now accepts `hv2-udp/1` upgrades through the same private route context and authorization as TCP. The handlers share strict cluster mTLS/token/context prerequisites; both setup authorization checks, actual destination identity/pending/lifecycle checks, 128 shared private transport slots, activity leases, active-stream revocation and cancellation cleanup remain common. Guest forwarding uses the existing bounded u16 big-endian datagram framing and IPv4 UDP operation.

**64 ordinary daemon tests pass**, with two explicit KVM-only tests excluded from that suite. The owned two-daemon fixture passes **34 checks** with zero guests and every process reaped. An owned host mTLS client with a real running source guest identity preserves exact empty, 13-byte binary and maximum **65,507-byte** datagrams through the new receiver into a real target KVM UDP server. An oversized length prefix closes its session, and a later valid session recovers. TCP negotiation on the UDP endpoint, wrong cluster token, wrong source node, duplicate context, cross-owner and stale source-generation claims refuse. Rejoining the source membership closes the already-established UDP framed session.

This implements and verifies receiving transport only. Source guest UDP Ethernet interception, Rust source UDP connector/router integration and DNS-to-datagram delivery remain unimplemented. The host-origin test does not claim guest-origin UDP private networking or complete product parity. Both nodes share one host. UDP closure is inspected after the corresponding TCP closure wait, so its small reported additional observation time is not a UDP revocation latency measurement. IPv6 private UDP, UDP-specific lifecycle permutations, pending/owner mutation schedules, saturation, independent hosts and crash durability remain unverified or incomplete. No competitor or performance claim is added.
