# Focused repeated main-target pause/resume audit

The unchanged setup-overlap baseline performs its original resume and five added successful pause/resume cycles, then times out on the sixth added resume after 30 seconds. Every completed cycle requires prior-stream closure, fresh authenticated UDP upgrade and exact cycle-identified bytes. The targeted-wake candidate completes its original resume and all seven added cycles (**eight total**) and publishes its full successful report/cleanup. No timed retry or longer API deadline is used. Failure rows are journaled in `finally`. The diagnostic checker/driver are frozen temporary derivatives; root checker and production source are unchanged by this audit.

The baseline failing restore logs only seven vCPU exits before teardown, matching the previously retained candidate full-cohort resume timeout. This demonstrates that the failure can occur on the unchanged baseline; it does not prove a cause, establish a failure rate or excuse candidate lifecycle failures. The original four-cohort performance experiment remains incomplete. Raw cycle outcomes, failure stack, logs, candidate report/runtime hashes and process inventory are retained. Candidate guest/process cleanup is verified; baseline process inventory finds no tracked services, but no final guest-count report exists.

Permitted source inspection finds that `VM::pause()` sends `VCpuMessage::Pause` with ignored `try_send` results, kicks owners and writes `VMState::Paused` without an owner acknowledgement. Snapshot capture requires this state but does not await a pause acknowledgement. This is a concrete quiescence-contract gap and a candidate investigation target, not demonstrated causality for the seven-exit stalls. The Linux wrapper already restores with `ClockOnRestore::Continue`; changing clock policy is not justified by these artifacts. Frozen VM/wrapper source is included. Protected root backend/boot files were not read or modified.

Run `python3 verify-results.py` to verify cycle chronology/outcomes, retained timeout, candidate exact-data/cleanup report and diagnostic hashes. Full KVM saturation workload is absent from this focused audit; it cannot establish performance, fleet migration or competitor superiority.
