# Volume metadata flush and failure handling

Creation now exclusively opens the token-bearing metadata temporary file with mode 0600, writes it, syncs the file and data directory, atomically renames metadata, then syncs the volume directory and store root. Only after all operations succeed does creation report success. Before-publication failures clean up the owned empty reservation. After-publication sync errors return failure while preserving both metadata and data; duplicate retries conflict instead of replacing tokens. This avoids deleting the data directory after metadata is already visible.

All 45 isolated daemon unit tests passed, including injected errors at each of four sync stages, concurrent 16-creator exclusivity, incomplete-directory preservation, and metadata mode 0600. The owned two-daemon API fixture passed: one creation and 15 conflicts, matching winning token on both nodes, duplicate preservation, winning process restart, and cleanup. No guest was created; all daemons were reaped. Logs, API input hashes, and exact source are frozen here. Builds used accepted isolated core sources and did not overwrite immutable release benchmark copies.

This establishes syscall ordering and ordinary error/restart behavior, not simulated power-loss survival. Newly created store-root ancestors are not recursively synced: production store roots should be durably provisioned by the operator. Directory fsync support and guarantees depend on the filesystem; failures propagate to the API. NFS/RWX storage, Kubernetes rollout, guest data-write durability, and volume deletion durability remain unverified. Post-publication failure can leave a readable volume even though POST returned an error; preserve and inspect it rather than recreating the same ID.
