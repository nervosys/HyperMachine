# Strict discovery schema: HTTP boundary and KVM verification

The updated control binary passes 13 owned HTTP/Redis checks. Empty and single-entry pages return 200. Extra capability fields at top/row level, missing cursor, wrong kind, duplicate IDs, more than 32 entries, inconsistent short-page cursor, malformed JSON, a 20,000-byte body and an entry at the requested cursor return 502. The capability marker is absent from every public response. Wrong API authentication returns 401 without a node call. Every forwarded node request carries the correct cluster token and omits the client API key. Redis, control and HTTP listener are reaped.

Four real KVM profiles with the same updated control binary pass 27 checks each: SET/XADD failures across IPv4/two-peer and IPv6/eight-peer ingress. Valid discovery pages remain accepted; initial missing-record and resumed uncertain guests are discovered/reconciled through CLI, unauthorized scopes/unknown nodes refuse, and recovered entries disappear. Exact guest execution and forwarding succeed, with zero guests and all owned processes reaped.

The HTTP boundary fixture uses owned loopback plaintext HTTP and a fake registered node, not KVM or TLS. The separate real KVM cohorts use verified control HTTPS and node mTLS. Multi-page completeness remains tested by the 65-entry unit test rather than a 65-guest cohort. Truncated/chunked transport variants, automatic reconciliation, accepted-request cancellation and durable crash recovery remain unverified or incomplete. No performance or competitor advantage is claimed.

Current control source is built only in the isolated checkout and frozen. Node/CLI/gateway/kernel/image are unchanged immutable inputs from the prior discovery experiment. Reports retain input/checker hashes, status outcomes and cleanup. Source/checker/driver snapshots, build log, permitted source catalog and manifest preserve evidence; credentials, temporary policy files, guest descriptors and private keys are excluded.
