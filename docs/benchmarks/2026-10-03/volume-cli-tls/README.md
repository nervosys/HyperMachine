# Integrated volume CLI HTTPS verification

All five owned shipped-CLI protocol tests pass. A generated CA signs a separate localhost leaf with CA:false and DNS SAN localhost. Upload/download both succeed with --api-ca-cert and exact 1 MiB bytes; the server verifies bearer authorization and absence of a platform API key. Untrusted chains and a trusted chain with wrong hostname are refused before HTTP payload arrival. Both commands refuse redirects without a follow-up request. One-second client deadlines refuse slowly arriving response bodies; downloads leave no destination or staging file. Truncated and advertised 4 GiB+1 downloads also fail without local file publication. Every subprocess has an eight-second test bound, and all listener/request threads plus key/certificate directories are cleaned up.

The initial test fixture used its CA certificate as a server leaf; Rust correctly rejected it as CaUsedAsEndEntity. The final fixture uses distinct CA/leaf roles and validates the actual supported trust contract. No runtime TLS code changed for these checks. Exact CLI binary identity, test source and successful log are frozen. Build/source provenance remains in ../volume-cli-stream-download. No private certificates/keys, raw token values or uploaded bytes are archived.

These are direct owned endpoint tests, not a shipped control-plane HTTPS process, mTLS node forwarding, public CA operation, successful 4 GiB transfer, unknown-length overflow, network storage, KVM or performance evidence. The advertised oversized response tests refusal rather than transferring 4 GiB. Local HTTP real-storage checks remain separate in ../volume-cli-stream-download. No competitor win follows.
