# Two-node legacy adoption, claim race and actual migration

Two owned Redis/mTLS/KVM profiles pass 25 checks each. The final production node/control/gateway/CLI binaries and guest image are unchanged from the [administrator workflow archive](../legacy-owner-adoption-workflow/README.md). Only the checker adds --owner-adoption-cross-node, requiring --owner-adoption. It starts a second actual KVM daemon sharing the first node's snapshot directory and Redis namespace, with independent API/proxy ports and node identity. Generated cluster credentials and node/control TLS credentials remain private to the owned fixture.

Each profile exercises two cross-node paused-description orderings:

1. A two-worker barrier races adoption on node two against resume on node one. Both observed runs return resume 201 and adoption 409: the resume claims the description, and adoption refuses its unavailable claim. The checker accepts either valid claimant winning but does not infer every scheduling outcome from these observations.
2. A fresh ownerless paused VM is adopted on node two while writes on the owned Redis are paused for 300 ms. The checker observes node two's claimed description before attempting resume on node one. Resume returns 404 rather than bypassing the held claim; adoption completes with 204 and the returned description holds the correct principal. The finite write pause is a fixture control, not a production performance setting. A preliminary 1,500 ms pause exceeded the Redis client's response deadline and returned uncertain adoption outcome; that failed run and preliminary race-only runs are excluded from the accepted evidence.

The original raced VM is paused again if necessary, adopted on node two, then restored on node two. Redis must report node two, the assigned owner and running state. Guest execution returns an exact marker through the control plane. An owner-only both-protocol reservation is exposed and a temporary native gateway verifies 1 MiB of exact TCP plus UDP payloads of 0, 10 and 65,260 bytes through the migrated guest. An actual fork on the new node retains the assigned owner. Child and source deletion leave no allocation; live native TCP closes and the gateway stops gracefully. The second node stops gracefully after its guests are deleted. The original primary VM subsequently completes the normal one-node ownership/rotation/native-protocol/lifecycle checks.

IPv4 ingress uses two baseline peers and IPv6 ingress eight. Guest destinations remain IPv4. The migrated forwarding test uses one reservation; the earlier [sixteen-port mixed profile](../legacy-owner-adoption-workflow/README.md) retains its separate 33-check evidence. This archive does not claim sixteen-port migration or timed throughput/latency advantages. All owned processes are reaped and zero guests remain. Logs are checked for generated API/cluster credentials and the primary CLI workload token.

host-source-context.json is copied from the accepted final workflow source context. All 133 permitted root/isolated Rust source files and accepted isolated core hashes are rechecked before archiving; protected modified root core is excluded. Runtime reports hash every executable, kernel, image and exact checker before/after. Raw reports/logs, checker, image report and context are covered by manifest.json. No private certificate keys or policy files are archived. No Rust source changed or binaries were rebuilt here.

Reproduce with the accepted binaries/image and the checker command from the administrator workflow, adding --owner-adoption-cross-node and fresh output directories. The cross-node profiles use --tls --mtls --owner-context --owner-port-api --owner-port-cli --owner-adoption; capacity/mixed flags are omitted. Add --local-ipv6 --peer-count 8 for the second profile. The fixture requires an owned Redis supporting CLIENT PAUSE WRITE and POSIX shared snapshot claim semantics. The controlled 300 ms pause must remain below the store client's response deadline.

This establishes the observed resume-first and held-adopter-first races and actual ownership-preserving two-node migration. It is not proof of all distributed schedules, machine-crash claim recovery, managed failover, guest reboot persistence, public Internet operation or competitor performance superiority. The broader competitive goal remains open.
