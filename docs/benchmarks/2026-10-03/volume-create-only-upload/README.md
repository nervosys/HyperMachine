# Create-only volume uploads

PUT /volumecontent/{id}/file accepts overwrite=false; default remains overwrite=true. In-place mode uses O_CREAT|O_EXCL without truncation. Atomic mode stages normally and publishes with renameat2(RENAME_NOREPLACE), so absence at initial validation is not mistaken for permission to replace a concurrent winner. Publication conflicts map to 409 and unpublished staging is dropped. Non-regular targets continue to be refused. The helper exposes --no-clobber and sends overwrite=false.

All 46 daemon tests and eight owned HTTPS client tests passed. The expanded two-daemon API fixture runs 16 concurrent uploads for each mode: exactly one 201 and fifteen 409 responses in both atomic and in-place mode. Exact winning bytes are checked on both nodes; a subsequent create-only PUT conflicts. The actual streamed client also refuses --no-clobber on its existing destination with exact readback preserved. Existing binary/atomic-abort/token/root-upload/restart and cleanup checks pass, with all processes reaped and no guests created. Source, build/test logs and input hashes are frozen here.

This is exclusive creation, not an update compare-and-swap. Atomic mode needs temporary space for the whole upload and can discover conflict only at publication. Filesystems must support RENAME_NOREPLACE; unsupported operation fails rather than falling back to replacement. In-place creation is still streamed: the winning writer can leave a partial new file if interrupted. Atomic hard-kill orphan/post-publication uncertainty limits still apply. Shared local filesystem concurrency was tested; network-filesystem, power-loss and competitor performance are unverified.
