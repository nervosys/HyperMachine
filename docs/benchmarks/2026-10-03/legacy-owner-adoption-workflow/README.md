# Administrator legacy-owner adoption through real KVM

The shipped CLI now exposes `hm sandbox vm adopt-owner ID --principal-id LABEL`, backed by POST /sandboxes/{id}/owner with {"principalId":"LABEL"}. Successful adoption and same-owner replay return 204 and empty CLI output. Only authenticated legacy administrators or operator-role policies with admin scope may adopt. Sandbox/inventory scopes, observers, wrong credentials and anonymous mode cannot dispatch adoption to the node. A private administrator extension enforces that condition inside the handler independently of path spelling. Unknown fields and invalid principal labels are refused. Control forwarding strips API keys and client owner headers; a nonempty cluster token is required at control and node boundaries.

The node holds its transition lock while assigning ownership and updating its in-memory record. Running and paused VMs are supported. Portable paused descriptions are exclusively claimed, rewritten privately and returned. A Drop guard returns that description if the request is cancelled during store I/O; an explicit release error returns 503. Fork and resume resolve authoritative ownership from the shared store. Memory/Redis lifecycle record updates preserve an existing owner when given a stale ownerless record. Redis appends that owner to the original serialized JSON rather than re-encoding arrays in Lua, preflights ACL permissions and inventory key type before SET/SADD, and is tested to leave records unchanged when the inventory index is malformed.

The atomic store operation refuses existing different owners, missing records and ownerless VMs with per-VM public-port reservations. Same-owner replay is idempotent. This does not implement owner transfer or automatic reassignment/deletion of legacy reservations. Operators must remove legacy reservations through privileged maintenance before adopting such a record.

Verification: 87 cluster library tests, 31 control-plane HTTP tests, 48 node tests, 149 CLI tests and the explicit owned Redis/AOF fixture pass. Store tests include 32 competing principals, stale ownerless lifecycle updates, reservation refusal, JSON preservation and orderly AOF recovery. HTTP tests prove refusal before backend dispatch, body validation, both administrator categories, replay, no transfer and stripping of credentials/context. The new async node regression aborts an adoption task while it holds a paused description and verifies the description is restored.

Both final IPv4/two-peer and IPv6/eight-peer ingress profiles pass 33 actual Redis/mTLS/KVM checks. The primary VM is created ownerless by the shipped CLI under a legacy administrator, then adopted by the shipped CLI before native forwarding. It verifies one-port 1 MiB TCP and empty/binary/maximum UDP payloads, key rotation, protocol/removal/reexposure, fork/pause/resume/delete, and sixteen distinct both-protocol publications. Those capacity phases verify 1,600 UDP exchanges followed by 1,600 TCP exchanges, then 32 synchronized mixed workers verify a further 1,600 exchanges per protocol. Resource caps and exact distinct-destination tagging retain the [mixed capacity scope](../native-mixed-tcp-udp-capacity/README.md); no throughput/latency advantage is claimed.

Separate real legacy VMs verify administrator CLI adoption and replay while running, owner-only port access and wrong-owner refusal, different-owner transfer refusal, actual fork inheritance and pause/resume retention. Another VM is paused before adoption: the shared snapshot description is checked for the assigned owner before resume verifies that owner again. Every run leaves zero guests and reaps all owned processes. API/cluster credentials and the primary CLI-created workload token are checked absent from runtime logs.

Source context records 133 permitted root/isolated matches and accepted isolated core hashes; protected modified root core is excluded. Exact changed source/test/checker snapshots, immutable-input runtime reports, test/build logs and the unchanged image report are covered by manifest.json. No private keys or policies are archived. Intermediate runs before final claim/inventory guards are excluded from this evidence.

Reproduce with separately built final node/control/gateway and CLI binaries, the kernel/image identities in the reports, and the KVM checker flags --tls --mtls --owner-context --owner-port-api --owner-port-cli --owner-adoption --native-capacity --native-tcp-capacity --native-mixed-capacity. Use a fresh output directory; add --local-ipv6 --peer-count 8 for the second profile. The normal baseline command and image construction are documented in the preceding capacity archive.

The tested scope is owned single-node KVM with a shared snapshot store and IPv4 guest destinations. Cross-node adoption/resume races, interrupted-machine claim recovery, public Internet operation, guest reboot persistence and central organization identity remain unverified here. A 503 may follow a committed adoption; retry the same principal. Earlier performance archives retain their original source/binary context. This closes the verified administrator running/paused adoption workflow, not the overall competitive goal.
