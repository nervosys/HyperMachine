# Opt-in atomic volume uploads

PUT /volumecontent/{id}/file accepts atomic=true. It exclusively stages a private 0600 temporary file beside the destination through a pinned parent descriptor, streams the request, applies requested metadata, syncs the file, and publishes with renameat in that same directory. The parent and containing directory chain are synced before success. Existing non-regular destinations are refused. Ordinary failures before publication remove the owned temporary name and leave the previous destination intact. Default uploads remain in-place for compatibility.

All 46 daemon unit tests passed, including old-file preservation while staging and after abort, successful replacement, temporary cleanup, and symlink refusal. Two owned two-daemon API cohorts passed: atomic and default nested binary uploads/replacement, cross-node exact reads, wrong-token refusal, restart and cleanup. The atomic cohort also ends an authenticated upload before its declared length: the API returns 400, previous bytes remain exact, and no .hm-upload-* file remains. All processes were reaped; no guests were created. The exact source, build/test logs, fixture and input hashes are frozen here.

Atomic mode creates a new inode: open readers and hard links keep the old inode; metadata defaults to mode 0644 and current service ownership unless requested. It needs temporary disk space for the full new file. Concurrent writers are last-publisher-wins, not compare-and-swap. Parent namespace changes require caller coordination. A hard process kill may leave a private staging file; no automatic orphan deletion is implemented. Errors after rename may leave the new file visible while returning an error. Newly created force=true parent directories can remain after aborted upload. No power-loss, network-filesystem, performance or managed competitor claim follows.
