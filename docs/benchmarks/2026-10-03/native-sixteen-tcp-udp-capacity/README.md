# Sixteen simultaneous TCP and UDP publications through real KVM

Both owned Redis/mTLS/KVM profiles pass 30 checks. One actual shipped-CLI-created VM publishes sixteen distinct both-protocol reservations for guest ports 19000–19015. Each guest UDP reply includes its destination port; each TCP connection begins with that port as a two-byte tag. Full tags and payloads prevent misrouting all public ports to a single service from passing.

Sixteen UDP peers first complete 100 exact 512-byte round trips each. They remain live while sixteen TCP connections are opened together and a sixteen-worker barrier starts 100 exact 4,096-byte round trips per connection. This yields 1,600 verified UDP exchanges and 1,600 verified TCP exchanges per profile. UDP and TCP listeners/sessions coexist; the two transfer phases are sequential, not simultaneous mixed traffic. No measured retries or throughput/latency claims are made. Only readiness retries are allowed.

The owner listing matches all sixteen unique public allocations. The allocation window contains seventeen ports; a seventeenth reservation returns 409. The fixture then replaces one tagged destination with primary guest port 18082, retaining sixteen both-protocol publications. Pause closes all sixteen TCP sessions and unbinds all sixteen UDP sockets while allocations remain unchanged. Resume verifies the unchanged owner list, restores primary TCP/UDP and reconnects all fifteen tagged TCP/UDP destinations. Deletion closes all TCP sessions, removes all allocations and unbinds UDP sockets. TCP session closure is tested, not exclusive TCP bind after closure (TIME_WAIT can persist). All owned processes are reaped and zero guests remain.

IPv4 ingress uses two baseline peers and an aggregate session cap of 36; IPv6 ingress uses eight baseline peers and cap 42. Both use max namespace reservations 32 and the baseline per-listener UDP peer cap. Guest UDP/TCP destinations remain IPv4. These are configured functional capacity profiles, not equal-resource optimizations or fleet/public Internet benchmarks.

The TCP fixture gains opt-in --capacity: the original four services remain at 18080–18083 and sixteen streaming tagged services are added at 19000–19015. Default and --nodelay behavior retain the four original services. Accepted production host binaries already include Redis preflight validation and are unchanged from the [post-fix archive](../native-port-preflight-kvm/README.md); only the checker and TCP guest fixture change here. The fresh image retains the accepted base, agent and tagged UDP helper. image-report.json records the resulting hashes. The static TCP compile uses -O2 -Wall -Wextra -Werror. Existing 1 MiB primary TCP and maximum-size untagged UDP checks also pass in these runs.

host-source-context.json identifies the accepted isolated host source. Protected modified root core was excluded. Runtime reports hash executables, kernel, image and checker before/after. Source snapshots, image report, raw reports and runtime logs are covered by manifest.json; no private certificate keys or credential policy files are archived. The checker verifies generated API/cluster credentials and CLI workload token are absent from logs.

Reproduce from a fresh directory using the preceding [capacity command](../native-sixteen-port-capacity/README.md), adding --native-tcp-capacity alongside --native-capacity and using an image built with the capacity-capable TCP fixture. Add --local-ipv6 --peer-count 8 for the second profile. Guest reboot persistence, public DNS/firewall/Internet operation, central organization identity and competitor performance remain unverified.
