# Secret rotation and revocation on one guest HTTPS connection

Two owned KVM cohorts passed all 15 checks and cleanup: current isolated debug daemon with 128 bindings and one guest vCPU, and immutable optimized release daemon with one binding and two guest vCPUs. Each cohort made 22 successful upstream requests, including three transfers on one guest HTTPS connection. Curl num_connects was asserted to be exactly 1, 0, 0; this verifies guest connection reuse rather than assuming it from command structure.

The owned server handles the first transfer, then writes the rotated exact-ID policy and waits for successful SIGHUP reload before responding. It handles the second transfer, removes that scope and waits for reload before responding. The third transfer uses the same guest connection. Received headers/bodies are checked against original secret, updated secret, and unchanged placeholder respectively. Every Content-Length matches the verified body. The fixture restores the policy before fork/pause/resume checks. The result proves next-request behavior after completed reload on an established guest TLS connection. It does not claim byte-level behavior for a request already in flight during reload or atomic fleet-wide policy updates.

The owned upstream may use separate TLS connections per forwarded request; only guest-to-gateway connection reuse is asserted. The local certificate chain and hostname are verified. No managed competitor or keepalive performance comparison was measured. Private keys and raw payloads are not archived. Reports record binary/kernel/initrd hashes and process cleanup. Release source/build provenance is in ../secret-https-release/build-context.json; current debug daemon validation is in ../daemon-guest-sizing. The archived checker differs from the first debug run only in a report limitation string clarifying the optional keepalive mode.
