# Owner-only public-port API

Public port management now uses the authenticated policy principal and trusted creator recorded at VM creation. Opt-in `--native-port-range FIRST-LAST` enables GET `/sandboxes/{id}/public-ports`, PUT `/sandboxes/{id}/public-ports/{machine-port}` and DELETE on that destination. PUT accepts `{}` (TCP default) or `{"protocol":"tcp|udp|both"}` and returns 202 with machinePort/publicPort/protocol. Replay and protocol updates retain the allocated port. GET returns only reservation fields, not owner IDs. DELETE returns 204 for removal, 404 for no reservation; removed reservations can be safely recycled. Responses acknowledge store state, not immediate listener readiness/closure: the separately running gateway reconciles asynchronously.

Every owned store operation checks VM existence and exact non-null creator identity inside the same MemoryStore mutex or Redis Lua operation that reads/mutates indexes. The first reservation is protected too; no key digest or client owner header/body selects ownership. Ownerless records and wrong principals are refused. Legacy admin and policies without a principal cannot manage these routes; observers/inventory-only keys are denied by existing scope/role checks. Existing team-wide sandbox lifecycle/execution permissions remain unchanged. Privileged internal allocator methods remain separate for operator fixtures; HTTP handlers call only the owner-authorized methods. Unsupported custom stores fail closed. Management is disabled by default; the operator installs one immutable window of 1–4,096 nonzero ports. Store calls have five-second deadlines; a timed-out mutation may have committed and callers should retry the same idempotent request.

Verification includes 86 library tests (one explicitly invoked owned-Redis fixture ignored in that default suite), 30 HTTP control tests and one explicitly executed owned Redis/AOF test. The shared Memory/Redis owner contract rejects ownerless/other creators, runs 32 concurrent same-destination claims, retains protocol-update allocation, checks the 16-reservation cap, deletion and missing VM, and refuses a previous creator after a trusted record change. The HTTP test verifies disabled configuration, wrong/observer/inventory/unassigned/admin identities, unknown body fields, zero port, ownerless/missing VMs, all sixteen reservations, updates at the cap, pool exhaustion, owner removal and reuse of a freed port. Owned Redis restart retains the trusted owner and exact reservation; the old key/ACL/index-fault tests continue to pass. This proves orderly owned AOF restart, not physical power loss or managed failover. Six invalid operator windows are refused before store startup, and a valid window/help path exits successfully.

Two actual Redis/mTLS/KVM profiles pass twenty checks each: IPv4/two UDP peers and IPv6/eight peers, with the same frozen development host/CLI/kernel/image inputs. All reservation and TCP/UDP/both protocol changes in these profiles use the real owner API; Redis observations do not seed or mutate their allocations. Wrong principals are refused before first exposure, including forged owner headers. A separately created legacy VM's stored record is explicitly ownerless and all management operations are refused. Owner reservations forward exact native 1 MiB TCP and empty/binary/65,507-byte UDP. Two KVM forks retain creator identity but do not inherit or alter the source allocation. Actual policy-file SIGHUP rotation revokes the old credential while preserving owner and allocation for the replacement key. API removal closes the native TCP session/listener; reexposure restores TCP and UDP. Pause/resume retain the reservation and trusted owner; actual VM deletion removes its native index entries and sessions. All owned processes are reaped, zero guests remain, and generated fixture credentials are absent from logs.

Host binaries were built only in accepted isolated `/var/tmp/hm-egress-log-mA2CCL` and frozen to fresh paths. The archive identifies 133 matching permitted source/manifest/test files and revalidated accepted isolated core hashes. Protected modified root core sources were not read, built or staged. This is limited accepted-context verification, not whole-root verification. Reports hash the executable/kernel/image/current checker before/after; exact sources, logs and provenance are covered by manifest.json. Earlier checker iterations and the earlier narrower HTTP test are excluded. No certificate private keys or policy files are archived.

Reproduce with a dual-service guest image, compatible owner-aware host binaries and a fresh output directory:

```sh
python3 tools/check-udp-cluster-kvm.py --daemon /path/hv2-sandboxd \
  --control-plane /path/hv2-control-plane --cli /path/hm \
  --kernel /path/bzImage --initrd /path/native-fixture.cpio.gz \
  --native-gateway /path/hv2-native-gateway --tls --mtls --owner-context \
  --owner-port-api --output /fresh/results
```

Add `--local-ipv6 --peer-count 8` for the second profile. Current native guest UDP negotiation remains IPv4. Gateway availability/readiness barriers, native management CLI commands, explicit legacy adoption/ownership transfer, guest reboot, public DNS/firewall/Internet operation, central organization identity provisioning, fleet byte quotas and competitor performance remain incomplete or unverified. The sixteen-port limit is verified for reservations over HTTP and both stores; these KVM profiles publish one reservation per VM, not sixteen simultaneous external public listeners. No performance score or across-the-board competitive win follows from this feature verification.
