# Initial unnamed creation: explicit-node CLI recovery

Four fresh real KVM profiles pass 25 checks each, covering SET and XADD refusal in IPv4/two-peer and IPv6/eight-peer configurations. The fixture denies the selected command on its owned Redis instance, creates through the trusted mTLS node API, asserts a 503 response and identifies exactly one new preserved guest through node-local inventory. SET refusal leaves no shared sandbox record; XADD refusal leaves a committed running record. Both refuse pause mutation while registration is pending.

After restoring the command, the shipped CLI invokes administrator control-plane recovery with explicit registered node and preserved sandbox ID. It succeeds even when the sandbox record is absent. The resulting shared record retains owner identity and running state; exact command execution returns initial-recovery-ok with exit code zero. The preserved guest is deleted and disappears from node-local inventory. Each profile then exercises the existing resume failure/recovery, scoped-key refusals, exact forwarding and complete guest/allocation/process cleanup.

These checks prove initial record/event failure recovery on a known node using local inventory. Initial creation is issued directly to the authenticated node; automatic control-plane discovery of missing registrations and a failed CLI create-response workflow are not measured. Cancellation, committed reply loss, response-bound runtime refusal and machine-crash recovery remain unverified or incomplete. Exactly-once lifecycle events and performance superiority are not claimed.

The first attempt used incorrect execution request fields and stopped after successful initial recovery; the fixture was corrected to the established cmd/timeout_secs and exit_code shape. Fresh v2 cohorts are accepted evidence; v1 is excluded. Frozen production binaries are unchanged from the prior recovery CLI experiment. Build/source provenance is retained under ../registration-recovery-cli-kvm and ../registration-recovery-cli. Raw reports/logs, checker/driver snapshots, verified runtime hashes and manifest preserve scope. No private keys, policies, credentials or descriptor bodies are archived.
