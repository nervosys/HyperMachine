# Retained high-concurrency readiness snapshots

An owned Firecracker guest booted the exact kernel/initrd from the 16/32 cold-slot cohort and supplied symbol bounds for all 10 distinct RIPs in its 19 failed HyperMachine attempts. The probe passed, guest/process cleanup passed and all input hashes were unchanged. This is a separate diagnostic guest; none of its timings enter benchmark rankings. The failed cohort is copied unchanged here and remains preserved in the original archive.

Ten timeout snapshots are halted at `default_idle+15`. Nine are runnable at addresses in `__pick_eevdf`, `__queue_work.part.0`, `inode_init_once`, `note_page` (two addresses), `perf_event_task_tick`, `ptdump_pte_entry`, `rcu_sched_clock_irq` and `security_task_prctl`. These are heterogeneous snapshots, not evidence that every failure had the same listener-backlog or interrupt cause. Symbol bounds come from a separately booted identical kernel, not execution traces from failed guests.

All 19 snapshots contain TSC/deadline values. Six deadlines are zero; two nonzero deadlines are at or before the sampled TSC. The MSR reads are sequential rather than atomic, and the failure diagnostics include different capture phases. These comparisons do not prove missed timer delivery, a stuck listener or a root cause. A timer workaround is not justified by these snapshots alone. The current scored benchmark and runtime settings remain unchanged.

The agent's repeated-refusal timeout wording previously claimed the service was listening but busy. Refusals alone do not establish this. The message now says the agent may be absent, still starting or busy. No connection loop, deadline or retry logic changed. All 13 existing guest-agent unit tests passed on Linux and Windows using clean source copies; the three provisional core boot/backend changes were excluded. The diagnostic guest image and previously accepted benchmark daemon were not rebuilt for this message change.
