What Actually Ran

A thousand hardware-isolated agents run at once under a command graph, a unikernel reaches executing code in 2.67 ms, and a sandbox costs 0.157 MiB. Every one of those is measured. What is new is that the path an agent payload would take is now closed end to end: a unikernel written in Rust, compiled by the ordinary toolchain, booted by Multiboot, receiving a swarm message over vsock — and shutting down afterwards, which no VM had ever done. The Type-1 hypervisor has also now hosted a guest, nested under the Type-2 one — a smaller claim than bare metal and a much larger one than compiling.

The one thing to read first

VM::stop() returns now. It never had before.

Before this it did not return slowly — it did not return at all, at twenty seconds, for every guest shape tried. examples/halt_stop_probe is those same three variants, differing only in what the guest does before shutdown, run against both: 

write-then-halt : DID NOT RETURN within 20 s   →   returned in 0.7 ms   console "."
halt-only       : DID NOT RETURN within 20 s   →   returned in 0.8 ms   console ""
spin-forever    : DID NOT RETURN within 20 s   →   returned in 0.7 ms   console ""

stop() clears the running flag, sends each vCPU a Stop message, then awaits the vCPU task handles — all of which depend on the vCPU leaving KVM_RUN, and none of which a thread inside the ioctl can observe. It could not be made to leave, because KvmVcpu::run retried on EINTR unconditionally: 

Err(e) if e.raw_os_error() == Some(libc::EINTR) => continue,

That retry is exactly the mechanism a VMM uses to kick a vCPU out. Without a check before it the vCPU was uninterruptible by construction: a guest that stopped exiting to userspace, by halting or by spinning, owned its thread until the process died.

Diagnosed against a hung process: 0% CPU, all 28 threads sleeping, vcpu-0 at wchan = kvm_vcpu_block, everything else parked on futexes. Nothing starved and nothing raced, which is what said the problem was reachability rather than scheduling.

The fix is three things, because a kick has three moments to miss

Getting a vCPU out of KVM_RUN
PartThe moment it covers
SIGRTMIN, handler installed without SA_RESTART A vCPU already inside the ioctl. With SA_RESTART the kernel restarts the call itself and userspace never learns the signal arrived. A real-time signal rather than SIGUSR1, which belongs to whoever embeds this crate.
kvm_run->immediate_exit A vCPU that has not reached the ioctl yet, at which a signal would be aimed at nothing. KVM checks this on the way in and answers EINTR without entering the guest.
A per-vCPU flag, read by the EINTR arm The retry itself. This is what turns a delivered signal into a returned call instead of a re-entered guest.

The ordering is what makes the race benign: the flag and immediate_exit are both set before the signal is sent, and run() checks the flag after publishing its thread id and before entering the ioctl. A kick landing anywhere in that window is latched and seen at the next entry — the difference between a shutdown that hangs intermittently and one that does not hang.

HypervisorBackend::kick_vcpu is how stop() reaches it, and VmExit::Interrupted is what a kicked vCPU reports. The run loop continues on that exit, which sends it to the top of the loop to read the flag and the control channel — the reason it was kicked. No guest state is touched, so re-entering is correct when the kick was for something else. tests/vcpu_kick.rs asserts on the effect, that stop() completes, and covers the before-entry race separately by requiring a pending kick to end a run without the guest being entered.

This changes how to read the older numbers below. Runs that appeared to finish were killed by their timeout after printing. The measurements were already on stdout and are unaffected. The 1,000-VM figure has since been re-run and now ends by exiting: 59 seconds, all 1,000 guests executed, 0.157 MiB each, every stop() returned.

What shipped

The cold start was never measured, and the first measurement found a 474× defect

Nothing in this repository had ever timed a boot. vm_bench, whose results are published to gh-pages, measures guest-memory allocation and snapshot serialisation — neither is a boot. So no performance claim about HyperMachine could be checked in either direction.

hv2-agent --example cold_start is the instrument. It reports percentiles decomposed into four phases and refuses to print a number it did not measure. Its first run said launch was 998.79 ms and scaled with guest memory — the shape of touching every page.

The cause was one line and one alignment. create_vm allocated guest RAM with alloc_zeroed at 4096-byte alignment, and Rust forwards that to calloc only when alignment ≤ MIN_ALIGN (16 on x86-64). A page-aligned request took the other branch: aligned_alloc then write_bytes(ptr, 0, size) — a full memset of the guest's RAM, zeroing memory the kernel already guarantees is zero. Measured on the host: calloc of 1 GiB is 0.0 ms, memset of 1 GiB is 848 ms. The memset was the cold start.

It decided density as much as latency: a 1 GiB VM cost 1 GiB of host RAM before executing an instruction. Now an anonymous mmap, faulted in lazily.

Concurrency was capped at one VM per core, on the path a sandbox takes

run() chose between two execution paths. run_parallel gives each vCPU a thread; run_single awaited backend.run_vcpu() inline on the shared runtime, and run_vcpu blocks inside KVM_RUN. The condition sent a VM to run_single unless it had multiple vCPUs and parallel_vcpu, or pinned affinity — and a sandbox is a one-vCPU VM with neither.

23 VMs worked; 24 hung at 0% CPU on a 24-core host. After routing every VM through the threaded path: 1,000 concurrent VMs, all 1,000 guests verified as having executed, 156.75 MiB between them.

Worth knowing for next time: the first attempt at this fixed spawn_vcpu_task and changed nothing, because run_single never called it. The fix was applied to the path the measurement was not using, and only the measurement caught that.

A unikernel boots, and having no kernel is the whole argument

BootSource::Raw named unikernels in its documentation and the only example using it loaded examples/guest_code/hello.bin — a path that has never existed in this repository. It has never been runnable.

hv2-core --example unikernel_boot assembles its guest in-process so it cannot rot into a missing asset: 73 bytes of 16-bit real mode that write to COM1 and halt. First output at 2.67 ms median over nine runs. Every out leaves the guest, is decoded here, and lands in a device model, so the console line proves the whole path — which is why the example prints the console rather than a success line.

An orchestration layer that enforces rather than describes

hv2-swarm is a command graph: down is a command to any descendant, up is a report to the immediate parent only, sideways needs an explicit one-way grant, everything else is refused with the rule named. A message may also name a capability, and then the recipient must hold it — and on a command, so must the sender. Authority delegates downward but does not amplify; without that rule every capability in the swarm belongs to anyone with a subordinate who holds it.

Swarm::send is the only way a message moves and consults the graph inside it. The tests assert on delivery, not on verdicts: a rule that returns "denied" while the message still arrives passes a verdict test and fails the swarm. hv2-core is a dev-dependency, not a dependency — the policy layer needs no hypervisor to decide who may talk.

examples/guest_transport carries a message across the host/guest boundary over COM1 and watches the guest echo it, with the refusal verified at the recipient's console rather than at the sender's return value.

A Multiboot guest was not silent; it was executing its own file header

The loader wrote every Multiboot image to 1 MB verbatim and entered it at its first byte. That is correct for a flat binary and wrong for anything a linker emits: an ELF's first byte is \x7fELF, and 7F 45 decodes as jns +0x45, so a compiled kernel jumped 0x45 bytes into its own header and died quietly. Single-stepping the old loader shows it exactly — 0x100000 → 0x100047, then a fault.

That is why every guest that ever ran here was hand-assembled and nothing from a toolchain ever did. The specification gives an image two ways to say where it belongs and neither was read. MultibootProtocol::place_kernel now honours the header's own address fields when flags bit 16 is set, and the ELF32 program headers otherwise — segments at p_paddr, the tail past p_filesz zeroed as .bss — falling back to flat-at-1 MB only for an image that says neither. examples/multiboot_probe runs one guest program built all three ways; against this commit all three speak, against its parent only the flat one does.

A guest a compiler produced, and what it proves that assembly cannot

Every guest until now was hand-assembled bytes. That proves the hypervisor works and proves nothing about whether anyone can write a guest for it, which is the only question that matters for an agent payload. crates/hv2-unikernel is a no_std Rust binary: no scheduler, no init, no allocator, no syscall boundary, because there is nothing on the other side of one.

It prints a greeting, then EAX and EBX. The greeting proves the ELF was loaded by its program headers and entered at e_entry. EAX proves more: the specification says a bootloader leaves 0x2BADB002 there, and nothing but the loader can put it there, so a guest reporting it was booted by the protocol rather than jumped to. It reports magic 0x2BADB002 OK.

Stable Rust, no nightly and no -Z build-std: i686-unknown-linux-musl is the 32-bit x86 target rustup ships a prebuilt core for, and nothing Linux survives — the crate links with rust-lld and no C runtime. First output at 3.6 ms median over nine boots, against 5.3 ms for the hand-assembled guest on the same host: being compiled costs nothing.

A swarm message that reaches an agent, over a socket rather than a wire

The host has had a complete virtio-vsock device for some time — split virtqueues walked out of guest memory, connection state, credit accounting. What it never had was a guest that could talk to it, so every delivery here was a byte written to a serial port: real, one-directional, and not a socket. hv2-unikernel/src/vsock.rs is the missing half — a virtio-mmio bring-up, two split virtqueues, and the packet protocol.

hv2-swarm --example vsock_swarm boots three unikernels, connects to each, and runs the command graph over them. A command from the root reaches a worker and comes back echoed; a message between siblings is refused and does not arrive, checked at the recipient, whose guest echoed nothing and printed nothing; granting the edge makes the same bytes arrive, which is what distinguishes an enforcing transport from a broken one. Round trip 1.2 ms.

The driver polled at first — no IDT, no handler, a spin on the used ring — which was only tolerable because of the fix at the top of this page: before stop() could kick a vCPU out of KVM_RUN, a spinning driver would have been unstoppable rather than merely busy. It sleeps now; the section below is what that took.

An idle agent sleeps, and stops costing a core

A polling guest costs a host core for as long as it runs, which was the one figure on this page worse than a Linux container's: a container doing nothing costs nothing. An IDT, a programmed PIC, one handler and sti; hlt in the idle path fix it, because a halted vCPU is a thread blocked in KVM_RUN and a thread blocked there is one the host never schedules.

Measured over the same three-agent vsock_swarm run, warm, twice each: 

polling    user 1.82 s, 1.88 s
sleeping   user 0.65 s, 0.37 s

Three of the four pieces are one-liners. The fourth is the PIC: KVM's in-kernel 8259 comes up unprogrammed, and an unprogrammed 8259 delivers IRQ 0-7 as vectors 8-15 — which are processor exceptions, so the remap is the difference between an interrupt and a double fault. The handler acknowledges the device before the PIC, because the virtio line is level-triggered and held until InterruptACK; the other order is re-entered immediately and forever.

Two defects, and both presented as the console stopping mid-word. iret is the 16-bit form in Intel syntax, which is what global_asm! uses — the 32-bit one is iretd — so the handler ran perfectly and returned to a garbage selector popped off a frame of the wrong width. And the i386 ABI wants ESP 16-byte aligned at a call, which an interrupt frame plus pusha does not leave it; this target's core is built with SSE2, so a compiler-emitted movaps against a stack slot faults on a misaligned one.

A fault with no gate is a general protection fault, which also has no gate, which is a triple fault — and from outside, a triple fault is a console that stops. So the guest now carries thirty-two exception stubs, one per vector, each pushing its own number into a handler that prints the vector and the three words the CPU pushed. The moment that existed the answer was one line: 

FAULT vector 0x0000000D frame 0x00000010 0x00100026 0x00000008

#GP at 0x100026, which objdump showed to be the iret. The lesson is the ordering: fault reporting belongs before interrupt handling, because a guest that says "vector 13 at this address" can be debugged and a guest that stops mid-word can only be bisected.

And then a thousand of them, which is the measurement this is about

The thousand-agent figure on this page has always come from unikernel_swarm, whose agents halt immediately and never speak — which measures the hypervisor rather than the swarm. vsock_swarm ran three that did speak, because a polling guest costs a core and three cores is a demonstration where a thousand is a fan. With idle agents halting there is no longer a reason for those to be different numbers. 

agents        : 1000 unikernels booted and connected in 37296.6 ms
memory        : 220.79 MiB resident, 0.221 MiB per agent
idle          : 0.02 s of CPU across 1000 agents over 3.0 s — 0.7% of one core
stop          : 1000 halted guests in 612.7 ms

Every one is a full VM with its own vsock device, its own context ID and its own open connection, and the command graph's three checks still pass against the first three of them. The idle figure is measured as CPU consumed over a window of wall time rather than with a timer — for a halted guest those are unrelated numbers and for a spinning one they are the same, which is the distinction being made — and it is read from /proc/self/stat, so it counts every thread the process owns, including a thousand vCPU threads and their interrupt and vsock pumps.

Two caveats, both in the example. The 37 ms per agent is serial setup and mostly polling granularity — the loop waiting for a guest to announce its device and then for the handshake sleeps a millisecond at a time — so it is not a measure of how fast a VM boots; rust_unikernel puts that at 3.6 ms. And 0.221 MiB per agent is more than unikernel_swarm's 0.157 MiB because these agents have what those do not: a device, a driver, an IDT and a connection.

The Type-1 hypervisor executed, for the first time

Every claim ever made about hv1-core was a claim about rustc. The reason never changed: it is a bare-metal hypervisor and there was no bare metal to put it on. There still is not — but hv2-core can now boot a Multiboot ELF, and this host's CPU offers AMD-V to its guests, so there was somewhere else. 

efer  0x0000000000000500 LMA — 64-bit
svm   available
hv1   version 1.1.0
hv1   initialize() OK
hv1   efer now 0x0000000000001500 SVME set — the CPU accepted SVM

The last line is the one that matters, because "OK" is a verdict. svm::initialize()'s entire architectural effect is setting EFER.SVME, so the MSR is read back afterwards: 0x500 before, 0x1500 after, bit 12 set by hv1's own code. An initialize() that returned success and enabled nothing would read as a pass and fail at the first VMRUN; the example calls that a failure.

What it does not prove. Not hardware: the layer underneath is KVM, and a guest sees the CPU its hypervisor chose to show it. And not, at this point in the afternoon, a working hypervisor — initialising is the first step, and hosting anything was still ahead. That distance is said in the example, in the guest, and in the pillars table above, because the gap between "ran nested" and "runs on a machine" is exactly the kind this page exists to keep open.

Two pieces of machinery were needed. The image is an ELF64 and the specification's ELF path is ELF32, so the header carries its own load addresses — the a.out kludge, filled in from linker script symbols, and the first real image to use the path added when the Multiboot loader was fixed. And boot.rs crosses from the 32-bit mode Multiboot hands over in to the long mode a 64-bit hypervisor needs: page tables, CR4.PAE, EFER.LME, CR0.PG, far jump. The two arguments cannot travel on the stack across that — a 32-bit push writes four bytes and a 64-bit pop reads eight, so the first pop returns both glued together — and go in EDI/ESI instead, where the 64-bit ABI wants them anyway.

And then it hosted a guest, which found three defects in an afternoon

Initialising is not hosting: a hypervisor that enables SVM and never enters a guest is one MSR write away from doing nothing. So the next thing was VMRUN — a VMCB the hardware accepts, a guest that executes, an exit that says why, and a second entry afterwards. 

hv1   guest exit 1 0x81 VMEXIT_VMMCALL — the guest called its hypervisor
hv1   guest exit 2 0x78 VMEXIT_HLT     — the guest halted

Two exits rather than one, deliberately. One entry proves a guest ran; two prove the hypervisor stepped over the intercepted instruction and went back in, which is the difference between a hypervisor and a launcher — an intercepted instruction nobody advances past is re-executed forever. The guest is four bytes of real mode, vmmcall then hlt, and it is vmmcall because nothing else produces VMEXIT_VMMCALL, so the exit code cannot be a coincidence.

Three defects, each found by running and none findable otherwise.

What only execution found
DefectHow it presented
svm_run's asm! had no input operands at all — it assumed RDI held the register block and RSI the VMCB, the reverse of what the ABI passes, and computed vmcb_pa into a local nothing read It had never been executed, so it presented as nothing whatsoever. RAX, which is where VMRUN takes its VMCB address, was loaded from the slot holding the register block
Nested page tables need the U/S bit at every level VMEXIT_NPF on the first instruction fetch, at an address that was plainly mapped. A nested page walk is a user-mode access whatever the guest's CPL, and nothing in a kernel's own map is user-accessible
setup_vmcb_controls sets the IOIO and MSR intercepts and neither bitmap address The hardware reads both maps whenever those bits are set, so a VMCB built entirely by the crate's own helper fails VMRUN's consistency check before a guest instruction runs

Using the bare svm::vmrun helper instead is what made the console stop mid-word: #VMEXIT restores only RAX, RSP and RIP, so every other host register came back holding a guest value and the next thing the host did ran on the guest's data. That is precisely what svm_run exists to prevent, and why the broken one mattered.

A fourth was self-inflicted and worth recording for the shape of it. A Vmcb is four kilobytes constructed by value; the boot stack was 16 KiB and sat directly above the page directory, so building one overflowed into a page table and the machine died several instructions later inside a print, nowhere near the cause. The stack is 128 KiB now with a guard page under it, so the next overflow faults on its own address instead of quietly rewriting a translation.

A model costs a fleet once, not once each

The agents these unikernels are for run small language models with task-specific tools, and talk to each other under the permission graph. That changes the arithmetic that every figure on this page rests on. An agent VM costs 0.221 MiB because it holds nothing but its own code; an agent that runs a model holds the model, and a 0.6-billion-parameter model at four bits is around 350 MB. A thousand private copies is 350 GB, and "a thousand agents on a node" does not survive contact with the thing the agents are for.

They do not need private copies. Every agent in a fleet runs the same weights, reads them and never writes them, which is exactly a shared read-only mapping. Measured, a thousand agents against a 350 MiB region: 

region        : 350 MiB filled — resident grew 350.1 MiB
read the ROM  : 1000 of 1000 read 0xa7 at 0xe0000000, write refused
resident      : 526.9 MiB total, 176.9 MiB from the agents
per agent     : 0.177 MiB
if copied     : 1000 x 350 MiB would be 341.8 GiB
saved         : 341.3 GiB, 99.85% of what copying would have cost

Every VM in this process is backed by host memory in this process, so handing several VMs the same host address for a memory slot copies nothing: the pages behind them are the same physical pages. Read-only is enforced by the hardware and checked from inside the guest rather than asserted here — every guest writes to the region, reads it back and reports whether the write took, because one writable copy shared by a thousand agents is a thousand agents able to rewrite each other's model.

The guests read it too, for the reason this page always gives: a region that is mapped and unreadable costs exactly the same and is worth nothing. That check earned itself immediately — an unmapped guest-physical address reads as 0xFF rather than as zero, so a guest reading nothing and a guest reading a region of zeroes are indistinguishable without a marker.

And what an agent costs once it holds a context

Sharing is the half a fleet does not pay for twice. The other half it pays for per agent, and for a language model that is the KV cache — which cannot be shared with another agent by definition, since it is that agent's conversation. That number, not 0.221 MiB, is what density now depends on, so it is worth knowing whether private guest memory costs what it should or carries a multiplier.

It does not. A hundred agents, a 350 MiB shared model, 24 MiB of private working set each: 

touched       : 24 MiB each — 24.184 MiB per agent, +0.184 MiB against what was asked for
resident      : 2768.5 MiB total
if copied     : 100 agents x 374 MiB would be 36.5 GiB
saved         : 33.8 GiB, 92.60% of what copying would have cost

The overhead is 0.184 MiB, which is what an agent costs holding nothing. So the density of a fleet is the model once, plus per agent exactly what that agent touches — measured rather than assumed, because a hidden factor of two would have halved how many agents fit on a node and nothing in the code would have shown it.

Worth knowing for whoever sizes a node from this: a KV cache for a small model is roughly 12 KiB per token at two bytes per element, so a 2,000-token context is around 24 MiB and a 8,000-token one around 96 MiB. The formula is what this measures; the constant is the model's and belongs to whoever picks it.

An agent asks for a tool, and holding one is a permission

A sandbox that can only talk to other sandboxes is not much of an agent. What makes it one is tools — reading a file, calling an API, spending money — and what makes it safe is that holding a tool is a permission rather than a property of the code. An agent that can decide which tool to call can also decide to call one it should not have, and the point of a hardware-isolated sandbox is that deciding is not doing. 

trusted       : asked, allowed, tool returned "heimdall"
untrusted     : asked, refused, tool not called
tool ran      : 1 time(s), for 2 agents that asked

Two agents, identical images, one grant between them. The assertion is the last line, and it is counted at the tool rather than at the broker that gates it: a gate that refuses and then calls anyway is indistinguishable from a working one at the agent, and distinguishable everywhere that matters. Same reason the swarm's own tests assert on delivery and not on verdicts.

The capability is checked where a request crosses from a guest into the host — one place, consulted inside the thing that does the work. Capability and holds already existed for messages between agents; a tool call is the same question asked of a different edge.

What is honest about the agent here: nothing in the guest decides anything. A task beginning do: is answered with tool: and the rest, by one rule, standing in for a model choosing a tool. What is under test is the path a decision travels and the permission that governs it — neither of which cares how the decision was reached, which is exactly why it can be measured before there is a model to do the deciding.

How fast a guest can stream weights, and what that rules out

Memory was the question that decided whether a fleet could hold a model. Bandwidth is the one that decides whether it can use it. The loop a quantised forward pass is made of — read a weight, multiply by an activation, accumulate — run over the shared region, twice, reporting each pass separately: 

arithmetic : 13.20 cycles/byte cold, 1.66 warm

The two are separated because they answer different questions. The first pass takes a nested-paging fault per page — 65,536 VM exits for 256 MiB — and pays it once for the life of the VM. The second is the steady state. A single number would have described a warm-up as a per-token cost, which is a factor of eight in the wrong direction.

At 1.66 cycles/byte a 350 MiB model is about 0.6 Gcycles of weight streaming per token per agent — before any attention, softmax or dequantisation. That is a floor rather than an estimate, and it is the number worth having, because it rules something out: a thousand agents inferring at once on one model would need hundreds of GB/s of aggregate bandwidth, which no node has.

A thousand agents that are mostly idle is a completely different proposition, and that one is already measured at 0.7% of a core. So the fleet scales on the axis it was designed for — many sandboxes, cheap, isolated, talking under a policy — and inference is a resource to be scheduled across them rather than something every guest does simultaneously. Whether that scheduling belongs in the guest, in the host, or in a capability the guest invokes is a design decision this measurement informs and does not make.

What that settles about the architecture, and what it does not

One thing is now measured and the rest follows from it or is still open. Keeping those apart is the point of this page.

What is left open is the guest itself rather than the machine under it. The hypervisor's side of an agentic fleet is now measured end to end: a model shared once, a working set that costs what it is, a channel that reaches inside the guest, a policy that refuses, and an idle agent that costs nothing. What has never run is an agent — a model, a tokeniser, a tool call — and everything above is the floor that sits under one.

Two failing tests, and neither was flaky

Both had been failing long enough to be read as background. That is the dangerous state for a test to be in — noise a reader learns to ignore is how a real failure gets ignored too — and neither turned out to be the flake it was filed as.

test_timer_frequency already ran on a paused clock and still counted 16 or 17 of 19 ticks, because the thing it counted did not: update_count read std::time::Instant to decide how far to advance the PIT, so under a paused clock it advanced by almost nothing. The fix is not a tolerance band. advance_by(Duration) takes the elapsed time from its caller and the periodic task passes its own period — which is the more interesting half, because measuring the wall clock meant a tick delayed by the executor advanced the emulated PIT by the delay, and a guest reading its own timer learned how busy the host was.

test_vm_creation_with_backend asserted the backend was Tcg or Whpx — the two it was written on. KVM satisfies neither, so it passed everywhere it had ever run and failed the moment a Linux host with /dev/kvm ran it. A test that names the backends it was developed against fails when the code starts working somewhere new.

Quotas that refuse, at the point every VM operation crosses

AgentPolicy carried quotas and rate_limits and neither did anything: allows consults enabled and permissions, so a sixth VM was created under a max_vms of five and nothing ever constructed the QuotaExceeded that exists for the purpose. The machinery to count was never missing — RateLimiter was already in limits.rs. Somewhere to put the count that a caller could not go around was.

GovernedVmHost is a VmHost that wraps another one, and a refused operation never reaches the inner host. Every test counts what arrived at the host underneath rather than reading the governor's answer, because a governor that refuses correctly and delegates anyway is indistinguishable from a working one until the host runs out of memory. The same shape as Swarm::send, for the same reason.

Open, with diagnosis

Eight items that stood here have been closed. What is left is the one thing this machine cannot do, two things that still compile and have never run, and one honest edge of what shipped. Nothing on this list is a failing test: the suite is green, which it had not been for a while.

1. hv1 has still never run on hardware

It initialises and it hosts a guest, both nested under hv2, and that is as far as this machine goes. The layer under it is KVM, so it read a CPU that a hypervisor chose to show it; the firmware path, the real memory map, the AP bring-up and every device are untested, and nesting hides all of them. That needs a machine and a serial console, and nothing here substitutes for it.

The guest it hosted is also four bytes of real mode. Between that and an operating system lie an exit handler worth the name, an IDT, interrupt delivery, and a device or two — all of which can be built and run on the nested path, and none of which have been.

2. ARM Type-1 has not executed at all

hv1-arm — EL2, stage-2, vGIC — is where hv1-core was a day ago: it compiles, on nightly with -Zbuild-std, and nothing has run it. The trick that worked for x86 does not transfer, because this host is x86: running it nested needs an AArch64 host, and emulating one proves something about the emulator. The pillars table marks it typed for that reason.

3. WHPX can be kicked and can boot Multiboot, and has done neither

WhpxBackend::kick_vcpu cancels the run with WHvCancelRunVirtualProcessor, and its Multiboot path now receives a resolved entry point rather than treating one as a load address. Neither has been observed: WHP does not start on this host (HRESULT 0x80370302), so both are compilation results and are marked as such, the same way Type-1 is.

4. Quota usage does not survive a restart

GovernedVmHost counts what it has admitted, in one process, for as long as it exists. A process that comes back up has admitted nothing and will admit a full quota again. Persisting it needs a store and an answer to what happens when the store disagrees with the host's inventory, which is a larger decision than the enforcement was. Recorded here rather than in a doc comment nobody reads, since it is the same class of gap that left the quotas unenforced in the first place.

Environment notes that cost time

  • KVM works here. WSL2, kernel 6.18.33.2, API version 12, 24 vCPUs, 45 GB. The user must be in the kvm group; sudo blocks on a password, and wsl -u root -e usermod -aG kvm $USER does not.
  • Build WSL into its own target directory. CARGO_TARGET_DIR=/var/tmp/hm-target — a WSL build over /mnt/c shares target/ with the Windows host and silently invalidates its artifacts.
  • protoc is not installed in WSL, so hv2-api does not build there and cargo test --workspace fails on the Linux side. Per-crate runs work: hv2-core is 2,167 passing with the one timer failure, hv2-swarm 18.
  • Windows Hypervisor Platform fails on this host with Failed to set processor count: HRESULT 0x80370302, so the Windows backend is unexercised here.
  • Paths through wsl.exe need MSYS_NO_PATHCONV=1, or Git Bash rewrites /var/tmp/... into a Windows path.

What to do next

  1. Give hv1 a guest worth running. It hosts four bytes of real mode. An exit handler that does something with an exit, an IDT, interrupt delivery and a device or two are what stand between that and an operating system, and every one of them can be built and run on the nested path that already works — no hardware required. The three defects that afternoon found are the argument for doing it this way: each was invisible to review and obvious the moment something executed.
  2. Then boot hv1 on hardware, the only item here that cannot be done on this machine. It needs bare metal and a serial console, so it needs somebody to decide to provide them — and it is where the firmware path, the real memory map, AP bring-up and every device stop being hidden by a hypervisor underneath.
  3. Decide where inference runs. The measurement above says a fleet cannot all infer at once, and says nothing about whether the answer is scheduling in-guest inference, or making inference a capability the sandbox invokes and keeping the guest as small as it is. The second keeps the property the sandbox exists for — minimal, and therefore auditable — and the permission graph that would gate such a call already exists and already refuses. The first keeps the isolation boundary around the model. This is a product decision with the numbers now under it.
  4. Then put something real behind whichever it is. Weights, a tokeniser, a forward pass. Nothing on this page has run a model; every figure here is the floor a model would sit on, and the tool call above is a rule standing in for a decision.
  5. Give the guest a heap. It has none, which is why the tool request is assembled in a 128-byte array on the stack and why a payload longer than that is truncated rather than refused. Any real agent protocol — arguments, results, a conversation — needs one, and hv1-multiboot already carries the worked example.
  6. Move the agent guest to 64-bit. It is i686 because stable Rust ships a prebuilt core for that target, which was the right call for a guest that writes to a serial port and the wrong one for a guest that does arithmetic: inference wants AVX2 and more than 4 GB of address space. hv1-multiboot is already the worked example of the 64-bit shape, heap included.
  7. Make the agent payload do something. The guest echoes, which was the right thing to prove and is not a workload. What an agent actually runs inside a unikernel — and whether it needs an allocator, a heap, and therefore rather more than 8 KB of image — is the next real design question, and it is now answerable by experiment rather than by argument.
  8. Keep the suite green. It is, as of today, and both tests that were not turned out to be describing real defects rather than being flaky. That is the usual outcome and the reason not to leave one sitting.

One habit is worth carrying forward, because it has now earned its place six times: measure before claiming, and assert on the effect rather than the verdict. The memset was found by timing, not by reading. The run_single ceiling was found because the fix that should have worked changed nothing. The first regression test written for the VM-id collision passed against the broken code, which is how the second came to check entropy instead of luck. The stop() hang was a diagnosis before it was a fix: wchan = kvm_vcpu_block on an otherwise idle process ruled out every explanation involving scheduling and left only reachability.

Twice more today, and both were the same mistake in different clothes. The Multiboot guest was reported as silent, and running the same program built three ways showed that only the ELF and the address-carrying image were silent — which turned a vague symptom into jns +0x45. And the first timing of the compiled unikernel said 12 ms, then 31 ms for a smaller guest, which is the shape of a number that means nothing: the cost was a cold read of the image over a 9p mount, 9.0 ms against 0.02 ms for everything else provisioning does with it. One run measures whatever else the machine was doing. A median over nine does not.

The strongest case for the habit, though, is svm_run. It sat in the tree looking like a working function — documented, plausible, the sort of thing a review skims and accepts. Its inline assembly had no input operands at all, so it read its two arguments from the wrong registers and handed VMRUN an address that was not a VMCB. Nothing could have found that except running it, and nothing had run it, because running it needed a Multiboot loader that worked and a way to get from 32-bit to 64-bit — which is how a defect stays invisible for as long as the thing above it is unfinished. The lesson is not "review harder". It is that unexecuted code should be labelled unexecuted, which is what the pillars table has been doing all along.
