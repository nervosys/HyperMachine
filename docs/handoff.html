Boot path, enforcement, and the CI that was already broken

A long run of commits took VMs from “configured” to “able to execute a guest,” wired security controls that existed only as types, gave the guest a way to speak back, and repaired a pipeline that had been red since June. What follows is what shipped, what is actually proven, and what remains genuinely unverified.

The one thing to read first

No real distro kernel has booted on any backend.

Every test asserts what a backend was asked to do — which images landed at which guest physical addresses, what architectural state vCPU 0 was left in — not that a guest executed. The KVM and HVF boot paths have never run at all; they are type-checked only.

This host reports HypervisorPresent=True with VMMonitorModeExtensions=False: Hyper-V owns VT-x, so WHPX partition setup fails with 0x80370302. Closing this needs hardware where a hypervisor is actually available.

One clarification, because the newest tests are easy to misread: constructing a VM succeeds on this machine, so the console tests run in full rather than skipping. That is evidence about the device and VM layers and nothing more. VM::new only selects a backend; the partition is created later, in provision(), which those tests never reach. “The tests ran” does not mean WHPX works.

The console, and why attached exists

The most recent work, and the one place where an API shape is load-bearing rather than plumbing.

An empty log means two different things

A VM with no serial device registered and a guest that booted silently both produce an empty console. The log alone cannot separate them, and the cheap version of this API — return a string — would send an operator hunting a boot failure that was really a missing device.

So the seam is Device::console_output() -> Option<Vec<u8>>, defaulting to None. None is “not a console”; Some(vec![]) is “a console that has said nothing yet.” That distinction is carried up unchanged as attached on VmConsole and on the REST response. Nothing registers a serial device automatically, so attached: false is the common case today and needs to be legible.

Two defects the console work uncovered on the way

SerialDevice’s transmit buffer was unbounded and drained only when someone read it, so a guest printing in a loop could exhaust host memory — the same shape as the snapshot-chain OOM below. It is now capped at 1 MiB, oldest bytes dropped first.

output() was also destructive, which made polling lossy: a status check ate the boot log it was reporting, and two watchers were impossible. peek_output() reads without consuming, and every layer above it — DeviceManager, VM, AgentVM, VmHost, the tool, the route — is non-destructive by construction. DeviceManager::console_output also sorts by device name rather than following HashMap order, so concatenating COM1 and COM2 yields the same log on every call.

Defects found, by shape

Nearly every bug this session was one of two kinds: a control declared but never consulted, or a value that reads as a measurement but is not one.

Controls that never fired

Image admission was never on the admission path

ImageRegistry’s own doc claimed admission checks that “the scheduler and VM provisioning path call.” Neither did — check_admission was reachable only from an advisory REST endpoint and from tests. An image could be denied or revoked and still boot.

It is now enforced at VM::provision, keyed on SHA-256 of the bytes about to be loaded, so renaming a kernel cannot change the verdict. It also ran after backend.create_vm at first, meaning a refusal had already cost a partition; resolution and admission now precede the backend entirely.

ScriptEngine held a CapabilitySet and never read it

An engine built with no capabilities handed scripts the same VM view as a fully privileged one. The root cause sat one level up: AgentVMBuilder had no setter for capabilities or sandbox_config, so both were pinned at their defaults and unreachable from any caller. SandboxConfig::max_cpu_time likewise bounded nothing.

execute_script was advertised as running inside the guest

It evaluates a Rhai script on the host against four read-only scalars. There is no in-guest agent. Four separate descriptions claimed otherwise, and the documented example was echo ‘Hello’ — a shell command Rhai cannot parse, which taught agents a mental model the engine does not support.

Values that lied

Multiboot mods_addr pointed at module data

Not at the 16-byte descriptor array. A kernel walking that pointer reads its module’s contents as addresses and silently finds no initrd; module command-line strings were never written at all. One shared prepare_guest_memory now serves every backend, so their guest images cannot drift.

Plan steps executed in HashMap order

topological_sort seeded its queue from a hash map, so independent steps ran in arbitrary order — a plan that happened to work was a coin flip, and rollback would unwind a different sequence than the one that ran. Ties now break toward declaration order, pinned by a 25-iteration test, because a hash-ordered implementation passes a single run by luck.

SnapshotId::generate() returned a bare timestamp

Two snapshots created inside one clock tick received the same ID. Because a parent is referenced by ID, an incremental snapshot could become its own parent, and get_chain then walked parent links forever, allocating until the process died — which is why macOS reported SIGKILL rather than a timeout. IDs are now strictly increasing via an atomic CAS, and get_chain separately refuses to follow a cycle.

Lookups that meant something narrower than they read

A backend resolved “the” partition by recency

WhpxBackend keyed vcpu_map by bare vCPU id and resolved load_boot’s partition with vms.last(). KvmBackend was identical. Two VMs on one backend therefore shared a vCPU 0, and a boot image went into whichever partition was newest. HVF had the same defect in a different shape — Hypervisor.framework allows one VM per process and every field is backend-global, so a second create_vm aliased the first outright.

Nothing was observed to be broken, because VM::new builds a backend per VM and the invariant held by accident. But VM::new_with_backend is public, so the aliasing path was expressible with no warning.

The invariant is now in the type rather than in the reader’s head: vms: Vec<_> became vm: Option<_>, and create_vm refuses a second with an error saying why. Caveat: the four new tests skip on any host without a usable hypervisor, which includes this machine and CI. The wiring is verified; the runtime refusal is not.

CI state

Master had been red since June. Six defects were stacked behind one another — each fix revealed the next, and fail-fast kept the queue from showing them all at once. Run 32192729164 is the first fully green run.

Read the table as of f67dac1, not as of head

Nineteen of nineteen jobs were green at f67dac1, and that is the last run anyone has watched. Several commits have landed since, up to d420538. Each was verified locally — the full workspace suite, cargo test -p hv2-core, doc tests, and clippy under CI’s exact invocation (--workspace --all-targets --exclude hv1-core --exclude hv1-boot -- -D warnings) — but no CI run has been observed for them. Given how many of this session’s defects were things a green local sweep could not see, check the runs before trusting the chips below.

Stable moved to 1.98 and its new lints break the build — on any branch

Every job installs dtolnay/rust-toolchain@stable unpinned. Stable became 1.98.0 on 2026-08-20, bringing manual_slice_fill, large_const_arrays-adjacent chunking lints and result_unit_err. Four sites in this repo fail -D warnings under it, none of them related to any recent commit. They are fixed here, but the exposure is structural: an unpinned stable means a Rust release can turn master red without anyone pushing anything. Worth deciding whether that is the intended trade — the HV1 jobs already pin a nightly date for exactly this reason.

Open, with diagnosis

HV1 ARM64 — the job asked an x86-only crate to build for ARM

It ran cargo check -p hv1-core --features arm64 --target aarch64-unknown-none, which fails with ~75 unresolved references to x86_64, x86 and raw_cpuid across eight files. That is not a defect: hv1-core’s own manifest states it is “the x86_64 Intel-VMX / AMD-SVM Type-1 hypervisor; ARM is the separate hv1-arm crate,” and vm/vcpu/boot are built on VMX/SVM throughout.

Making the step pass would mean implementing ARM support in hv1-core, not fixing a bug, so the step was removed — ARM coverage is the hv1-arm check in the same job, verified clean for aarch64-unknown-none. If hv1-core is meant to have an ARM mode, this step should return alongside that work. That is a reversible judgment call, flagged here rather than buried.

HV1 bare-metal — bootloader’s build script is broken upstream

Two layers deep. The first was real and is fixed: bootloader 0.11.15 shipped target specs with "rustc-abi": "x86-softfloat", which current nightly rejects; 0.11.17 ships "softfloat". Verified by reading both versions’ JSON out of the cargo registry.

Underneath, 0.11.17’s build script shells out to cargo install for its BIOS/UEFI stages, and that nested build cannot compile lock_api 0.4.10 (can’t find crate for `std`). Reproduced locally on a June nightly, with and without -Zbuild-std, and for the host target too — so it is neither our configuration nor nightly drift. The step is continue-on-error so it still runs and stays visible without blocking.

The nightly pin, and what it cost to land

The HV1 jobs now pin nightly-2026-08-17 — the toolchain that produced the first all-green run. Unpinned, they broke four times in a day for reasons unrelated to any commit here: a new required method on core::iter::Step, a renamed rustc-abi value, unused_must_use becoming an error, and a yanked spin.

Note for whoever bumps the date: rust-toolchain.toml pins channel = "stable" for the repo and overrides whatever default the action installs, so those five steps name the toolchain explicitly as cargo +nightly-2026-08-17. The date therefore appears in both the with: blocks and the commands, and both must move together. Bump deliberately and watch these jobs when you do — not warning you about upstream churn is precisely the tradeoff.

It took three attempts. The first invented an action tag that does not exist (the working idiom was twelve lines up, in the MSRV job); the second dropped +nightly without checking what selects the toolchain. Workflow edits have no local test, which is exactly when reading the surrounding file matters most.

Left open deliberately

limits.rs stays unwired — wiring it would duplicate McpConfig::rate_limit, which already works. Operation.rate_limit remains advisory metadata, per your call. execute_script refuses as a plan step rather than fabricating guest output. HVF on Apple Silicon falls through to TCG; a real ARM implementation is a separate project, not a gap in this one. hm-cli’s separate agentic ontology did not get a vm.console tool — it tracks its own VMs, and the tool would have been a stub there.

What to do next

In dependency order. The first item unblocks most of the rest, and it needs hardware rather than code.

  • Boot a real kernel. A Linux host with /dev/kvm accessible, an Intel Mac for HVF, or a Windows host with Hyper-V disabled so WHPX can take VT-x. Gate: a distro kernel prints to serial and halts. Until then treat every boot-path claim as untested — and note the console is now in place to see that output when it happens.
  • Confirm the one-VM-per-backend refusal on real hardware. The guard is written and the tests are wired, but they skip wherever no hypervisor is available — so this rides along with the item above rather than standing on its own.
  • Make execute_script mean what it says. Either a serial-console command protocol on top of the console work (no guest install, limited) or a real in-guest agent over virtio-vsock (richer, needs a guest-side binary and a build story).
  • memory_used_bytes stays null everywhere until virtio-balloon or a guest agent exists. That is correct today; do not let anyone “fix” it with a plausible number.

Environment notes

Four defects reached master despite a green local sweep. All shared one shape: verification ran on Windows, against files this machine happens to have. The last two entries are new, and are about the machine rather than the code.

  • cargo check does not link. The HVF backend used Intel-only Hypervisor.framework VMX symbols and type-checked cleanly on aarch64-apple-darwin for months. Only CI’s linker caught it.
  • Gitignored build artifacts. examples/guest_code/*.img are build.sh outputs excluded by .gitignore. Tests include_bytes!’d them, so a clean checkout failed to compile. Reproduce by moving them aside, not by re-running tests.
  • rustdoc lints are platform- and flag-dependent. Use RUSTDOCFLAGS="-D warnings" cargo doc --target x86_64-unknown-linux-gnu; a Windows run reports zero warnings regardless.
  • Local nightly is gone, along with most other toolchains — casualties of the rollbacks above. Only 1.98.0 and a metadata-less stable survive, so hv1-core and hv1-boot cannot be built here at all until rustup works again.
  • Build resources, and what a full disk actually looks like. target/debug reached 132 GB and took the volume to 100 % (3.7 TB, 31 GB free). The symptoms did not look like a disk problem: mkdir failed EEXIST, temp writes failed EPERM, directory listings returned different contents on consecutive calls, and rustup quietly rolled back every install — leaving stable without a component manifest, so bare cargo, rustc and clippy all stopped working. Check df before believing any of those errors. Deleting target/debug reclaimed 194 GB and restored normal behaviour.
  • rustup is still broken on this host and reinstalling stable fails even with space free — freshly extracted files under ~/.rustup become unreadable immediately, which points at antivirus or a sync client on the profile directory rather than at Rust. The workaround, and how this session’s verification was run, is to invoke the toolchain directly and skip the shim: PATH="$TB:$PATH" RUSTUP_TOOLCHAIN=1.98.0-x86_64-pc-windows-msvc "$TB/cargo.exe" … where $TB is ~/.rustup/toolchains/1.98.0-x86_64-pc-windows-msvc/bin. Note this bypasses rust-toolchain.toml, so the version is whatever you name.
  • Fail-fast hides failures behind failures. Test (ubuntu-latest) was cancelled in every earlier run and only ran to completion once the jobs ahead of it went green — then failed, because a test I wrote assumed /dev/kvm was usable. Expect the queue to keep producing “new” failures as it drains.
  • Three tests asserted wall-clock behaviour a platform is not obliged to provide — a 1 ms health interval, PIT tick counts, and a strictly-increasing span timestamp. All passed locally; all failed elsewhere.
