What Actually Ran

A thousand hardware-isolated agents run at once under a command graph, a unikernel reaches executing code in 2.67 ms, and a sandbox costs 0.157 MiB. Every one of those is measured. What is new is that the path an agent payload would take is now closed end to end: a unikernel written in Rust, compiled by the ordinary toolchain, booted by Multiboot, receiving a swarm message over vsock — and shutting down afterwards, which no VM had ever done.

The one thing to read first

VM::stop() returns now. It never had before.

Before this it did not return slowly — it did not return at all, at twenty seconds, for every guest shape tried. examples/halt_stop_probe is those same three variants, differing only in what the guest does before shutdown, run against both: 

write-then-halt : DID NOT RETURN within 20 s   →   returned in 0.7 ms   console "."
halt-only       : DID NOT RETURN within 20 s   →   returned in 0.8 ms   console ""
spin-forever    : DID NOT RETURN within 20 s   →   returned in 0.7 ms   console ""

stop() clears the running flag, sends each vCPU a Stop message, then awaits the vCPU task handles — all of which depend on the vCPU leaving KVM_RUN, and none of which a thread inside the ioctl can observe. It could not be made to leave, because KvmVcpu::run retried on EINTR unconditionally: 

Err(e) if e.raw_os_error() == Some(libc::EINTR) => continue,

That retry is exactly the mechanism a VMM uses to kick a vCPU out. Without a check before it the vCPU was uninterruptible by construction: a guest that stopped exiting to userspace, by halting or by spinning, owned its thread until the process died.

Diagnosed against a hung process: 0% CPU, all 28 threads sleeping, vcpu-0 at wchan = kvm_vcpu_block, everything else parked on futexes. Nothing starved and nothing raced, which is what said the problem was reachability rather than scheduling.

The fix is three things, because a kick has three moments to miss

Getting a vCPU out of KVM_RUN
PartThe moment it covers
SIGRTMIN, handler installed without SA_RESTART A vCPU already inside the ioctl. With SA_RESTART the kernel restarts the call itself and userspace never learns the signal arrived. A real-time signal rather than SIGUSR1, which belongs to whoever embeds this crate.
kvm_run->immediate_exit A vCPU that has not reached the ioctl yet, at which a signal would be aimed at nothing. KVM checks this on the way in and answers EINTR without entering the guest.
A per-vCPU flag, read by the EINTR arm The retry itself. This is what turns a delivered signal into a returned call instead of a re-entered guest.

The ordering is what makes the race benign: the flag and immediate_exit are both set before the signal is sent, and run() checks the flag after publishing its thread id and before entering the ioctl. A kick landing anywhere in that window is latched and seen at the next entry — the difference between a shutdown that hangs intermittently and one that does not hang.

HypervisorBackend::kick_vcpu is how stop() reaches it, and VmExit::Interrupted is what a kicked vCPU reports. The run loop continues on that exit, which sends it to the top of the loop to read the flag and the control channel — the reason it was kicked. No guest state is touched, so re-entering is correct when the kick was for something else. tests/vcpu_kick.rs asserts on the effect, that stop() completes, and covers the before-entry race separately by requiring a pending kick to end a run without the guest being entered.

This changes how to read the older numbers below. Runs that appeared to finish were killed by their timeout after printing. The measurements were already on stdout and are unaffected. The 1,000-VM figure has since been re-run and now ends by exiting: 59 seconds, all 1,000 guests executed, 0.157 MiB each, every stop() returned.

What shipped

The cold start was never measured, and the first measurement found a 474× defect

Nothing in this repository had ever timed a boot. vm_bench, whose results are published to gh-pages, measures guest-memory allocation and snapshot serialisation — neither is a boot. So no performance claim about HyperMachine could be checked in either direction.

hv2-agent --example cold_start is the instrument. It reports percentiles decomposed into four phases and refuses to print a number it did not measure. Its first run said launch was 998.79 ms and scaled with guest memory — the shape of touching every page.

The cause was one line and one alignment. create_vm allocated guest RAM with alloc_zeroed at 4096-byte alignment, and Rust forwards that to calloc only when alignment ≤ MIN_ALIGN (16 on x86-64). A page-aligned request took the other branch: aligned_alloc then write_bytes(ptr, 0, size) — a full memset of the guest's RAM, zeroing memory the kernel already guarantees is zero. Measured on the host: calloc of 1 GiB is 0.0 ms, memset of 1 GiB is 848 ms. The memset was the cold start.

It decided density as much as latency: a 1 GiB VM cost 1 GiB of host RAM before executing an instruction. Now an anonymous mmap, faulted in lazily.

Concurrency was capped at one VM per core, on the path a sandbox takes

run() chose between two execution paths. run_parallel gives each vCPU a thread; run_single awaited backend.run_vcpu() inline on the shared runtime, and run_vcpu blocks inside KVM_RUN. The condition sent a VM to run_single unless it had multiple vCPUs and parallel_vcpu, or pinned affinity — and a sandbox is a one-vCPU VM with neither.

23 VMs worked; 24 hung at 0% CPU on a 24-core host. After routing every VM through the threaded path: 1,000 concurrent VMs, all 1,000 guests verified as having executed, 156.75 MiB between them.

Worth knowing for next time: the first attempt at this fixed spawn_vcpu_task and changed nothing, because run_single never called it. The fix was applied to the path the measurement was not using, and only the measurement caught that.

A unikernel boots, and having no kernel is the whole argument

BootSource::Raw named unikernels in its documentation and the only example using it loaded examples/guest_code/hello.bin — a path that has never existed in this repository. It has never been runnable.

hv2-core --example unikernel_boot assembles its guest in-process so it cannot rot into a missing asset: 73 bytes of 16-bit real mode that write to COM1 and halt. First output at 2.67 ms median over nine runs. Every out leaves the guest, is decoded here, and lands in a device model, so the console line proves the whole path — which is why the example prints the console rather than a success line.

An orchestration layer that enforces rather than describes

hv2-swarm is a command graph: down is a command to any descendant, up is a report to the immediate parent only, sideways needs an explicit one-way grant, everything else is refused with the rule named. A message may also name a capability, and then the recipient must hold it — and on a command, so must the sender. Authority delegates downward but does not amplify; without that rule every capability in the swarm belongs to anyone with a subordinate who holds it.

Swarm::send is the only way a message moves and consults the graph inside it. The tests assert on delivery, not on verdicts: a rule that returns "denied" while the message still arrives passes a verdict test and fails the swarm. hv2-core is a dev-dependency, not a dependency — the policy layer needs no hypervisor to decide who may talk.

examples/guest_transport carries a message across the host/guest boundary over COM1 and watches the guest echo it, with the refusal verified at the recipient's console rather than at the sender's return value.

A Multiboot guest was not silent; it was executing its own file header

The loader wrote every Multiboot image to 1 MB verbatim and entered it at its first byte. That is correct for a flat binary and wrong for anything a linker emits: an ELF's first byte is \x7fELF, and 7F 45 decodes as jns +0x45, so a compiled kernel jumped 0x45 bytes into its own header and died quietly. Single-stepping the old loader shows it exactly — 0x100000 → 0x100047, then a fault.

That is why every guest that ever ran here was hand-assembled and nothing from a toolchain ever did. The specification gives an image two ways to say where it belongs and neither was read. MultibootProtocol::place_kernel now honours the header's own address fields when flags bit 16 is set, and the ELF32 program headers otherwise — segments at p_paddr, the tail past p_filesz zeroed as .bss — falling back to flat-at-1 MB only for an image that says neither. examples/multiboot_probe runs one guest program built all three ways; against this commit all three speak, against its parent only the flat one does.

A guest a compiler produced, and what it proves that assembly cannot

Every guest until now was hand-assembled bytes. That proves the hypervisor works and proves nothing about whether anyone can write a guest for it, which is the only question that matters for an agent payload. crates/hv2-unikernel is a no_std Rust binary: no scheduler, no init, no allocator, no syscall boundary, because there is nothing on the other side of one.

It prints a greeting, then EAX and EBX. The greeting proves the ELF was loaded by its program headers and entered at e_entry. EAX proves more: the specification says a bootloader leaves 0x2BADB002 there, and nothing but the loader can put it there, so a guest reporting it was booted by the protocol rather than jumped to. It reports magic 0x2BADB002 OK.

Stable Rust, no nightly and no -Z build-std: i686-unknown-linux-musl is the 32-bit x86 target rustup ships a prebuilt core for, and nothing Linux survives — the crate links with rust-lld and no C runtime. First output at 3.6 ms median over nine boots, against 5.3 ms for the hand-assembled guest on the same host: being compiled costs nothing.

A swarm message that reaches an agent, over a socket rather than a wire

The host has had a complete virtio-vsock device for some time — split virtqueues walked out of guest memory, connection state, credit accounting. What it never had was a guest that could talk to it, so every delivery here was a byte written to a serial port: real, one-directional, and not a socket. hv2-unikernel/src/vsock.rs is the missing half — a virtio-mmio bring-up, two split virtqueues, and the packet protocol.

hv2-swarm --example vsock_swarm boots three unikernels, connects to each, and runs the command graph over them. A command from the root reaches a worker and comes back echoed; a message between siblings is refused and does not arrive, checked at the recipient, whose guest echoed nothing and printed nothing; granting the edge makes the same bytes arrive, which is what distinguishes an enforcing transport from a broken one. Round trip 1.2 ms.

The driver polls rather than taking interrupts — no IDT, no handler, a spin on the used ring. That is only tolerable because of the fix at the top of this page: before stop() could kick a vCPU out of KVM_RUN, this driver would have been unstoppable rather than merely busy. Three spinning guests now stop in 0.8 ms.

Quotas that refuse, at the point every VM operation crosses

AgentPolicy carried quotas and rate_limits and neither did anything: allows consults enabled and permissions, so a sixth VM was created under a max_vms of five and nothing ever constructed the QuotaExceeded that exists for the purpose. The machinery to count was never missing — RateLimiter was already in limits.rs. Somewhere to put the count that a caller could not go around was.

GovernedVmHost is a VmHost that wraps another one, and a refused operation never reaches the inner host. Every test counts what arrived at the host underneath rather than reading the governor's answer, because a governor that refuses correctly and delegates anyway is indistinguishable from a working one until the host runs out of memory. The same shape as Swarm::send, for the same reason.

Open, with diagnosis

Four items that stood here have been closed and moved up the page. What is left is one test that measures the wrong thing, one that asserts the wrong thing, two claims that compile and have never run, and the honest edges of what shipped.

1. hv1 has never booted on hardware

The Type-1 hypervisor compiles — EL2, stage-2, vGIC — and that is the whole of the evidence. Nothing on this host can change that: it needs bare metal and a serial console, not a VM inside WSL2. Until then "uniquely supports four models" is three models and a compilation result, and the pillars table above says so.

2. test_timer_frequency fails on Linux

16 or 17 ticks against an expected 19, on a clean tree, with and without any change from any session. A wall-clock-dependent test; the fix is virtual time, not a wider tolerance.

3. test_vm_creation_with_backend fails on any host with KVM

The test asserts the selected backend is Tcg or Whpx, which KVM never satisfies — so it has passed everywhere it has been run and fails the moment a real Linux hypervisor is present. What it means to check is that the VM has a backend at all. Left alone rather than quietly rewritten, because deciding what it should assert is a decision, not a typo.

4. WHPX can be kicked and can boot Multiboot, and has done neither

WhpxBackend::kick_vcpu cancels the run with WHvCancelRunVirtualProcessor, and its Multiboot path now receives a resolved entry point rather than treating one as a load address. Neither has been observed: WHP does not start on this host (HRESULT 0x80370302), so both are compilation results and are marked as such, the same way Type-1 is.

5. The agent guest polls, and a polling guest costs a core

hv2-unikernel's vsock driver spins on the used ring: no IDT, no interrupt handler, no hlt while it waits. That is the simplest thing that can work and it is why vsock_swarm runs three agents rather than a thousand — unikernel_swarm is where the graph is run at scale, with guests that halt. An interrupt handler is the fix, and it is a real piece of work: an IDT, a PIC or APIC path, and a handler that agrees with the device about the interrupt line.

6. Quota usage does not survive a restart

GovernedVmHost counts what it has admitted, in one process, for as long as it exists. A process that comes back up has admitted nothing and will admit a full quota again. Persisting it needs a store and an answer to what happens when the store disagrees with the host's inventory, which is a larger decision than the enforcement was. Recorded here rather than in a doc comment nobody reads, since it is the same class of gap that left the quotas unenforced in the first place.

Environment notes that cost time

  • KVM works here. WSL2, kernel 6.18.33.2, API version 12, 24 vCPUs, 45 GB. The user must be in the kvm group; sudo blocks on a password, and wsl -u root -e usermod -aG kvm $USER does not.
  • Build WSL into its own target directory. CARGO_TARGET_DIR=/var/tmp/hm-target — a WSL build over /mnt/c shares target/ with the Windows host and silently invalidates its artifacts.
  • protoc is not installed in WSL, so hv2-api does not build there and cargo test --workspace fails on the Linux side. Per-crate runs work: hv2-core is 2,167 passing with the one timer failure, hv2-swarm 18.
  • Windows Hypervisor Platform fails on this host with Failed to set processor count: HRESULT 0x80370302, so the Windows backend is unexercised here.
  • Paths through wsl.exe need MSYS_NO_PATHCONV=1, or Git Bash rewrites /var/tmp/... into a Windows path.

What to do next

  1. Boot hv1 on hardware, or stop calling Type-1 a supported model. It is first because it is the only claim on the front page of this project that has never been executed, and because it is the one thing on this list that cannot be done on this machine — it needs bare metal and a serial console, so it needs somebody to decide to provide them.
  2. Give the agent guest an interrupt handler, so a guest waiting for work halts instead of spinning. Until then an agent costs a host core while idle, which is the one number in this page that is worse than a Linux container's.
  3. Make the agent payload do something. The guest echoes, which was the right thing to prove and is not a workload. What an agent actually runs inside a unikernel — and whether it needs an allocator, a heap, and therefore rather more than 8 KB of image — is the next real design question, and it is now answerable by experiment rather than by argument.
  4. Fix the two failing tests, which are cheap and are currently noise that a reader has to learn to ignore. Noise a reader learns to ignore is how a real failure gets ignored too.

One habit is worth carrying forward, because it has now earned its place six times: measure before claiming, and assert on the effect rather than the verdict. The memset was found by timing, not by reading. The run_single ceiling was found because the fix that should have worked changed nothing. The first regression test written for the VM-id collision passed against the broken code, which is how the second came to check entropy instead of luck. The stop() hang was a diagnosis before it was a fix: wchan = kvm_vcpu_block on an otherwise idle process ruled out every explanation involving scheduling and left only reachability.

Twice more today, and both were the same mistake in different clothes. The Multiboot guest was reported as silent, and running the same program built three ways showed that only the ELF and the address-carrying image were silent — which turned a vague symptom into jns +0x45. And the first timing of the compiled unikernel said 12 ms, then 31 ms for a smaller guest, which is the shape of a number that means nothing: the cost was a cold read of the image over a 9p mount, 9.0 ms against 0.02 ms for everything else provisioning does with it. One run measures whatever else the machine was doing. A median over nine does not.
