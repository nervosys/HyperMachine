What Actually Ran

A model runs. That sentence was the largest gap on the last version of this page, which said in its own standfirst that every figure it carried was the floor under something that had never happened. A 1.2-billion-parameter Llama now answers questions put to it from inside hardware-isolated sandboxes, under the same capability graph that governs every other tool — and the sandbox that was not granted it gets nothing, counted at the model. The guest underneath is 64-bit compiled Rust that boots in 3.1 ms, sleeps when idle, and can hold three requests in the air at once. All of it is measured on this machine.

How to read this page

Every claim here is tagged with what stands behind it: ran means something executed and printed the number quoted, typed means it compiles and has never run, none means it was not attempted. The distinction is not pedantry — the most expensive defects in this repository have all sat in code that compiled cleanly, was documented accurately, and had never once been executed.

Measurements were taken on WSL2 with real KVM: kernel 6.18.33.2, 24 vCPUs, 45 GB, AMD with nested virtualisation on. That is a virtualised host, so proportions travel and absolutes are not bare-metal comparable.

The one thing to read first

A model answered, inside the permission graph, and the agent without the capability got nothing.

Three identical sandboxes; two hold tool:infer. Each is given a task, each answers with a tool call, and the host runs a real forward pass over real weights for the two that are allowed. The answers arrive on each guest's own console, inside its own VM. 

model         : 16 layers, width 2048, 32 heads over 8 kv heads, vocab 128256 — 1260 MiB mapped
agents        : 3 sandboxes, identical images — 2 hold tool:infer

alpha         : "What is the capital of France? Answer in one word."   -> "Paris."  178 ms per token
beta          : "What colour is the sky on a clear day? ..."           -> "Blue."   169 ms per token
gamma         : asked, refused — no forward pass was run

alpha  says   : agent done   #0x00000001 "infer: What is the capital of France?..." = "Paris."
gamma  says   : agent denied #0x00000001 "refused" was "infer: What is the capital of Japan?..."

forward passes: 51, for the 2 agents that were allowed — 1 asked and ran none

The last line is the assertion, and it is counted inside the model rather than at the broker that gates it. A gate that refuses and infers anyway is indistinguishable from a working one at the agent, and distinguishable everywhere that matters. It is the same shape as Swarm::send and as every other permission in this repository, for the same reason.

hv2-infer is a GGUF reader, a byte-level BPE tokeniser built from the vocabulary inside the model file, and a Llama forward pass: RMS normalisation, rotary position, grouped-query attention over a per-conversation key/value cache, a gated feed-forward, a tied output head and greedy decoding. No GPU, no BLAS, no network, and about a thousand lines of code. The model is mapped, not read, which is the arrangement this project had already measured a page of figures about before it had anything to put in it.

The convention the file could not tell us

Position is encoded by rotating pairs of components of the query and key vectors, and which components pair up is a convention. The reference implementation pairs i with i + head/2; the GGUF ecosystem pairs 2i with 2i + 1 and permutes the weights at conversion time so that the two agree. Nothing in the file says which was used, and a file converted by one convention and read by the other does not error — it produces fluent-looking nonsense.

So it is decided by running. detect_rope runs a short prefix under both and keeps the one whose next-token distribution is sharper, which works because the wrong convention does not break the model, it blurs it: attention loses its position information and the output flattens. That costs 5.0 seconds of the 5.2 the model takes to "load", and the two numbers are reported separately rather than added — a single figure would have described reading a 1.3 GB file as ten times slower than it is, which is exactly the kind of number this project keeps having to take apart afterwards.

Where inference runs, and why that is a decision

In the host, invoked by the guest as a capability — not inside the sandbox. The other answer was nearly taken and is defensible, so the argument is worth having in the open:

  • A fleet cannot all infer at once. Streaming a model's weights costs about 1.4 cycles per byte warm, so a thousand agents inferring simultaneously would need hundreds of gigabytes per second of aggregate bandwidth, which no node has. Inference has to be scheduled across the fleet, and a scheduler that lives inside a thousand independent guests is not a scheduler.
  • The isolation the other answer appears to buy is already spent. An in-guest forward pass would keep the prompt and the key/value cache inside the sandbox — but the weights are a host-owned read-only mapping either way, and the host is the thing that created the guest's memory. The sandbox boundary protects the host and an agent's peers from the agent; it has never protected the agent from the host, and pretending otherwise here would be the first dishonest claim on this page.
  • The sandbox's security argument is its size. "A guest with no kernel has no kernel attack surface" is the case for the whole design. A tokeniser, a matrix kernel and a sampler are the largest body of code in the system, and putting them inside the thing whose smallness is the claim would retract the claim.
  • The gate already exists, already refuses, and already answers under the refused request's own id. Inference is a tool by every property that matters.

What it costs, stated where the decision is made rather than left implicit: an agent's prompt and its key/value cache live in host memory, so agents are separated from each other's inference by the host's own bookkeeping rather than by hardware. A Session is the unit of that bookkeeping — one per agent, holding that agent's cache and nothing else — and the capability graph decides which agents may ask at all.

What shipped: a queue, a conversation each, and a bound on both

Deciding where inference runs left the harder half open: a node cannot run many passes at once, so somebody has to decide who goes next. The first version served one agent at a time in a loop with a fresh conversation per request, which is a fine proof that the parts connect and is not how a node with a hundred agents on it behaves.

hv2-infer::schedule is a first-in-first-out queue, a fixed number of passes in flight, and one session per agent kept between requests. Two bounds, because they are two resources: batch decides how many conversations share a pass, and context_tokens bounds memory — at 64 KiB of key/value cache per token that is the figure a node is sized from, and it is the one thing an agent cannot share, because it is that agent's conversation. An agent over its bound is refused with the numbers in the refusal and refused before it takes a place in the queue: a request that cannot be served should not make anyone else wait for it. 

scheduler     : 1 worker on 8 of 24 cores, 96 tokens of context per agent (6.0 MiB of cache)

alpha  turn 2: "7"    [waited 10.4 s, ran 4.6 s, context 49 tokens]

beta   turn 2: "7"    [waited  4.6 s, ran 4.3 s, context 49 tokens]
gamma  turn 1: "0"    [waited  4.5 s, ran 5.9 s, context 27 tokens]

gamma is the assertion that matters. Alpha and beta were each told a number and asked for it back in a second turn, and answered from their own earlier turn — which is what a session kept between requests is for. On its own that proves nothing: a model asked "what number did I ask you to remember" might simply favour seven. So gamma holds the same capability, is given only the second question, and does not know. An agent cannot read another agent's context because there is no way to name another agent's session, and this checks that rather than asserting it.

The peak queue depth is reported and the example fails if it never exceeds one. A scheduler that was never asked for two things at once has not been tested, and a demonstration that quietly ran everything serially would otherwise pass.

And a conversation can be let go

context_tokens bounds one agent. Nothing bounded the node, so a node's memory was decided by how many agents had ever asked rather than by how many were talking. cache_bytes bounds it — a gigabyte by default, because a real number is a better default than no policy — and when admitting a request would take the total past it, the least-recently-used conversation that is not in a lane is dropped.

Never the agent being admitted, which would otherwise evict itself and arrive with its own context missing; and never one in a lane, which is why the total can sit above the bound while somebody is being served. A soft bound, said where it is printed rather than left for a reader to notice.

The reclaiming is the easy half. An evicted agent has silently lost its memory, which is the same failure this project chased in gamma: a model answering confidently from a context it does not have. So an answer says whether it continued a conversation that was already there, and an agent that expected to be remembered finds out there rather than by being wrong later. 

cache bound : 1.5 MiB across the whole node
ask 1 : one   -> continued false, node holding 1.0 MiB
ask 2 : two   -> continued false, node holding 2.0 MiB
ask 3 : two   -> continued true,  node holding 1.9 MiB
ask 4 : three -> continued false, node holding 1.0 MiB
ask 5 : one   -> continued false, node holding 2.0 MiB
evicted : 2

The first version of that demonstration was not one: every ask in it reported false, so a flag hard-coded to false would have passed. It now runs five asks by three agents so the flag has to be right in both directions — two asks twice running and must say true, and one is the least recently used when room is needed and must say false when it comes back. The example fails on either, because a signal that cannot say yes cannot be trusted when it says no.

What shipped: 2.6× faster, and the obvious optimisation was not the one

The previous version of this page said to make the model faster or admit what it costs. It is 2.6 times faster end to end — 470 ms per token to 178 — and neither half of that came from where it was expected to.

Using every core was costing a quarter of the rate

A matrix-vector product spreads its rows across rayon's global pool, which is sized to the machine. Over 1.25 GiB of weights, median of five runs of four passes: 

   1 thread   1589.7 ms   0.77 GiB/s
   2           799.3      1.53
   4           479.9      2.55
   8           346.5      3.53   <- the knee
  12           412.0      2.97
  16           426.4      2.87
  24           434.9      2.81   <- what the default was doing

It scaled nearly linearly to a third of this machine's cores and then got worse, and what limited it there was not established at the time. It has been since, and it was not the machine: the section below on the knee has the answer and the numbers it replaced. Everything in this section still holds — it is the reason the thread count matters at all — but the figures here are the ones from before that was understood.

AVX2 is worth 1.8×, but only once threads stop being the bottleneck

The first comparison said wider arithmetic bought nothing. It was taken at 24 threads, where the pass is limited by something else — so the measurement was of the wrong thing, and it looked conclusive. At eight threads, same moment, same process:

So the two changes are not independent, and that is the whole lesson here: widening the arithmetic is invisible until the thread count is fixed, which is exactly why the first measurement of it was wrong. Two optimisations that each look worthless can be worth 2.2× together, and the only way to find that is to vary them together.

The kernel is dispatched at runtime against is_x86_feature_detected, so a portable binary gets it and an older machine still runs — -C target-cpu=native was the alternative and produces something that dies with an illegal instruction elsewhere. It is tested against the scalar version it replaces on four block counts, and a second test checks the tolerance is tight enough that a single dropped block would not pass as agreement. HV2_INFER_SCALAR=1 forces the narrow path, which is how the table above was measured on one machine at one moment.

A gap this opened, and closed

The pool belongs to the scheduler, so anything calling Session::forward directly still got the global one — generate was still at 425 ms per token after the fix that was supposed to have halved it. Both examples now build a pool and Session's documentation says a direct caller has to. A configuration fix applied at one layer is not applied at the layer above it, and the only reason this was caught is that the end-to-end number was re-measured rather than inferred from the component one.

What shipped: the fleet shares a pass, not just the weights

Sharing the weights read-only was the first arithmetic this project ever did about fleets, and it was only half of the saving available. A forward pass reads all 1.25 GiB of those weights whether it produces one token or eight — so a node with eight agents waiting was reading the model eight times to produce eight tokens.

A batched matrix product reads each weight row once and dots it against every lane. Everything that is not a weight — the norms, the rotation, the attention over each conversation's own cache — stays per lane, because none of it is shared and none of it is the expensive part. 

lanes=1   3.59 tokens/s   278.9 ms per token
lanes=2   7.60            131.5
lanes=4  13.40             74.6
lanes=8 17.05            58.6   — 4.7x

Sub-linear past four lanes, because once the weight read is amortised the arithmetic starts to matter — which is the AVX2 finding from the other direction and the same underlying fact about where the time goes.

What makes the speed worth having

A batch that quietly mixed two conversations together would run at exactly the same speed and answer fluently with the wrong lane's answer. Throughput cannot detect that; four different one-word answers can. examples/batched asks the same four questions twice — once each alone, once all four in one batch — and compares: 

lane 0: "What is the capital of France"        alone "Paris."  batched "Paris."
lane 1: "What colour is the sky on a clear day"       "Blue."           "Blue."
lane 2: "What is the capital of Japan"               "Tokyo."          "Tokyo."
lane 3: "How many legs does a spider have"                "8"               "8"

one at a time : 24.5 s      all at once : 8.7 s      2.83x

It names that failure specifically if it sees an answer come back on the wrong lane, because "an answer changed" and "the lanes are crossed" want different fixes.

And the batching is continuous

A request that arrived while a batch was running used to wait for the whole batch — which is why the largest batch was two out of four. The agents are real sandboxes and each has to exchange a frame with its guest before it can ask, so they do not arrive together, and the second pair missed the first pair's batch entirely. Lanes are now filled from the queue at the top of every token step and emptied as they finish: 

                     static batching   continuous
largest batch          2 of 3            3 of 3
time in the queue      6 - 8 s           0.1 s
wall clock            16.2 s            10.9 s

Every lane's state lives in the scheduler rather than on the thread driving it, which is what makes this simpler than it sounds: any waiter can take the next step, and a thread whose own answer is ready stops driving and returns rather than finishing everybody else's work.

The knob was the wrong one, and the measurement said so

The scheduler's bound used to be workers: how many passes to run at once. That is the wrong question. Two concurrent passes read the model twice; a batch of two reads it once, for the same arithmetic and half the memory traffic. So there is one pass at a time and its width is the knob, and the fleet's figures move accordingly: 

scheduler : batches of 4 on 8 of 24 cores
batches   : 3 passes over the weights for 5 answers, largest carried 2
time      : 16.2 s of wall clock, 100% of it someone's share of a pass

Against 23.7 s before batching and 61.3 s before any of this session's performance work, for the same five turns. There is no worker thread: whichever caller finds no batch in flight runs one and wakes everybody in it, which needs no spawning and no way for a thread to outlive the model's borrow.

Two things this exposed. Per-request service time cannot be summed — a batch's duration belongs to every request in it, so adding them up reported 169% of the wall clock as "service"; what a request cost is its batch divided by how many shared it. And two requests from the same agent cannot share a batch, because they would need the same conversation in two lanes of one pass; the second waits for the next batch.

What shipped: the knee was ours, and removing it reached the memory bus

A correction to what this page said two sections ago.

It said a forward pass stopped getting faster at about a third of this machine's cores and then got worse, and that what limited it there had not been established. That was honest and it was also a place to stop looking. The limit was not the machine, and finding that out took one experiment that should have been run when the curve was first drawn.

examples/bandwidth reads the same bytes at the same thread counts with no transformer — just a sum over every byte of every tensor: 

threads  1  18.74 GiB/s     threads 12  18.78
threads  2  18.25             threads 16  18.90
threads  4  20.63             threads 24  19.01
threads  6  18.47

Reading is flat: a single thread already gets 18.7 GiB/s and twenty-four get no more. It does not knee at all. So the degradation was in how the work was handed out — the pass was running at 7 GiB/s against a machine that reads at twenty.

The cause was granularity. The matrix-vector product gave rayon one task per matrix row: a couple of kilobytes read and a couple of thousand multiply-accumulates, and 128,256 of them for the output head alone. Handing out a hundred thousand tasks costs more the more threads are competing to take one, which is the shape of the curve. Sixty-four rows to a task:

The optimum moved from eight threads to four, and four reaches 17.0 GiB/s against the 20.6 that reading alone manages — about 83%. So the single-lane case is close to memory-bound with some headroom left, which is a weaker claim than the one this page made first and is the one the numbers support.

And that number is a correction too

This page said the pass was at the memory bus, against a probe reporting 15.9 GiB/s. Then the pass learned AVX-512 and came out at 17.0 — faster than the ceiling. A probe the thing under test can outrun is not a ceiling, and that is how it was caught.

The probe summed bytes one at a time, which measures a scalar loop rather than a memory system. Reading eight bytes at a time into four independent accumulators: 20.6 GiB/s at four threads, and 18.7 at one. The instrument was the thing being measured, which is the same mistake as timing one boot and calling it a cold start — twice in one page, in two different disguises.

AVX-512, and a prediction that held

The previous version of this page put AVX-512 on the list with a prediction attached: it should do nothing for one lane, which is limited by bytes, and help the batched case, where the arithmetic had become the limit. It does. 

8 lanes, 8 threads   AVX2 28.6 ms/token  ->  AVX-512 24.4   1.17x
1 lane,  4 threads        73.1 ms/pass   ->          71.8   nothing

A Q8_0 block is thirty-two weights, which is exactly two 512-bit registers. What it is deliberately not is a VNNI kernel, though this CPU has avx512_vnni and that is the obvious shape for a quantised product: VNNI wants both operands as integers and the activations here are floats, so using it means quantising the activations too — which changes what the model computes and belongs behind its own measurement of whether the answers survive it.

So the thread default now takes the batch width, because the two answers differ. One lane wants four threads — enough to saturate memory and no more. Eight lanes want eight, because eight times the arithmetic per byte read stops it being purely memory-bound. 

lanes=1, 4 threads   84.0 ms per pass, 14.56 GiB/s, 11.9 tokens/s
lanes=8, 8 threads   27.3 ms per token, 36.7 tokens/s

Against 58.6 ms per token before this change and 470 ms at the start of the work. AVX-512, below, takes it to 24.4 — nineteen times, for a fleet.

One number moved the wrong way and is worth saying so. This helped the unbatched path more than the batched one, so batching's relative advantage shrank from 2.83× to 1.94× while both got substantially faster. A speedup ratio is a ratio, and the denominator moved.

What shipped: an agent that holds more than one thing at once

The protocol has carried a request id since it had a shape, and nothing had ever used two of them. Every example sent one frame and waited for its answer — which is exactly the arrangement the id was added to escape, since a reply that can only be answering the one outstanding thing needs no id to say so.

The guest could not have used two anyway, for two reasons that only showed when something tried. It answered a task under the task's own id, so a task producing two requests would have produced two requests sharing an id. And its frame handler parsed one frame per packet and discarded the rest along with the buffer — which is the defect the framing exists to prevent, still present on the guest's side of it, invisible because nothing had ever sent two.

So the guest keeps what an agent has to keep: a stream buffer it drains frame by frame, a table of what it has asked for, and its own id space separate from the host's. An answer is reported against the request it settles, and an answer to nothing is reported as stray — which under the old scheme could not be detected at all, because whatever arrived was the answer. 

agent task   #0x00000001 "tools alpha beta gamma"
agent call   #0x00000001 "alpha"
agent call   #0x00000002 "beta"
agent call   #0x00000003 "gamma"
agent holds  0x00000003
agent recv   #0x00000001 "a message while you are busy"
agent done   #0x00000003 "gamma" = "G"
agent denied #0x00000002 "refused" was "beta"
agent done   #0x00000001 "alpha" = "A"

Three claims, and each needs the others. The host reads all three tool calls before writing any answer, so a guest that blocked for each reply could not have produced the second frame. A peer's message is admitted by the graph and lands on the console before any of the agent's own answers, so an agent cannot be silenced by a slow tool. And the answers come back last-asked-first with the middle one refused: matched by arrival order instead — which is what every previous version of this guest effectively did — the first of those lines would have read #3 "alpha", and the refusal would have settled the wrong tool entirely. 16.0 ms from the task to the last answer.

What shipped: the guest is 64-bit

It was i686 because stable Rust ships a prebuilt core for i686-unknown-linux-musl and everything Linux could be linked away. That was the right call for a guest whose whole job was writing to a serial port and the wrong one for a guest expected to hold a context: thirty-two bits caps an agent's address space at 4 GiB, which is below one small model's weights plus its own working set.

x86_64-unknown-none is a real freestanding target with a prebuilt core, so this is still stable Rust with no -Z build-std and no nightly. What it costs is the 32-bit half of the boot: boot.rs builds page tables, sets CR4.PAE, arms EFER.LME, turns on paging and far-jumps through a 64-bit code descriptor. The map is 4 GiB rather than the 1 that hv1-multiboot's equivalent needs, because the host puts the shared model region at 3.5 GiB and the virtio window at 3.25, and an address outside the map is not slow, it is a fault.

SSE is put back by hand, and the reason is measured

The target spec disables SSE and builds core soft-float, which is right for a freestanding kernel and wrong for a guest that moved to 64 bits for arithmetic. Over the same 256 MiB sweep — the loop a quantised forward pass is made of — the difference is a factor of three: 

32-bit, SSE      : 13.20 cycles/byte cold, 1.66 warm
64-bit, no SSE   : 15.07 cycles/byte cold, 4.18 warm
64-bit, SSE      : 12.38 cycles/byte cold, 1.38 warm

So the port made that loop faster rather than slower, and the third row is the one that ships. It is not free: nothing enables SSE on a CPU coming out of reset, so four control-register bits have to be set before the first vectorised instruction, and the fault reporter has to be installed before that. Both of those cost the 32-bit guest a debugging session each, and the reason they cost one session rather than three is that the guest reports a vector and an address instead of stopping mid-word.

A cold-start regression that was not one

The first reading after the port said first output had moved from 3.6 ms to 8.0 ms, which would have been a serious loss. It was one sample. This host's own provision and launch phases vary between 1.4 and 12.3 ms run to run, and the guest's own share — first output minus launch — is 1.2 to 2.7 ms in 64 bits against 1.2 to 1.6 in 32. Three runs of each, and the median first output is 3.1 ms.

Worth recording because the instinct was to go looking for the cost in the page tables, and one experiment — mapping 1 GiB instead of 4 — appeared to confirm it before more runs showed the difference was noise. A single measurement of a noisy quantity will confirm whatever you suspected.

One thing did move, and upward. A thousand agents each with a vsock device and an open connection: 

                     32-bit        64-bit
booted and connected  37.3 s        26.1 s
memory per agent      0.221 MiB     0.276 MiB
idle, over 3 s        0.7% of core  0.3% of core
stop, all 1,000       612.7 ms      580.8 ms

A quarter more memory per agent, which is the page tables and the larger boot stack that long mode costs — 0.055 MiB each, and a thousand of them is 55 MiB. Everything else got faster, and the boot figure most of all, though that one is mostly polling granularity rather than a VM booting: rust_unikernel puts an actual boot at 3.1 ms. Round trip is unchanged at 2.2 ms.

Also fixed while in the file: the block that touches an agent's working set had been written out three times in a row, so every agent touched its own pages three times over — invisible in the figure it produces, since residency is idempotent, and three times the boot latency for an agent with a large working set.

What shipped: hv1 is a hypervisor to its guest

It hosted four bytes of real mode: vmmcall, hlt, two exits, stop. That proved VMRUN works and nothing about hosting — a hypervisor that enters a guest twice and stops has run a guest the way a launcher runs a program. What separates the two is what happens on an exit. 

hv1   exit 26  0x7B VMEXIT_IOIO     -> COM1, emulated
hv1   exit 27  0x81 VMEXIT_VMMCALL  -> the guest says it is ready
hv1   exit 28  0x78 VMEXIT_HLT      -> idle — injecting vector 0x20
hv1   exit 29  0x81 VMEXIT_VMMCALL  -> from inside the interrupt handler
hv1   exit 30  0x81 VMEXIT_VMMCALL  -> the handler returned and the guest carried on
hv1   exit 31  0x78 VMEXIT_HLT      -> idle, and nothing left to send it
hv1   > hello from a guest of hv1

Three things, and each is asserted from the guest's side of the boundary. The console line arrived one intercepted out at a time — there is no serial port on the other side of it, there is hv1 decoding the port out of the exit information. The I/O permission map had to stop being all zeros for that: a zero map with INTERCEPT_IOIO set intercepts nothing, so the guest's out would have gone past this hypervisor to whatever is underneath it. And the interrupt is the piece that cannot be faked: the only way exit 29 happens is if the CPU really took vector 0x20 through the guest's own table, and the only way exit 30 happens is if an iret returned from it.

And then the guest left real mode

A guest that stays in real mode is a program the hypervisor happens to be running: its interrupt table is four bytes per vector at address zero, and none of the machinery an operating system needs is present. So it builds its own — a descriptor table, CR0.PE, a far jump into 32-bit code, and then an interrupt table of thirty-three eight-byte gates, each with a selector, a privilege level and a present bit. The thirty-two the processor reserves point at a handler that reports, so a guest that faults now says so with a hypercall instead of triple-faulting into a shutdown exit with no diagnostic. 

exit 27  VMEXIT_VMMCALL  rip 0x0000000000000021  -> real mode, about to leave it
exit 28  VMEXIT_VMMCALL  rip 0x0000000000001060  -> protected mode, GDT and IDT of its own
exit 30  VMEXIT_VMMCALL  rip 0x0000000000001074  -> from inside the interrupt handler
exit 31  VMEXIT_VMMCALL  rip 0x0000000000001069  -> the handler returned and it carried on

The RIP going from 0x21 to 0x1060 is the mode change seen from outside, and nothing had to be asserted for it to be visible: a real-mode RIP is an offset from a segment base of 0x1000, and a protected-mode one under a flat descriptor is the linear address itself.

Once in protected mode the guest has to know where it was loaded, so that address now exists twice — in the hypervisor and in the guest's assembly. A mismatch would not fail to build; it would far-jump somewhere plausible and die. The assembly exports its copy as an absolute symbol and the hypervisor compares them before VMRUN and refuses.

And a device with a ring

Writing bytes to a port is a device in the sense that a doorbell is one: the guest chooses nothing but the data. A ring is the other thing — the guest picks where the buffer is, describes it in a structure of its own, and the hypervisor walks what it finds there. 

0x2000  avail index     requests the guest has published
0x2002  used index      requests the device has completed
0x2004  descriptor 0    address and length of the message going out
0x200C  descriptor 1    address and length of the buffer for a reply

The guest copies its message into a buffer that has nothing to do with the image it was assembled into — so the address in the descriptor is the only way to find it — and rings a doorbell on an intercepted port. hv1 walks the descriptors, reads the message out of guest memory, writes a reply into the buffer the guest named, and marks the request used, all inside the exit the doorbell caused. 

hv1   ring     : the guest sent "a request through a ring" through a descriptor it filled in
hv1   returned : the guest read the reply back out of the buffer it named
hv1   >  hello from a guest of hv1
hv1   >  and a reply through the same ring

Every address in that paragraph came out of a structure the guest wrote. A device model that follows one without checking is a guest that can read and write its hypervisor's memory by putting a number in a field: nested paging stops the guest reaching out on its own and does nothing about the hypervisor being asked to reach out on its behalf. So the guest asks for that too — a descriptor pointing at 10 MiB, against a guest that has two — and the example asserts the refusal alongside the round trip, because a bounds check nobody has crossed is a bounds check nobody has tested.

One number moved because of it: the exit log went from 64 entries to 160. A serial port written a byte at a time costs one exit per character, so two short lines of console are sixty exits on their own — the old bound filled up mid-reply and reported the guest as never having returned. That is what real device models batch to avoid.

And a second processor

A second vCPU is the first thing hv1 has been asked for that is a hypervisor's own problem rather than a guest's. Two VMCBs, because a VMCB is four kilobytes the hardware reads and writes while its guest runs and two processors sharing one would be two processors sharing a register file — and one physical processor underneath both of them, so somebody has to decide which runs. 

exit 074  VMEXIT_HLT      -> yielded — the other processor runs
exit 075  VMEXIT_IOIO     -> COM1, emulated  x43
exit 118  VMEXIT_VMMCALL  -> the second processor ran, and is done

hv1   >  and this line is from the second processor
hv1   half a start: a startup that skipped the reset was refused
hv1   second cpu : INIT and STARTUP through the APIC page, up through real mode,
                   and the first processor saw its work in shared memory
hv1   switches   : 2

It is started the way hardware starts one. The first processor writes to the local APIC's page at 0xFEE00000, which the nested page tables do not map — they map two megabytes and stop — so the write faults out to the hypervisor, and that fault is how hv1 learns the guest wants an APIC. Nothing had to be arranged for it: the page was already absent.

What faults out is an address and a direction, not a value. So hv1 reads the instruction back out of the guest's own memory at CS.base + RIP and decodes it — not out of the VMCB's fetched bytes, because those are a decode assist and a hypervisor that requires one does not work on the parts that lack it. Two forms, because two forms are what this guest executes; a third returns nothing and is reported, since a decoder that invents a length re-executes the instruction forever.

Then the protocol. The high half of the command register says who; the low half says what, and writing it is what sends the message. INIT holds the other processor at reset. STARTUP carries a page number and nothing else — which is the whole shape of the problem, because a processor coming out of reset cannot be handed an address. So the first processor copies a real-mode trampoline to the page it is about to name, and the second one wakes at the top of that page in real mode with nothing set up, loads the shared descriptor table, sets CR0.PE and far-jumps into the 32-bit code both of them run.

That last part is also the evidence. The second processor is started with CR0 at 0x10 — no PE — at a page number, and the next thing seen from it is a serial write from a linear address in 32-bit code. Nothing else could have set that bit.

And it refuses half a protocol. The guest deliberately sends a STARTUP for a processor that was never reset, before doing it properly, and hv1 declines to start one. Real parts do not police this; a hypervisor that is the APIC can, and the refusal is in the log next to the bring-up that works — the same shape as the descriptor pointing outside the guest's memory two sections above. 

exit 070  VMEXIT_NPF  -> the command register's high half — who the next message is for
exit 071  VMEXIT_NPF  -> STARTUP to a processor that was never reset — refused
exit 072  VMEXIT_NPF  -> INIT — the other processor is held at reset
exit 073  VMEXIT_NPF  -> STARTUP — the other processor begins in real mode at the page it names

An APIC, not two registers of one

The command register alone is enough to start a processor and not enough to run one, so the guest now uses four more. It software-enables the APIC through bit 8 of the spurious-interrupt vector register, which is the step a kernel written from the manual forgets and then spends an afternoon on. Its interrupt handler writes end-of-interrupt before returning — injection here does not consult that, so this is the guest doing the right thing rather than being made to. And both processors read the identity register.

That last one is the whole difference between an APIC and a register the hypervisor keeps one copy of. It is a single routine at a single address, called by each processor: 

exit 030  VMEXIT_NPF  rip 0x11E1  -> its own identity — 0, the first processor
exit 084  VMEXIT_NPF  rip 0x11E1  -> its own identity — 1, the second one, from the same instruction

hv1   >  cpu 0
hv1   >  cpu 1

And the first time it ran, both said cpu 0.

The log said the hypervisor had returned 1. The guest printed 0. So the value was being lost between the two, and the reason is in svm_run: RAX travels in the VMCB because VMRUN needs RAX for the VMCB address itself, so the helper copies regs.rax into the save area on the way in and back out on the way out. A value written to vmcb.save.rax between two entries is overwritten before the guest ever sees it.

Two places in this hypervisor were already doing exactly that — the reply to an in from a port with nothing behind it, and the answer to CPUID. Both were wrong and neither had ever been noticed, because this guest executes neither instruction. They are fixed, and it is worth saying plainly what that means: the bug was found by a guest that read a register and printed the answer. Code that is never executed is not code that works, and two of these three sites were the unexecuted kind.

And a timer, which is the difference between being woken and keeping time

Every interrupt above this point was one the hypervisor decided to send. The timer is one the guest asks for: it picks the vector, the period and the mode, writes them to the local vector table, the divide configuration and the initial count, and then halts. Four more registers, and the four that change who is in charge of when. 

exit 137  -> the timer's divide configuration
exit 138  -> the timer's vector table entry — periodic, on the guest's own vector
exit 139  -> the timer's initial count — armed, and counting
exit 140  -> what is left on the timer, which is smaller every time it is asked  x2
exit 143  -> halted, waited for the guest's own timer, and delivered its vector
exit 144  -> end of interrupt, from inside the handler
        ... twice more, then:
exit 149  -> the timer's vector table entry — masked, so it delivers nothing

hv1   timer     : 3 ticks on the vector the guest chose, and its count went
                  down between two reads

Those exit numbers and that count are from the build described here, where there was one timer and one processor using it. Both change in the section after next, when the second processor gets a timer of its own; they are left as they were measured rather than quietly updated, because the paragraph around them is about that state and not this one.

Two things about it are honest rather than convenient. A tick is a timestamp-counter tick, because there is no bus clock to read here — which makes the period wrong by whatever the ratio is and the behaviour right: it counts down on its own, at a rate the guest cannot influence, and expires. And it expires at an exit. The hypervisor notices when the guest leaves and waits for the deadline when the guest halts, so a guest that never exits never gets its tick. Both are written down where the code is rather than smoothed over with a plausible-looking multiplier.

The first period was 200,000 ticks, and that was too short to measure with.

The guest reads the count twice with work in between, because a count that does not move is a register and a count that moves is a timer. It intermittently read the same value twice — zero, both times — and reported that its timer was not counting. The timer was fine. The period was shorter than the exits used to ask about it.

So the hypervisor now reports the gap between what the timer was armed with and what the guest read back first, and it is ≈124,000 ticks for two nested exits — about 60,000 each, call it 15–20 µs. A 200,000-tick period was one and a half exits long. The period is twenty million now, and the number that made it obvious is printed by the example on every run rather than remembered in a commit message.

Nine registers is still not an APIC. There is no interrupt priority, no remote read, no error status, nothing for the second processor's own timer, and a read of anything else returns zero and says so — the same rule the serial port follows, that an emulated device which invents data is worse than one which admits it has none.

And then it had to fire while the guest was running

The timer above expires at an exit, which is fine for a guest that halts and useless for one that schedules. So the guest's wait loop is now pause; jmp rather than hlt. It never leaves. A hypervisor that only ever looks at exits can no longer notice anything, and if the tick still arrives it arrives for a reason.

It does. hv1 arms its own local APIC — the real one, on the processor it is running on — for the guest's deadline, and sets the interrupt intercept so the arrival is a #VMEXIT rather than something the guest sees. The exit happens inside the spin loop, at the same address every time: 

exit 143  VMEXIT_INTR  rip 0x11C6  -> hv1's own timer, while the guest was running
exit 144  VMEXIT_NPF                  -> end of interrupt, from inside the handler
exit 145  VMEXIT_INTR  rip 0x11C6  -> hv1's own timer, while the guest was running
exit 146  VMEXIT_NPF                  -> end of interrupt, from inside the handler
exit 147  VMEXIT_INTR  rip 0x11C6  -> hv1's own timer, while the guest was running

0x11C6 is the pause. One interrupt per tick, so the calibration is right — and there is a calibration, because the APIC counts a bus clock and everything else here counts RDTSC, and nothing tells you the ratio. It is measured once at boot by running the two against each other: 2,000,108 timestamp ticks per 476,267 APIC ticks, about 4.2 to 1, which is a ~1 GHz emulated APIC under a ~4.2 GHz processor.

Three things had to be true first, and two of them were not.

The page had to be mapped. hv1's trampoline identity-mapped one gigabyte, and the local APIC is at 0xFEE00000 — just under four. It maps four now, with that one page marked uncacheable, because a write-back mapping of a device register is a write that may never arrive.

The APIC had to be on, and it was not — because of a bug in hv2. hv2 initialised each vCPU's segments from a zeroed kvm_sregs, and kvm_sregs carries apic_base next to the segments. KVM had already put 0xFEE00900 there — the architectural base, the enable bit, and the bootstrap-processor bit — and writing the struct back turned it off and unmapped the page. hv1 reported apic 0x0 DISABLED, application processor, id 255 on a vCPU that was none of those three things; 255 is what unassigned MMIO reads as. hv2 reads the struct back before modifying it now. That is a defect in the Type-2 hypervisor that would have hit any guest expecting a local APIC, which is every real kernel, and it was found by a kernel that read one register and printed it.

GIF had to be set. #VMEXIT clears the global interrupt flag, so after the first VMRUN a hypervisor that never executes STGI has interrupts masked at a level STI cannot reach — it can arm a timer, the interrupt can arrive, and the handler will never run. Nothing had noticed, because nothing had ever wanted an interrupt.

hv1 also has an interrupt table of its own now, for the first time: 256 sixteen-byte gates, the timer at its vector and every other one pointing at a handler that prints ?! and stops. A kernel with no table triple-faults on its first exception with nothing on the console, and a kernel with holes in its table does the same on the first vector it forgot.

It cost about three times as much per exit, and the guess about why was wrong

The guest measures the gap between arming its timer and reading the count back, which is one round trip through the exit loop. It was ~124,000 timestamp ticks before this mechanism and ~380,000 after. The obvious suspect was hv1 reprogramming its own timer on every entry, so that was guarded — arm only when the deadline moves — and the number did not move.

So the arming was measured directly rather than reasoned about again, and it is roughly half the round trip: 120,000–235,000 ticks for two uncached writes to a device the layer below emulates, each one an exit of hv1's own. The guard is kept, because writing a device register for no reason is still writing a device register for no reason, but it is not what fixed anything and the page should not say it was. Both numbers print on every run; both are noisy while the host is busy, which is why they are quoted as ranges.

A timer each, and a hypervisor that has to choose

One timer for two processors is one processor's timer. Each has its own now — the same register addresses, a different device behind them — and the second processor arms its own at twice the period of the first. Both then spin. Neither halts. Neither yields.

That is the first thing here that hv1 cannot dispatch its way out of. Two runnable processors, one physical processor, and no cooperation from either: something has to take it away. 

hv1   timer     : 4 ticks on the first processor and 3 on the second, each on
                  the vector it chose, both while spinning
hv1   switches  : 14–22 times the hypervisor moved from one processor to the other

Four and three, on periods of 20 and 40 million. One timer shared between them could not produce two different counts, and a hypervisor that ran them one after the other could not produce that ratio. Each waits on its own count rather than on a flag from the other, so what the numbers come out as is decided by the two timers and nothing else — they are the same on every run.

The policy is two rules. A processor whose own tick is overdue runs next, because it is the one with something waiting. Failing that, whoever has held the processor for a slice — two milliseconds — gives it up. hv1 arms its own APIC for whichever comes first, the nearest deadline of any runnable processor or the end of the slice, so the exit that arrives is either a delivery or a preemption.

Three ways this hung, and every one of them was a thing that is true of real hardware

Deadlines alone are not a scheduler. The first version ranked only processors that had armed a timer. A processor that had not armed one was never chosen, and it had not armed one because it had never run: hv1 sat in VMRUN on the second processor forever while the first waited to be scheduled so it could set the flag the second was spinning on. A policy that cannot schedule a task with no deadline is not a policy.

A one-shot is consumed when it fires. hv1 remembered which deadline it had asked its own timer for, and skipped re-arming when the deadline had not changed — which is right while the timer is still counting and wrong the moment it has fired. It went unnoticed while the only deadline was a guest timer's, because delivering a tick always produced a new one. A slice deadline outlives its own expiry.

And the second processor never enabled interrupts. The interrupt table is memory and these two processors share their memory, but IDTR and the interrupt flag are registers, and registers are per processor. The second one came out of reset with the real-mode vector table and interrupts off, and nothing the first one did changed that. It now loads its own IDTR and sets its own flag.

That last one did not present as a hang in the guest. It presented as a hang in the hypervisor: an external-interrupt intercept produces an exit when the interrupt would be delivered, and a guest with IF clear is a guest to which it never would be. hv1 armed its timer, entered that processor, and sat in VMRUN while the deadline went past. Which is worth stating as a limitation rather than a bug fixed: hv1 cannot currently preempt a guest that has disabled interrupts. A real hypervisor reaches for a different intercept for that, and this one has not needed to yet because its guest is cooperative about the one thing it would take to defeat it.

And a number that stopped being true

The section above quotes ~124,000 timestamp ticks rising to ~380,000 for one round trip through the exit loop, measured as the drop in the guest's own timer count between arming it and reading it back. With two processors to schedule, the other one now runs in the middle of that, so the number grew to ~20,000,000 without anything getting slower — it had stopped measuring what its name said.

It is gone rather than re-explained. What is left is the one taken directly, with a timestamp on either side of the writes: the cost of arming hv1's own timer. That number then had to be corrected twice, and both corrections are below.

The arming cost was wrong, and then it was halved

First, the statistic. It was reported as 120,000–235,000 ticks, and that was the first arming of each run. hv1 is itself a guest, so any single measurement can contain the host deciding to run something else in the middle of it — and this one ranged from 121,000 to 766,000 across runs with nothing changing. Taking the minimum over a run instead gives 44,000–62,000, stable to a few per cent. So the honest figure for two uncached device writes was about 53,000, not 140,000, and the earlier one was mostly a measurement of contention.

Then the fix. Arming wrote the timer's vector table entry and its count, every time — but the entry only has to change when the timer goes from stopped to running or back, and writing the count is what arms it. One write instead of two: 

two writes   44,044   51,700   53,196   60,940   62,260
one write    24,068   24,684   24,816   28,468   31,592

Halved, which is what one write instead of two should do and is therefore the answer confirming the explanation rather than a surprise. It also puts a number on the thing underneath: one uncached store to an emulated APIC costs about 25,000 timestamp ticks — six microseconds, for a single instruction.

Worth contrasting with the guard two paragraphs up, which was also "remove a device write" and changed nothing. That one removed armings that were not happening often; this one removed a write that happened on every one. The difference is not cleverness, it is that the second was measured first.

And then the same question was asked once more and answered no. The obvious next move is to arm less often, so each arming was attributed: seventeen or eighteen of about twenty per run are forced by hv1's own one-shot having fired, which cannot be avoided — a one-shot that has gone off has to be set again to go off again. The remaining two to four correspond to a deadline that really moved. So there is nothing left to remove, only a different design: a periodic host timer on a fixed grid would need no re-arming at all, at the cost of serving every deadline late by up to one grid period.

That trade was priced rather than argued about. Twenty armings at ~30,000 ticks is 600,000 ticks a run — about 143 µs, against a run of 255–400 ms. 0.03 to 0.04 per cent. Trading timer precision for that is not worth doing, and the item is closed rather than carried.

And the one instruction that defeats all of it

Everything above rests on an external-interrupt intercept, and that intercept produces an exit when the interrupt would be delivered. To a guest that has cleared its interrupt flag, it never would be. So the first processor now does exactly that, on purpose, and holds the machine for a measured fifty milliseconds while the second one's timer goes on running: 

hv1   masked    : a processor ran 201,450,921 timestamp ticks without leaving,
                  and hv1 could not take it back
hv1   late      : 165,037,493 timestamp ticks, the most a tick was ever late by

Against a window of 200,000,000. hv1 is not slow to react here. It is not running.

The first version of that measurement failed two runs in eight, and only under load

It asserted on the second number — how late the other processor's tick was. That is a true statement about a tick and a bad measure of what it was being used for: how late the late tick is depends on where in the window its deadline happened to fall. Under contention the phase moves, and it came out at 50,172,740 and 55,326,356 on two runs of eight, below a threshold set from the quiet case.

It passed twelve times in a row when run alone, and failed in the sweep, which is the only reason it was caught. So the measurement is now the interval across VMRUN itself: no hypervisor work in it, no dependence on phase, and a floor rather than a middle — contention can only make it larger, never smaller. Ten runs under twenty-four competing spinners give 200,309,776 to 306,915,670, and the window is 200,000,000.

That is the sixth instrument on this page to be wrong, and the second in one section. The pattern by now is specific enough to name: a number that varies with something other than what you are measuring will agree with you until the day it matters.

The example also now distinguishes a guest that never reached its last line from a guest that reached it with something false. It used to report the first as thirteen broken claims rather than as one run that did not finish.

The window is bounded because the point is to measure the gap rather than to hang; an unbounded one would be the same result with nothing to read off it. A guest that meant harm would not bound it.

The way out exists in the architecture, and this platform does not deliver it

An NMI is not maskable. The local vector table's timer entry cannot raise one — fixed delivery is all it supports — but the performance-counter entry can, which is why the Linux NMI watchdog is built on a performance counter rather than a timer. So: set a counter to overflow after so many cycles, point its LVT entry at NMI delivery, intercept NMI, and a guest with IF clear is preemptible again.

It was tried before it was believed, and the probe is in the boot output on every run: 

perf  PerfCtrExtCore, 230964 cycles counted, armed at 0x0000FFFFFFFD1DC5
      and reached 0x00000000014FB87F — past the 48-bit wrap, so it overflowed
      — but no NMI arrived

The counter exists, counts, and wrapped: it was armed 200,000 short of the wrap and ran twenty-one million past it. The overflow happened and nothing was delivered. So the mechanism is not written here, because a preemption path that has never once executed is not a preemption path — it is a claim, and this page has spent a lot of its length on the difference.

What that leaves is a measured statement about the layer underneath rather than about hv1: on this platform, a guest that clears its interrupt flag cannot be preempted at all. Whether the same is true on hardware is exactly the sort of thing that cannot be settled from inside a nested guest.

The rest is what two processors of one guest share, and it is in the controls rather than in the bring-up: the same nested page tables, the same ASID, the same permission maps, all set before either of them ran. Its stack is its own, because two processors on one stack is one processor with a corrupted one.

Scheduling is: run one until it halts, then run the other. hlt is intercepted, so it is a yield rather than a stop — which is why the first processor's wait loop halts instead of spinning. A busy loop would never give the other one a turn.

Four things this cost, and all four were the apparatus

Two finished processors handed the CPU back and forth forever, until a processor was marked finished when it made its last hypercall. The exit counter printed exit 100 as ;0, which is b'0' + 10. Sixty consecutive identical serial-port exits are a wall rather than a log, and printing them overran the console — runs collapse to one line and a count now. And the example waited for the console to contain "done", so it stopped reading partway through the log the moment hv1 gained an exit description ending "and is done", reporting every later claim as absent.

The last of those is the fourth measuring instrument on this page to fail and be briefly read as a result. A sentinel that can appear inside ordinary output is not a sentinel, and it is the same family of mistake as timing one boot, summing bytes to measure a memory bus, and a bound on an exit log that quietly truncated the evidence.

None of the four was in the hypervisor, and neither was anything else. The whole APIC path — an absent page, a hand-written decoder, a real-mode trampoline copied to a page number, and a processor started at reset — ran correctly the first time it was built. That is recorded because a page which only records failures is as misleading as one which only records successes.

And then the sweep that was meant to confirm it did it again. The verification script sums the test result lines with awk. protoc is installed on Windows and not inside WSL, so hv2-api's build script failed, no test binary ran, there were no lines to sum, and the summary printed " passed, failed" — which was briefly read as a pass, and the run before it, which did print a number, printed 3,331 against a full suite of 5,265. It had been surviving on a cached build-script output from days earlier, which is why it looked intermittent rather than broken. The fix is one environment variable; the lesson is the same one this page keeps learning, and it is now five for five: an instrument that returns nothing must not be allowed to look like a result.

Two supporting changes. The guest is assembled by the toolchain in a .code16 section rather than written out as hex — hand-assembly is why every guest in this repository stayed four bytes long. And the nested page tables now translate: guest-physical zero is the base of a 2 MiB region this image owns, and everything above it is absent. They used to identity-map the first gigabyte, which was survivable only because a four-byte guest touches nothing; this one has a stack and an interrupt table at its address zero, and an identity map would have put those in the hypervisor's own memory.

What a fleet costs, now with a model in it

The arithmetic this project published before it had weights survives contact with real ones, which is the useful outcome and was not guaranteed. 

the model     : mapped once, 1260 MiB, and every conversation ran over that one mapping
alpha         : 1.50 MiB of key/value cache held
beta          : 1.69 MiB of key/value cache held
per token     : 65536 bytes of cache

64 KiB per token, not the ~12 KiB this page previously estimated for a hypothetical model — the estimate was for a smaller one and at two bytes per element rather than four. It is the figure a node should be sized from, because it is the one thing an agent cannot share with another agent: it is that agent's conversation. A 2,000-token context is 125 MiB and an 8,000-token one is 500 MiB, so a node holding a hundred agents in conversation is holding the model once and 12 GiB of context.

And the sharing itself, at the scale the page has always claimed, with the 64-bit guest doing the reading: 

region        : 350 MiB filled — resident grew 350.0 MiB
agents        : 1000 booted in 28396.0 ms
read the ROM  : 1000 of 1000 read 0xa7 at 0xe0000000, write refused
per agent     : 0.232 MiB

saved         : 341.2 GiB, 99.83% of what copying would have cost

Read-only is enforced by the hardware and checked from inside each guest rather than asserted by the host: every one of the thousand writes to the region, reads it back, and reports whether the write took. One writable copy shared by a thousand agents is a thousand agents able to rewrite each other's model.

One number here is weaker than the others and is labelled so. The resident growth attributable to a session reads as 0.1 MiB against a 1.5 MiB cache, because a session allocates out of an arena that loading the model already grew. The first version of that measurement was worse: it let each session fall out of scope before the next was taken, so the second agent's cache came out of the first one's freed memory and its growth read as zero — a number about the allocator being presented as a number about what an agent costs. The cache size is counted rather than sampled, and that is the one to use.

What shipped earlier: the machine underneath

Kept because it is what the rest stands on, and because each of these was found the same way. None was found by reading.

  • stop() never returned. Not slowly — not at all, at twenty seconds, for every guest shape tried, because KvmVcpu::run retried on EINTR unconditionally and that retry is exactly the mechanism a VMM uses to kick a vCPU out. The fix is three things, because a kick has three moments to miss: a real-time signal without SA_RESTART, immediate_exit for a vCPU that has not reached the ioctl yet, and a per-vCPU flag read by the EINTR arm. Now 0.7 ms.
  • The cold start was a 474× defect nobody had measured. create_vm allocated guest RAM with alloc_zeroed at page alignment, which Rust forwards to aligned_alloc plus a full memset rather than to calloc. A 1 GiB calloc is 0.0 ms; a 1 GiB memset is 848. It decided density as much as latency.
  • Concurrency was capped at one VM per core, on the path a sandbox takes: run_single awaited a blocking KVM_RUN inline on the shared runtime, and a sandbox is a one-vCPU VM. 23 worked and 24 hung. The first attempt at the fix changed nothing because it fixed a function run_single never called — and only the measurement caught that.
  • Quotas refused nothing. GovernedVmHost wraps another host and a refused operation never reaches the inner one. Every test counts what arrived at the host underneath rather than reading the governor's answer.
  • A Multiboot guest was executing its own file header. The loader wrote every image to 1 MB verbatim and entered it at its first byte; an ELF's first byte is \x7fELF, and 7F 45 decodes as jns +0x45. That is why every guest that ever ran here was hand-assembled and nothing from a toolchain ever did.
  • An idle agent used to cost a core. An IDT, a programmed PIC, one handler and sti; hlt fix it, because a halted vCPU is a thread blocked in KVM_RUN. The PIC is the part that is not a one-liner: KVM's in-kernel 8259 comes up unprogrammed, and an unprogrammed 8259 delivers IRQ 0-7 as vectors 8-15, which are processor exceptions.

Open, with diagnosis

Nothing on this list is a failing test — the suite is green. What is left is one thing this machine cannot do, two things that compile and have never run, and three honest edges of what shipped.

1. hv1 has still never run on hardware

It initialises, hosts a guest, emulates a device for it and delivers it an interrupt, all nested under hv2, and that is as far as this machine goes. The layer under it is KVM, so the firmware path, the real memory map, AP bring-up and every real device are untested, and nesting hides all of them. That needs a machine and a serial console, and nothing here substitutes for it. The guest it hosts is also real mode with one emulated port; a protected or long-mode guest, a second vCPU, and a device with a ring in it can all be built on the nested path that already works.

2. ARM Type-1 has not executed at all

hv1-arm — EL2, stage-2, vGIC — is where hv1-core was a few days ago: it compiles, on nightly with -Zbuild-std, and nothing has run it. The trick that worked for x86 does not transfer, because this host is x86: running it nested needs an AArch64 host, and emulating one proves something about the emulator.

3. WHPX can be kicked and can boot Multiboot, and has done neither

WhpxBackend::kick_vcpu cancels the run with WHvCancelRunVirtualProcessor, and its Multiboot path receives a resolved entry point rather than treating one as a load address. Neither has been observed: WHP does not start on this host (HRESULT 0x80370302), so both are compilation results.

4. There are no priorities and no preemption

The queue is first-in-first-out and a lane runs to the end of its answer. An agent that asks for thirty tokens delays one that wants three, and there is no way to say that one agent's work matters more than another's. The capability graph decides who may ask and says nothing about who goes first.

5. VNNI is written, correct, and unmeasured

Quantising the activations is what unlocks vpdpbusd, and it is implemented — scalar and 512-bit. Two things about it are settled and one is not.

  • It does not change what the model says. Thirty-two tokens of prose came back identical token for token against the float path, and the four one-word answers survive. That was checked before any of the wide code was written, which is the only order in which the check is worth anything.
  • The wide kernel is right. It agrees with the scalar integer path to within rounding, and that path is within 2% of the float one — two tests, because "agrees with the other integer version" and "is a recognisable approximation of the real product" are different claims.
  • Whether it is faster is unknown, and this host could not say. The Windows side of this machine sat at 97% CPU while the comparisons ran, and the same configuration measured 40.8, 54.3 and 58.9 ms per token in three consecutive attempts. The difference between the two paths is smaller than that spread, and the medians put the integer path ahead in one round and behind in another.

So the float path ships and this waits for a quiet machine. A default that changes what the model computes needs a demonstrated benefit, and there is not one yet. HV2_INFER_QUANT_ACT=1 turns it on.

6. About a fifth of the memory rate is still unclaimed

A pass reads at 17.0 GiB/s and reading the same bytes and doing nothing manages 20.6. That gap is small enough to be prefetching, the transpose between the batched product and the lane-major buffers, or the per-lane work that is not a matrix product at all — and nothing here distinguishes them. Said as an open number rather than closed with a guess, which is what the last two versions of this section got wrong.

7. The tokeniser's pre-tokeniser is written out by hand

The reference expresses the cuts as one regular expression with a lookahead; the regex crate has no lookahead, so the six rules are implemented directly. That handles the cases an English prompt is made of and a language whose words are not separated by spaces would be cut differently here than by the reference. Tested for the property that matters most — that the pieces always rejoin into the input, and that it always terminates — but not against the reference tokeniser, because there is none on this machine to compare with.

8. Quota usage does not survive a restart

GovernedVmHost counts what it has admitted, in one process, for as long as it exists. A process that comes back up has admitted nothing and will admit a full quota again. Persisting it needs a store and an answer to what happens when the store disagrees with the host's inventory, which is a larger decision than the enforcement was.

And the sweep that checks all of it was not checking rustfmt

Three violations across three files accumulated before anything checked, and cargo fmt --all -- --check is a CI job, so those commits would have failed there while the local sweep called itself green.

The sweep runs it first now, before the slow parts, and clippy runs with --all-targets rather than against one example — the narrow form misses examples and tests, which is exactly where scripted edits land. Eighth instrument, and the first one that was not measuring anything: it was simply not there.

And widening clippy immediately found that the CI job was failing. crates/hv2-net/src/nat.rs carried #[allow(clippy::chunks_exact_to_as_chunks)] — a lint name that does not exist, so it raises unknown_lints, and CI runs cargo clippy --workspace --all-targets -- -D warnings. The suppression was dead — removing it leaves clippy silent, so it was never suppressing anything — and it was five commits old and nothing local looked at it, because the local sweep had been running clippy against a single example.

And a security check that could not fail, over a vulnerability that is real

cargo audit reports one vulnerability in this tree: RUSTSEC-2023-0071, the Marvin attack — potential RSA key recovery through a timing sidechannel, severity 5.9, in rsa 0.9.10, with no fixed upgrade available. rsa is a direct dependency of hv2-core, and crypto/asymmetric.rs generates private keys and decrypts with them, which is exactly the operation the advisory is about. It applies.

The security workflow runs on every push and every pull request and has been green throughout. Its check was: 

if grep -q "Vulnerability" audit-output.txt; then exit 1; fi

cargo audit writes 1 vulnerability found!, in lower case. The condition could not be true. The step could not fail, and did not, for as long as the advisory has existed. It uses the exit status now, which is what cargo audit sets for precisely this purpose, and the artifact uploads on failure too — the run where it is worth reading.

And then the reason it was never noticed turned out to be that it had already been decided. deny.toml accepts RUSTSEC-2023-0071 explicitly, with ten lines of reasoning beside it: rsa is the only pure-Rust RSA implementation that supports key generation, there is no fixed release upstream, the attack needs precise timing of private-key operations on chosen inputs, and HyperMachine does not expose RSA as an online decryption oracle. Tracked for migration when a constant-time release ships.

So the decision existed and was written down. What was missing is that cargo audit had never been told about it, and the check that would have shown the two tools disagreeing was the broken one. The workflow reads the accepted list out of deny.toml now rather than keeping a second copy — the same fix as the MSRV job two paragraphs up, for the same reason, found the same afternoon. With those applied, cargo audit exits clean, and it will now fail on the next advisory nobody has looked at.

Environment notes that cost time

  • KVM works here. WSL2, kernel 6.18.33.2, API version 12, 24 vCPUs, 45 GB, AMD with nested=1. The user must be in the kvm group; sudo blocks on a password.
  • Build WSL into its own target directory. CARGO_TARGET_DIR=/var/tmp/hm-target — a WSL build over /mnt/c shares target/ with the Windows host and silently invalidates its artifacts.
  • Keep the model off the 9p mount too. Reading a 1.3 GB GGUF from /mnt/c took 44 seconds against 6 from /var/tmp. The same trap as the guest image, which cost 9.0 ms against 0.02 and made the first timing of the compiled unikernel meaningless.
  • protoc is not installed in WSL, so hv2-api does not build there and a workspace-wide cargo test fails on the Linux side — including with --exclude hv2-api, since other crates depend on it. Per-crate runs work, and the Windows host covers the workspace.
  • Check the exit status of the compiler, not of tail. A broken commit reached master because cargo check | tail -3 && git push reports the pipeline's last command. Use ${PIPESTATUS[0]}.
  • In Intel-syntax inline assembly, a bare symbol is an address. mov ax, SOME_CONSTANT assembles as a load from that address, silently. offset is what makes it an immediate, and objdump over the section is what tells you which one you got.
  • Check the Windows host before timing anything in WSL. The VM's 24 vCPUs are the host's 24 logical CPUs, so a busy desktop halves them with no signal inside Linux — /proc/loadavg read 2.7 while the host was at 97%. What a request waits for, and why the queue has no priority

The standing question was whether the queue needs a priority: it is first-in-first-out, a lane runs to the end of its answer, and a request that arrives when every lane is busy waits. Nobody had measured the wait, so nobody could weigh the change. examples/queueing measures it: two lanes, eight agents asking at once from their own threads.

Counted in steps, not seconds

A wait in milliseconds is a fact about the host. This machine has measured 40.8, 54.3 and 58.9 ms per token in three consecutive runs of one configuration because the Windows side was busy, and a queueing result that moves by 40% with somebody else's build is not a result. A step is one pass over the weights, so counting those makes the answer a property of the scheduler. It comes out identical on a loaded machine and an idle one, which is the whole reason to count them. 

waits, in steps: [0, 1, 19, 20, 38, 39, 57, 58]
                 [0, 0, 19, 19, 38, 38, 57, 57]   (a second run)
                 longest 58, against 19 steps that one answer holds a lane

A staircase in treads of two — the lane count — rising by one answer each time. The longest wait is 3.1 answers' worth, and askers/lanes − 1 predicts 3. The only thing that moves between runs is the ±1 inside each tread: whether the two threads of a pair reach the queue in the same step or one apart, which is a race between eight threads and not a property of the scheduler. The treads themselves — 0, 19, 38, 57 — are identical every time. That is first-in-first-out doing exactly what it says: a request waits for a lane, a lane frees when an answer finishes, nobody may jump, and the cost is spread evenly because of it.

Which settles the engineering half and leaves the other half clean. A priority would not make that wait smaller. It would move it from the urgent request onto somebody else. Whether that trade is worth making is a question about which agents are urgent — and that is the capability graph's to answer, since it already decides who may ask at all. What was missing was the size of the thing being traded, and it is three answers.

The first version of the denominator was wrong, and it was the batching that hid it

It divided total steps by answers served: 77 steps, 8 answers, 9 steps each. But with two lanes a step serves two answers, so that is the batching-amortised cost, and dividing a wait by it overstated the wait by the batch width — 6.4 answers' worth instead of 3.1. The figure a waiting request actually waits for is how long an answer holds a lane, which is steps divided by rounds of lanes: 77/4 = 19.

Caught because the corrected number had to agree with askers/lanes − 1 and the first one did not. It is the seventh instrument on this page to be wrong and the first to be caught by a prediction rather than by a failure.

The parser nobody had ever shown a bad file

The item below about the examples being the only verification has a sharper version, and looking for it found something. gguf.rs is 409 lines that read a file header, a tensor table, and slices of a memory mapping. It had no tests at all. Its entire exercise was one person pointing it at one correct 1.2 GB model.

So: seven files with headers that lie. Three of them made it panic. 

a_string_longer_than_the_file      panicked: attempt to add with overflow   gguf.rs:213
a_tensor_past_the_end              panicked: attempt to add with overflow   gguf.rs:398
dimensions_that_overflow           panicked: attempt to multiply with overflow

All three are the same shape: a number is taken from the file and used in arithmetic before anything checks it. Cursor::take computed self.at + n and compared the result against the length — so a string header claiming u64::MAX - 16 bytes made the sum wrap, the bounds test pass, and the slice that followed do whatever it liked. Gguf::bytes added an offset from the file to the start of the data section. TensorInfo::elements multiplied the dimensions straight through.

They are checked now, and the two saturating cases saturate deliberately: a corrupt tensor ends up claiming more bytes than any file holds, so it is refused by the ordinary bounds check with Truncated("tensor data") rather than by aborting the process. A fourth — Vec::with_capacity(rank) on a u32 read from the file, which is a 34 GB request before a single dimension has been read — did not panic when tested, so it is capped rather than reported as a bug that was caught.

The same question asked one layer up found one more. Model::load reads the shape out of the metadata and derives head_dim as width / heads — so a file declaring llama.attention.head_count = 0 divides by zero while loading. There was no validation of the shape at all: every field went from the file straight into arithmetic.

Shape::check now refuses the ones the forward pass cannot work in, and the checks are the relations it assumes rather than a taste test: it slices width into heads of head_dim and those into kv_heads groups, so a width the heads do not divide is a model that would be mis-sliced silently, which is worse than one that is refused. It is a plain function over a struct, so its five tests need no file at all — and one of them asserts that the shape of the model this crate was actually written against still passes, which is the test that would catch a validator that is merely strict.

And one more, in the other direction: not a missing check but a test that was passing without running anything. tensor.rs has good differential tests — every hand-written kernel has to agree with the scalar one, which is the only property a SIMD kernel can be wrong about while still producing a number — but they went through the dispatcher, and the dispatcher picks exactly one. On a machine with AVX-512 it picks wider, so wide, the AVX2 kernel, was never executed by the suite here at all. The untested one is the one that runs on somebody else's processor.

Each kernel is now called directly, under the same feature check the dispatcher uses, and the test prints which it reached: 

kernels exercised beyond the scalar one: ["avx2", "avx512", "avx512vnni"]

The VNNI case was worse than untested. the_wide_integer_product_agrees_with_the_narrow_one compares dot_q8_0_quant against dot_q8_0_quantised, and on a processor without VNNI the second is the first — so the assertion is that a number equals itself, and it passes for free on exactly the machines where the kernel it is named after does not exist. It is left as it is, with that written above it, and the direct call is what covers the kernel everywhere.

Asking the question a third way — which tests never run at all? — found seven. tests/kvm_backend.rs marks every one of its tests #[ignore] // Requires /dev/kvm access, and every one of those tests already checks for KVM and returns with a printed reason when it is absent. The attribute was suppressing tests whose own bodies did the skipping. On this machine, which has /dev/kvm, they pass in 0.14 seconds and had never been run by the suite.

The file beside it had already settled the question in a comment: "Without it these skip rather than fail, so they are not #[ignore]d: on a machine that can run them, the ordinary suite does." One file followed that rule and its neighbour did not. It does now, and those seven run.

The count of what is still ignored was itself wrong, twice over

The sweep was extended to report ignored tests alongside passed and failed, and it said zero. That was very nearly published. It is an awk field index — $8 of a line split on spaces and semicolons — and it lands on the wrong field. Counting the words instead of the positions gives twelve.

Which is the ninth instrument on this page to be wrong, and the second in the same afternoon to be an index into awk's idea of a line. The one that summed passed and failed was right by luck.

What the twelve actually are is worth knowing, because they are two different things. One is a real #[ignore], on a test that wants Windows hardware virtualisation — the kind the attribute is for. The other eleven are doc-tests: code samples written in ```ignore fences, which rustdoc neither compiles nor runs. Three in hv2-agent, six in hv2-core, one each in hv2-api and hv2-runtime. A sample in an ignore fence cannot fail, so it cannot tell you it has gone stale — no_run compiles without executing and text says plainly that it is not code, and either would be a more honest thing for a sample to be. That has not been changed here: it is twenty-three fences across eight files — not twenty, which was an earlier count of this same page's that missed the ones written ```rust,ignore rather than ```ignore.

Four of them were then measured rather than left to a decision, and all four were already broken. Sixteen of the twenty are in whpx.rs, a Windows-only backend that does not compile here at all, so those are fenced for a structural reason. The other four were changed to no_run to see what would happen, and every one failed: LinuxBootProtocol::boot and MultibootProtocol::boot are methods that no longer exist, LinuxBootParams had gained a memory_size field the sample did not set, two samples imported the Windows backend for no reason beyond having something to hand a handler to, one used ? with nothing to return it to, and one had the wrong error type entirely.

That is the module-level documentation of how to boot a guest, and a reader following it would have written code that does not compile. All four are rewritten against the API as it is and are now checked on every run.

Then the same to the seven fences the other crates carry, and one of them was the same story again: hv2-agent's orchestration example awaits three methods that are synchronous, passes two arguments to a method that takes three and another that takes four, and calls get_vm_status, which does not exist. It is rewritten and now runs. Two more were the same shape and are fixed the same way: hv2-runtime's workflow example builds steps out of closures, and WorkflowBuilder::step takes a StepSpec — a name, a command and what it waits for, which is data rather than a future precisely because the runtime decides where and when it runs. hv2-core's FIPS example was not stale at all: it simply never bound the plaintext and aad it encrypts, so it had never been anything a reader could copy.

One more compiled as it stood and was fenced for no reason. The last two were hv2-agent's, and the same shape again: a sample that used AgentRole without importing it, and one that awaited two synchronous methods and called call_tool on the session rather than on the server that holds the tools.

And then the sixteen that could not be checked here, were. They are fenced because whpx.rs is Windows-only and this work happens in WSL — but the machine underneath WSL is Windows, with its own toolchain, and nobody had thought to use it. cargo test --doc -p hv2-core run natively compiles that module for the first time in this session, and all sixteen failed.

One cause, sixteen times: every example opened with backend.create_vm(n, size).await? and then called vm.create_vcpu(0). create_vm does exist — as a trait method that returns a HypervisorVm, which has no create_vcpu. The concrete WhpxVm::new(n, size) is what the rest of each example needs, and it is not async. The remainder were imports the samples never made, and one crate::exit::VmExit — a path that means the doc-test's own crate rather than this one, so it can only ever have worked from inside.

And the count of which ones compiled was wrong, because it was inferred rather than measured

The first pass said four of the seven compiled. It did not: only one does. cargo test --doc was run across four crates at once, it failed in hv2-agent and stopped, and the crates it never reached were read as having passed. They had not been tried.

Which is the same error as the aborted sweep two sections up, made by the same hand within the hour, and it is worth being exact about the shape of it: a run that stops early does not report failures for the work it did not do. None of this is reachable by an attacker in any sense that matters today: the file is a model a person names on the command line. It is worth having anyway, and worth stating why. A parser that aborts on a truncated file tells you nothing about which file or which field; every one of these now returns an error naming what ran out. And WHPX could almost run here

The obvious next question is whether the Windows backend can be executed on this machine rather than merely compiled — the Windows counterpart of what hv1_under_hv2 does on Linux. The answer is one feature flag away, and it was measured rather than guessed: 

HypervisorPlatform                Disabled
Microsoft-Hyper-V-Hypervisor      Enabled
Microsoft-Hyper-V-All             Enabled

Hyper-V is on — it is what runs WSL2. Windows Hypervisor Platform is the separate optional feature that lets a non-Microsoft hypervisor use it, and it is off, so WhpxBackend::new() cannot succeed here. That makes the #[ignore] on the WHPX integration test correct on this machine, which is now a measured statement rather than an assumption.

Turning it on is Enable-WindowsOptionalFeature -Online -FeatureName HypervisorPlatform, an administrator and a reboot — a change to somebody's machine rather than to this repository, so it has not been made. But it is the cheapest untaken step on this page by a wide margin: the Type-2 hypervisor has a second backend that has never run, and the hardware to run it is already here.

  • Enable HypervisorPlatform and run the WHPX backend. One optional Windows feature, an administrator and a reboot, on this machine.   • Re-measure VNNI on a quiet machine. The kernel is written and correct and the answers survive it; what nobody knows is whether it is faster, because the host was at 97% CPU on its other side while the question was being asked. It is one environment variable and two commands.
  • Find out whether the NMI path works on hardware. It is the only way to preempt a guest that has cleared its interrupt flag, and on this platform the counter overflows and delivers nothing — which is a fact about KVM's emulated performance counters and says nothing about a real one. It needs the same bare metal the item below needs, and it would be the first thing worth trying once there is any.
  • Then boot hv1 on hardware, the only item here that cannot be done on this machine.   • Give the capability graph a notion of urgency, or decide it has none. The habit that found all of it

One rule keeps earning its place: measure before claiming, and assert on the effect rather than the verdict. The memset was found by timing, not by reading. The run_single ceiling was found because the fix that should have worked changed nothing. The stop() hang was a diagnosis before it was a fix. And the refused message that appeared to arrive was caught because the check read the recipient's console rather than the sender's return value.

Three more this time, and they are the same rule from three directions. The guest's frame handler had read one frame per packet since framing was introduced, and nothing had ever sent two — a defect that existed only in the space between what the code claimed and what had been asked of it. The transmit buffer was not a defect, and that had to be checked rather than asserted: the shared buffer was deliberately tried against the three-in-flight example and passed, because this host's device drains the queue inside the notification that announces it, so the comment says a property of the device rather than claiming a bug that was not seen. And a cold-start regression of 8.0 ms against 3.6 turned out to be one sample of a quantity whose noise is larger than the difference — an experiment aimed at the page tables had already appeared to confirm it.

Three more, and they are about measurement rather than about code. An optimisation measured in the wrong configuration looks worthless. AVX2 was tried at 24 threads, where the pass is limited by something else, and bought nothing; at eight threads it is worth 1.8×. Two changes that each look useless can be worth 2.2× together, and nothing but varying them together finds that. A fix applied at one layer is not applied at the layer above it. The thread pool belongs to the scheduler, so generate was still slow after the fix that was supposed to have halved it — caught only because the end-to-end number was re-measured instead of inferred from the component one. And a positive result needs a negative control. Two agents recalling a number they were told proves nothing on its own; a third agent, same capability, never told, answering something else is what makes it evidence.

And one more, which is the most expensive kind: the ceiling you assume is the one you never measure. This page carried "what limits it past there has not been established" as an honest admission, and an honest admission is still a place to stop looking. One experiment — read the same bytes with no transformer in the way — showed the machine reading at twice what the pass was managing and not degrading at all, which said the limit was ours. It was: a hundred thousand rayon tasks where six hundred would do. The pass is now at the memory bus, and it took less work to find that out than it took to write the paragraph explaining why it was unknown.

The strongest case is still svm_run, and it now has a companion. svm_run's inline assembly had no input operands at all, so it read its two arguments from the wrong registers and handed VMRUN an address that was not a VMCB; nothing could have found that except running it, and nothing had run it. This session's mov ax, HANDLER_OFFSET is the same shape in miniature: correct-looking, silently assembled as something else, and visible only in a disassembly of what was actually produced. The lesson is not "review harder". It is that unexecuted code should be labelled unexecuted, which is what the pillars table has been doing all along.
