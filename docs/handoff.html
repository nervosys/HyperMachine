What Actually Ran

A model runs. That sentence was the largest gap on the last version of this page, which said in its own standfirst that every figure it carried was the floor under something that had never happened. A 1.2-billion-parameter Llama now answers questions put to it from inside hardware-isolated sandboxes, under the same capability graph that governs every other tool — and the sandbox that was not granted it gets nothing, counted at the model. The guest underneath is 64-bit compiled Rust that boots in 3.1 ms, sleeps when idle, and can hold three requests in the air at once. All of it is measured on this machine.

How to read this page

Every claim here is tagged with what stands behind it: ran means something executed and printed the number quoted, typed means it compiles and has never run, none means it was not attempted. The distinction is not pedantry — the most expensive defects in this repository have all sat in code that compiled cleanly, was documented accurately, and had never once been executed.

Measurements were taken on WSL2 with real KVM: kernel 6.18.33.2, 24 vCPUs, 45 GB, AMD with nested virtualisation on. That is a virtualised host, so proportions travel and absolutes are not bare-metal comparable.

The one thing to read first

A model answered, inside the permission graph, and the agent without the capability got nothing.

Three identical sandboxes; two hold tool:infer. Each is given a task, each answers with a tool call, and the host runs a real forward pass over real weights for the two that are allowed. The answers arrive on each guest's own console, inside its own VM. 

model         : 16 layers, width 2048, 32 heads over 8 kv heads, vocab 128256 — 1260 MiB mapped
agents        : 3 sandboxes, identical images — 2 hold tool:infer

alpha         : "What is the capital of France? Answer in one word."   -> "Paris."  178 ms per token
beta          : "What colour is the sky on a clear day? ..."           -> "Blue."   169 ms per token
gamma         : asked, refused — no forward pass was run

alpha  says   : agent done   #0x00000001 "infer: What is the capital of France?..." = "Paris."
gamma  says   : agent denied #0x00000001 "refused" was "infer: What is the capital of Japan?..."

forward passes: 51, for the 2 agents that were allowed — 1 asked and ran none

The last line is the assertion, and it is counted inside the model rather than at the broker that gates it. A gate that refuses and infers anyway is indistinguishable from a working one at the agent, and distinguishable everywhere that matters. It is the same shape as Swarm::send and as every other permission in this repository, for the same reason.

hv2-infer is a GGUF reader, a byte-level BPE tokeniser built from the vocabulary inside the model file, and a Llama forward pass: RMS normalisation, rotary position, grouped-query attention over a per-conversation key/value cache, a gated feed-forward, a tied output head and greedy decoding. No GPU, no BLAS, no network, and about a thousand lines of code. The model is mapped, not read, which is the arrangement this project had already measured a page of figures about before it had anything to put in it.

The convention the file could not tell us

Position is encoded by rotating pairs of components of the query and key vectors, and which components pair up is a convention. The reference implementation pairs i with i + head/2; the GGUF ecosystem pairs 2i with 2i + 1 and permutes the weights at conversion time so that the two agree. Nothing in the file says which was used, and a file converted by one convention and read by the other does not error — it produces fluent-looking nonsense.

So it is decided by running. detect_rope runs a short prefix under both and keeps the one whose next-token distribution is sharper, which works because the wrong convention does not break the model, it blurs it: attention loses its position information and the output flattens. That costs 5.0 seconds of the 5.2 the model takes to "load", and the two numbers are reported separately rather than added — a single figure would have described reading a 1.3 GB file as ten times slower than it is, which is exactly the kind of number this project keeps having to take apart afterwards.

Where inference runs, and why that is a decision

In the host, invoked by the guest as a capability — not inside the sandbox. The other answer was nearly taken and is defensible, so the argument is worth having in the open:

  • A fleet cannot all infer at once. Streaming a model's weights costs about 1.4 cycles per byte warm, so a thousand agents inferring simultaneously would need hundreds of gigabytes per second of aggregate bandwidth, which no node has. Inference has to be scheduled across the fleet, and a scheduler that lives inside a thousand independent guests is not a scheduler.
  • The isolation the other answer appears to buy is already spent. An in-guest forward pass would keep the prompt and the key/value cache inside the sandbox — but the weights are a host-owned read-only mapping either way, and the host is the thing that created the guest's memory. The sandbox boundary protects the host and an agent's peers from the agent; it has never protected the agent from the host, and pretending otherwise here would be the first dishonest claim on this page.
  • The sandbox's security argument is its size. "A guest with no kernel has no kernel attack surface" is the case for the whole design. A tokeniser, a matrix kernel and a sampler are the largest body of code in the system, and putting them inside the thing whose smallness is the claim would retract the claim.
  • The gate already exists, already refuses, and already answers under the refused request's own id. Inference is a tool by every property that matters.

What it costs, stated where the decision is made rather than left implicit: an agent's prompt and its key/value cache live in host memory, so agents are separated from each other's inference by the host's own bookkeeping rather than by hardware. A Session is the unit of that bookkeeping — one per agent, holding that agent's cache and nothing else — and the capability graph decides which agents may ask at all.

What shipped: a queue, a conversation each, and a bound on both

Deciding where inference runs left the harder half open: a node cannot run many passes at once, so somebody has to decide who goes next. The first version served one agent at a time in a loop with a fresh conversation per request, which is a fine proof that the parts connect and is not how a node with a hundred agents on it behaves.

hv2-infer::schedule is a first-in-first-out queue, a fixed number of passes in flight, and one session per agent kept between requests. Two bounds, because they are two resources: batch decides how many conversations share a pass, and context_tokens bounds memory — at 64 KiB of key/value cache per token that is the figure a node is sized from, and it is the one thing an agent cannot share, because it is that agent's conversation. An agent over its bound is refused with the numbers in the refusal and refused before it takes a place in the queue: a request that cannot be served should not make anyone else wait for it. 

scheduler     : 1 worker on 8 of 24 cores, 96 tokens of context per agent (6.0 MiB of cache)

alpha  turn 1: "OK"   [waited  0.0 s, ran 4.5 s, context 23 tokens]
alpha  turn 2: "7"    [waited 10.4 s, ran 4.6 s, context 49 tokens]
beta   turn 1: "OK"   [waited 10.4 s, ran 4.5 s, context 23 tokens]
beta   turn 2: "7"    [waited  4.6 s, ran 4.3 s, context 49 tokens]
gamma  turn 1: "0"    [waited  4.5 s, ran 5.9 s, context 27 tokens]
delta  turn 1: refused: no capability, never queued

queue         : 5 admitted, 5 served, peak 2 waiting at once
time          : 23.7 s of wall clock against 23.7 s of forward passes
bound         : alpha asked again and was refused — holding 49 tokens,
                this turn needs 48 more, and the cap is 96

gamma is the assertion that matters. Alpha and beta were each told a number and asked for it back in a second turn, and answered from their own earlier turn — which is what a session kept between requests is for. On its own that proves nothing: a model asked "what number did I ask you to remember" might simply favour seven. So gamma holds the same capability, is given only the second question, and does not know. An agent cannot read another agent's context because there is no way to name another agent's session, and this checks that rather than asserting it.

The peak queue depth is reported and the example fails if it never exceeds one. A scheduler that was never asked for two things at once has not been tested, and a demonstration that quietly ran everything serially would otherwise pass.

What shipped: 2.6× faster, and the obvious optimisation was not the one

The previous version of this page said to make the model faster or admit what it costs. It is 2.6 times faster end to end — 470 ms per token to 178 — and neither half of that came from where it was expected to.

Using every core was costing a quarter of the rate

A matrix-vector product spreads its rows across rayon's global pool, which is sized to the machine. Over 1.25 GiB of weights, median of five runs of four passes: 

   1 thread   1589.7 ms   0.77 GiB/s
   2           799.3      1.53
   4           479.9      2.55
   8           346.5      3.53   <- the knee
  12           412.0      2.97
  16           426.4      2.87
  24           434.9      2.81   <- what the default was doing

It scales nearly linearly to a third of this machine's cores and then gets worse. What limits it past there has not been established, and is deliberately not asserted anywhere in the code — the finding is that all of them is a bad number, not that eight is a good one. The scheduler builds its own pool at a third of available parallelism, and examples/throughput takes a thread count so the knee can be found again on a different machine rather than inherited from this one.

AVX2 is worth 1.8×, but only once threads stop being the bottleneck

The first comparison said wider arithmetic bought nothing. It was taken at 24 threads, where the pass is limited by something else — so the measurement was of the wrong thing, and it looked conclusive. At eight threads, same moment, same process:

One forward pass, median of five runs of four
24 threads8 threads
scalar388.9 ms316.6 ms
AVX2 + FMA401.9 ms176.9 ms

So the two changes are not independent, and that is the whole lesson here: widening the arithmetic is invisible until the thread count is fixed, which is exactly why the first measurement of it was wrong. Two optimisations that each look worthless can be worth 2.2× together, and the only way to find that is to vary them together.

The kernel is dispatched at runtime against is_x86_feature_detected, so a portable binary gets it and an older machine still runs — -C target-cpu=native was the alternative and produces something that dies with an illegal instruction elsewhere. It is tested against the scalar version it replaces on four block counts, and a second test checks the tolerance is tight enough that a single dropped block would not pass as agreement. HV2_INFER_SCALAR=1 forces the narrow path, which is how the table above was measured on one machine at one moment.

A gap this opened, and closed

The pool belongs to the scheduler, so anything calling Session::forward directly still got the global one — generate was still at 425 ms per token after the fix that was supposed to have halved it. Both examples now build a pool and Session's documentation says a direct caller has to. A configuration fix applied at one layer is not applied at the layer above it, and the only reason this was caught is that the end-to-end number was re-measured rather than inferred from the component one.

What shipped: the fleet shares a pass, not just the weights

Sharing the weights read-only was the first arithmetic this project ever did about fleets, and it was only half of the saving available. A forward pass reads all 1.25 GiB of those weights whether it produces one token or eight — so a node with eight agents waiting was reading the model eight times to produce eight tokens.

A batched matrix product reads each weight row once and dots it against every lane. Everything that is not a weight — the norms, the rotation, the attention over each conversation's own cache — stays per lane, because none of it is shared and none of it is the expensive part. 

lanes=1   3.59 tokens/s   278.9 ms per token
lanes=2   7.60            131.5
lanes=4  13.40             74.6
lanes=8 17.05            58.6   — 4.7x

Sub-linear past four lanes, because once the weight read is amortised the arithmetic starts to matter — which is the AVX2 finding from the other direction and the same underlying fact about where the time goes.

What makes the speed worth having

A batch that quietly mixed two conversations together would run at exactly the same speed and answer fluently with the wrong lane's answer. Throughput cannot detect that; four different one-word answers can. examples/batched asks the same four questions twice — once each alone, once all four in one batch — and compares: 

lane 0: "What is the capital of France"        alone "Paris."  batched "Paris."
lane 1: "What colour is the sky on a clear day"       "Blue."           "Blue."
lane 2: "What is the capital of Japan"               "Tokyo."          "Tokyo."
lane 3: "How many legs does a spider have"                "8"               "8"

one at a time : 24.5 s      all at once : 8.7 s      2.83x

It names that failure specifically if it sees an answer come back on the wrong lane, because "an answer changed" and "the lanes are crossed" want different fixes.

The knob was the wrong one, and the measurement said so

The scheduler's bound used to be workers: how many passes to run at once. That is the wrong question. Two concurrent passes read the model twice; a batch of two reads it once, for the same arithmetic and half the memory traffic. So there is one pass at a time and its width is the knob, and the fleet's figures move accordingly: 

scheduler : batches of 4 on 8 of 24 cores
batches   : 3 passes over the weights for 5 answers, largest carried 2
time      : 16.2 s of wall clock, 100% of it someone's share of a pass

Against 23.7 s before batching and 61.3 s before any of this session's performance work, for the same five turns. There is no worker thread: whichever caller finds no batch in flight runs one and wakes everybody in it, which needs no spawning and no way for a thread to outlive the model's borrow.

Two things this exposed. Per-request service time cannot be summed — a batch's duration belongs to every request in it, so adding them up reported 169% of the wall clock as "service"; what a request cost is its batch divided by how many shared it. And two requests from the same agent cannot share a batch, because they would need the same conversation in two lanes of one pass; the second waits for the next batch.

What shipped: an agent that holds more than one thing at once

The protocol has carried a request id since it had a shape, and nothing had ever used two of them. Every example sent one frame and waited for its answer — which is exactly the arrangement the id was added to escape, since a reply that can only be answering the one outstanding thing needs no id to say so.

The guest could not have used two anyway, for two reasons that only showed when something tried. It answered a task under the task's own id, so a task producing two requests would have produced two requests sharing an id. And its frame handler parsed one frame per packet and discarded the rest along with the buffer — which is the defect the framing exists to prevent, still present on the guest's side of it, invisible because nothing had ever sent two.

So the guest keeps what an agent has to keep: a stream buffer it drains frame by frame, a table of what it has asked for, and its own id space separate from the host's. An answer is reported against the request it settles, and an answer to nothing is reported as stray — which under the old scheme could not be detected at all, because whatever arrived was the answer. 

agent task   #0x00000001 "tools alpha beta gamma"
agent call   #0x00000001 "alpha"
agent call   #0x00000002 "beta"
agent call   #0x00000003 "gamma"
agent holds  0x00000003
agent recv   #0x00000001 "a message while you are busy"
agent done   #0x00000003 "gamma" = "G"
agent denied #0x00000002 "refused" was "beta"
agent done   #0x00000001 "alpha" = "A"

Three claims, and each needs the others. The host reads all three tool calls before writing any answer, so a guest that blocked for each reply could not have produced the second frame. A peer's message is admitted by the graph and lands on the console before any of the agent's own answers, so an agent cannot be silenced by a slow tool. And the answers come back last-asked-first with the middle one refused: matched by arrival order instead — which is what every previous version of this guest effectively did — the first of those lines would have read #3 "alpha", and the refusal would have settled the wrong tool entirely. 16.0 ms from the task to the last answer.

What shipped: the guest is 64-bit

It was i686 because stable Rust ships a prebuilt core for i686-unknown-linux-musl and everything Linux could be linked away. That was the right call for a guest whose whole job was writing to a serial port and the wrong one for a guest expected to hold a context: thirty-two bits caps an agent's address space at 4 GiB, which is below one small model's weights plus its own working set.

x86_64-unknown-none is a real freestanding target with a prebuilt core, so this is still stable Rust with no -Z build-std and no nightly. What it costs is the 32-bit half of the boot: boot.rs builds page tables, sets CR4.PAE, arms EFER.LME, turns on paging and far-jumps through a 64-bit code descriptor. The map is 4 GiB rather than the 1 that hv1-multiboot's equivalent needs, because the host puts the shared model region at 3.5 GiB and the virtio window at 3.25, and an address outside the map is not slow, it is a fault.

SSE is put back by hand, and the reason is measured

The target spec disables SSE and builds core soft-float, which is right for a freestanding kernel and wrong for a guest that moved to 64 bits for arithmetic. Over the same 256 MiB sweep — the loop a quantised forward pass is made of — the difference is a factor of three: 

32-bit, SSE      : 13.20 cycles/byte cold, 1.66 warm
64-bit, no SSE   : 15.07 cycles/byte cold, 4.18 warm
64-bit, SSE      : 12.38 cycles/byte cold, 1.38 warm

So the port made that loop faster rather than slower, and the third row is the one that ships. It is not free: nothing enables SSE on a CPU coming out of reset, so four control-register bits have to be set before the first vectorised instruction, and the fault reporter has to be installed before that. Both of those cost the 32-bit guest a debugging session each, and the reason they cost one session rather than three is that the guest reports a vector and an address instead of stopping mid-word.

A cold-start regression that was not one

The first reading after the port said first output had moved from 3.6 ms to 8.0 ms, which would have been a serious loss. It was one sample. This host's own provision and launch phases vary between 1.4 and 12.3 ms run to run, and the guest's own share — first output minus launch — is 1.2 to 2.7 ms in 64 bits against 1.2 to 1.6 in 32. Three runs of each, and the median first output is 3.1 ms.

Worth recording because the instinct was to go looking for the cost in the page tables, and one experiment — mapping 1 GiB instead of 4 — appeared to confirm it before more runs showed the difference was noise. A single measurement of a noisy quantity will confirm whatever you suspected.

One thing did move, and upward. A thousand agents each with a vsock device and an open connection: 

                     32-bit        64-bit
booted and connected  37.3 s        26.1 s
memory per agent      0.221 MiB     0.276 MiB
idle, over 3 s        0.7% of core  0.3% of core
stop, all 1,000       612.7 ms      580.8 ms

A quarter more memory per agent, which is the page tables and the larger boot stack that long mode costs — 0.055 MiB each, and a thousand of them is 55 MiB. Everything else got faster, and the boot figure most of all, though that one is mostly polling granularity rather than a VM booting: rust_unikernel puts an actual boot at 3.1 ms. Round trip is unchanged at 2.2 ms.

Also fixed while in the file: the block that touches an agent's working set had been written out three times in a row, so every agent touched its own pages three times over — invisible in the figure it produces, since residency is idempotent, and three times the boot latency for an agent with a large working set.

What shipped: hv1 is a hypervisor to its guest

It hosted four bytes of real mode: vmmcall, hlt, two exits, stop. That proved VMRUN works and nothing about hosting — a hypervisor that enters a guest twice and stops has run a guest the way a launcher runs a program. What separates the two is what happens on an exit. 

hv1   exit 26  0x7B VMEXIT_IOIO     -> COM1, emulated
hv1   exit 27  0x81 VMEXIT_VMMCALL  -> the guest says it is ready
hv1   exit 28  0x78 VMEXIT_HLT      -> idle — injecting vector 0x20
hv1   exit 29  0x81 VMEXIT_VMMCALL  -> from inside the interrupt handler
hv1   exit 30  0x81 VMEXIT_VMMCALL  -> the handler returned and the guest carried on
hv1   exit 31  0x78 VMEXIT_HLT      -> idle, and nothing left to send it
hv1   > hello from a guest of hv1

Three things, and each is asserted from the guest's side of the boundary. The console line arrived one intercepted out at a time — there is no serial port on the other side of it, there is hv1 decoding the port out of the exit information. The I/O permission map had to stop being all zeros for that: a zero map with INTERCEPT_IOIO set intercepts nothing, so the guest's out would have gone past this hypervisor to whatever is underneath it. And the interrupt is the piece that cannot be faked: the only way exit 29 happens is if the CPU really took vector 0x20 through the guest's own table, and the only way exit 30 happens is if an iret returned from it.

And then the guest left real mode

A guest that stays in real mode is a program the hypervisor happens to be running: its interrupt table is four bytes per vector at address zero, and none of the machinery an operating system needs is present. So it builds its own — a descriptor table, CR0.PE, a far jump into 32-bit code, and then an interrupt table of thirty-three eight-byte gates, each with a selector, a privilege level and a present bit. The thirty-two the processor reserves point at a handler that reports, so a guest that faults now says so with a hypercall instead of triple-faulting into a shutdown exit with no diagnostic. 

exit 27  VMEXIT_VMMCALL  rip 0x0000000000000021  -> real mode, about to leave it
exit 28  VMEXIT_VMMCALL  rip 0x0000000000001060  -> protected mode, GDT and IDT of its own
exit 30  VMEXIT_VMMCALL  rip 0x0000000000001074  -> from inside the interrupt handler
exit 31  VMEXIT_VMMCALL  rip 0x0000000000001069  -> the handler returned and it carried on

The RIP going from 0x21 to 0x1060 is the mode change seen from outside, and nothing had to be asserted for it to be visible: a real-mode RIP is an offset from a segment base of 0x1000, and a protected-mode one under a flat descriptor is the linear address itself.

Once in protected mode the guest has to know where it was loaded, so that address now exists twice — in the hypervisor and in the guest's assembly. A mismatch would not fail to build; it would far-jump somewhere plausible and die. The assembly exports its copy as an absolute symbol and the hypervisor compares them before VMRUN and refuses.

Two supporting changes. The guest is assembled by the toolchain in a .code16 section rather than written out as hex — hand-assembly is why every guest in this repository stayed four bytes long. And the nested page tables now translate: guest-physical zero is the base of a 2 MiB region this image owns, and everything above it is absent. They used to identity-map the first gigabyte, which was survivable only because a four-byte guest touches nothing; this one has a stack and an interrupt table at its address zero, and an identity map would have put those in the hypervisor's own memory.

What none of this proves. Not hardware. The layer underneath is KVM, so hv1 read a CPU its own hypervisor chose to show it; the firmware path, the real memory map, AP bring-up and every real device are hidden by that. And one vCPU running 32-bit code with one emulated port is not an operating system either — a second vCPU and a device with a ring in it are the next two steps, and both can be taken on the nested path that already works.

What a fleet costs, now with a model in it

The arithmetic this project published before it had weights survives contact with real ones, which is the useful outcome and was not guaranteed. 

the model     : mapped once, 1260 MiB, and every conversation ran over that one mapping
alpha         : 1.50 MiB of key/value cache held
beta          : 1.69 MiB of key/value cache held
per token     : 65536 bytes of cache

64 KiB per token, not the ~12 KiB this page previously estimated for a hypothetical model — the estimate was for a smaller one and at two bytes per element rather than four. It is the figure a node should be sized from, because it is the one thing an agent cannot share with another agent: it is that agent's conversation. A 2,000-token context is 125 MiB and an 8,000-token one is 500 MiB, so a node holding a hundred agents in conversation is holding the model once and 12 GiB of context.

And the sharing itself, at the scale the page has always claimed, with the 64-bit guest doing the reading: 

region        : 350 MiB filled — resident grew 350.0 MiB
agents        : 1000 booted in 28396.0 ms
read the ROM  : 1000 of 1000 read 0xa7 at 0xe0000000, write refused
per agent     : 0.232 MiB
if copied     : 1000 agents x 350 MiB would be 341.8 GiB
saved         : 341.2 GiB, 99.83% of what copying would have cost

Read-only is enforced by the hardware and checked from inside each guest rather than asserted by the host: every one of the thousand writes to the region, reads it back, and reports whether the write took. One writable copy shared by a thousand agents is a thousand agents able to rewrite each other's model.

One number here is weaker than the others and is labelled so. The resident growth attributable to a session reads as 0.1 MiB against a 1.5 MiB cache, because a session allocates out of an arena that loading the model already grew. The first version of that measurement was worse: it let each session fall out of scope before the next was taken, so the second agent's cache came out of the first one's freed memory and its growth read as zero — a number about the allocator being presented as a number about what an agent costs. The cache size is counted rather than sampled, and that is the one to use.

What shipped earlier: the machine underneath

Kept because it is what the rest stands on, and because each of these was found the same way. None was found by reading.

  • stop() never returned. Not slowly — not at all, at twenty seconds, for every guest shape tried, because KvmVcpu::run retried on EINTR unconditionally and that retry is exactly the mechanism a VMM uses to kick a vCPU out. The fix is three things, because a kick has three moments to miss: a real-time signal without SA_RESTART, immediate_exit for a vCPU that has not reached the ioctl yet, and a per-vCPU flag read by the EINTR arm. Now 0.7 ms.
  • The cold start was a 474× defect nobody had measured. create_vm allocated guest RAM with alloc_zeroed at page alignment, which Rust forwards to aligned_alloc plus a full memset rather than to calloc. A 1 GiB calloc is 0.0 ms; a 1 GiB memset is 848. It decided density as much as latency.
  • Concurrency was capped at one VM per core, on the path a sandbox takes: run_single awaited a blocking KVM_RUN inline on the shared runtime, and a sandbox is a one-vCPU VM. 23 worked and 24 hung. The first attempt at the fix changed nothing because it fixed a function run_single never called — and only the measurement caught that.
  • Quotas refused nothing. GovernedVmHost wraps another host and a refused operation never reaches the inner one. Every test counts what arrived at the host underneath rather than reading the governor's answer.
  • A Multiboot guest was executing its own file header. The loader wrote every image to 1 MB verbatim and entered it at its first byte; an ELF's first byte is \x7fELF, and 7F 45 decodes as jns +0x45. That is why every guest that ever ran here was hand-assembled and nothing from a toolchain ever did.
  • An idle agent used to cost a core. An IDT, a programmed PIC, one handler and sti; hlt fix it, because a halted vCPU is a thread blocked in KVM_RUN. The PIC is the part that is not a one-liner: KVM's in-kernel 8259 comes up unprogrammed, and an unprogrammed 8259 delivers IRQ 0-7 as vectors 8-15, which are processor exceptions.

A correction to the previous version of this page

It carried 2.67 ms as the cold start of the 73-byte hand-assembled guest, described as a median of nine runs. unikernel_boot boots once per process and reports that one figure, so a median of nine can only have come from nine invocations — and five of those here read 3.4, 10.8, 12.4, 124 and 160 ms. The spread is process startup, image staging and whatever else the machine was doing, not a VM booting.

Both examples now boot nine times inside one process and print the range beside the median, which is the half that would have caught the original mistake. Three invocations of each:

Five invocations of each, spread over an afternoon on a host whose load moves. The compiled guest is not slower than the hand-assembled one and is considerably steadier — a firmer version of a claim this project has been making since the Rust guest existed, and one that needed the measurement fixed before it could be made at all. The spread is almost entirely the provision phase, which ranges from 0.78 to 23.6 ms across nine boots of the same image in the same process.

Open, with diagnosis

Nothing on this list is a failing test — the suite is green. What is left is one thing this machine cannot do, two things that compile and have never run, and three honest edges of what shipped.

1. hv1 has still never run on hardware

It initialises, hosts a guest, emulates a device for it and delivers it an interrupt, all nested under hv2, and that is as far as this machine goes. The layer under it is KVM, so the firmware path, the real memory map, AP bring-up and every real device are untested, and nesting hides all of them. That needs a machine and a serial console, and nothing here substitutes for it. The guest it hosts is also real mode with one emulated port; a protected or long-mode guest, a second vCPU, and a device with a ring in it can all be built on the nested path that already works.

2. ARM Type-1 has not executed at all

hv1-arm — EL2, stage-2, vGIC — is where hv1-core was a few days ago: it compiles, on nightly with -Zbuild-std, and nothing has run it. The trick that worked for x86 does not transfer, because this host is x86: running it nested needs an AArch64 host, and emulating one proves something about the emulator.

3. WHPX can be kicked and can boot Multiboot, and has done neither

WhpxBackend::kick_vcpu cancels the run with WHvCancelRunVirtualProcessor, and its Multiboot path receives a resolved entry point rather than treating one as a load address. Neither has been observed: WHP does not start on this host (HRESULT 0x80370302), so both are compilation results.

4. The batching is static, not continuous

A request that arrives while a batch is running waits for the next batch rather than joining the current one at its next token. That costs a late arrival some latency and costs throughput nothing, and it is a great deal simpler — but it is why scheduled's largest batch is two out of four: the four agents' requests do not arrive together, because each has to exchange a frame with its guest first. A continuously batched loop would have carried all four.

Also absent: priorities, preemption, and eviction of a cold conversation. An agent that stops asking holds its cache until something drops it, and nothing does — so a node's memory is decided by how many agents have ever asked rather than by how many are active.

5. What limits a pass past a third of the cores is not known

Throughput scales nearly linearly to eight threads on this host and then degrades. The scheduler avoids the bad region, which is enough to be worth doing and is not the same as understanding it — it could be memory bandwidth, cache contention between the shared weights and each agent's activations, rayon's own scheduling, or the fact that this is a virtual machine with 24 vCPUs on hardware it does not own. Nothing here distinguishes those, and the code says so rather than picking one.

6. The tokeniser's pre-tokeniser is written out by hand

The reference expresses the cuts as one regular expression with a lookahead; the regex crate has no lookahead, so the six rules are implemented directly. That handles the cases an English prompt is made of and a language whose words are not separated by spaces would be cut differently here than by the reference. Tested for the property that matters most — that the pieces always rejoin into the input, and that it always terminates — but not against the reference tokeniser, because there is none on this machine to compare with.

7. Quota usage does not survive a restart

GovernedVmHost counts what it has admitted, in one process, for as long as it exists. A process that comes back up has admitted nothing and will admit a full quota again. Persisting it needs a store and an answer to what happens when the store disagrees with the host's inventory, which is a larger decision than the enforcement was.

Environment notes that cost time

  • KVM works here. WSL2, kernel 6.18.33.2, API version 12, 24 vCPUs, 45 GB, AMD with nested=1. The user must be in the kvm group; sudo blocks on a password.
  • Build WSL into its own target directory. CARGO_TARGET_DIR=/var/tmp/hm-target — a WSL build over /mnt/c shares target/ with the Windows host and silently invalidates its artifacts.
  • Keep the model off the 9p mount too. Reading a 1.3 GB GGUF from /mnt/c took 44 seconds against 6 from /var/tmp. The same trap as the guest image, which cost 9.0 ms against 0.02 and made the first timing of the compiled unikernel meaningless.
  • protoc is not installed in WSL, so hv2-api does not build there and a workspace-wide cargo test fails on the Linux side — including with --exclude hv2-api, since other crates depend on it. Per-crate runs work, and the Windows host covers the workspace.
  • Check the exit status of the compiler, not of tail. A broken commit reached master because cargo check | tail -3 && git push reports the pipeline's last command. Use ${PIPESTATUS[0]}.
  • In Intel-syntax inline assembly, a bare symbol is an address. mov ax, SOME_CONSTANT assembles as a load from that address, silently. offset is what makes it an immediate, and objdump over the section is what tells you which one you got.
  • Paths through wsl.exe need MSYS_NO_PATHCONV=1, or Git Bash rewrites /var/tmp/... into a Windows path.
  • Pushes to master report a bypassed rule. Branch protection requires a pull request, the push succeeds anyway, and announces that it bypassed the rule. Somebody should decide which of the two is wrong.

What to do next

  • Make the batching continuous. A request that arrives while a batch is running waits for the whole batch. Letting it join at the next token is what turns "largest batch of two out of four" into "four", and the queue already knows who is waiting — what it cannot do is admit anyone once a pass has started.
  • Let a conversation be evicted. An agent holds its cache until something drops it and nothing does, so a node's memory is decided by how many agents have ever asked rather than by how many are active. The bound refuses new turns; it does not reclaim old ones.
  • Give hv1's guest a second vCPU and a device with a ring. It crosses into protected mode under its own tables and takes an injected interrupt through its own gates, which is most of what a small kernel does. Two vCPUs means an AP bring-up path and a lock; a virtqueue means the guest driving a device rather than writing a byte to a port. Both can be built on the nested path that already works.
  • Then boot hv1 on hardware, the only item here that cannot be done on this machine. It needs bare metal and a serial console, so it needs somebody to decide to provide them — and it is where the firmware path, the real memory map and every real device stop being hidden by a hypervisor underneath.
  • Find out what the thread knee is. Avoiding it was worth 1.4×, and understanding it might be worth more — or might say the ceiling is real, in which case wider batches are the only lever left.
  • Keep the suite green. It is.

The habit that found all of it

One rule keeps earning its place: measure before claiming, and assert on the effect rather than the verdict. The memset was found by timing, not by reading. The run_single ceiling was found because the fix that should have worked changed nothing. The stop() hang was a diagnosis before it was a fix. And the refused message that appeared to arrive was caught because the check read the recipient's console rather than the sender's return value.

Three more this time, and they are the same rule from three directions. The guest's frame handler had read one frame per packet since framing was introduced, and nothing had ever sent two — a defect that existed only in the space between what the code claimed and what had been asked of it. The transmit buffer was not a defect, and that had to be checked rather than asserted: the shared buffer was deliberately tried against the three-in-flight example and passed, because this host's device drains the queue inside the notification that announces it, so the comment says a property of the device rather than claiming a bug that was not seen. And a cold-start regression of 8.0 ms against 3.6 turned out to be one sample of a quantity whose noise is larger than the difference — an experiment aimed at the page tables had already appeared to confirm it.

Three more, and they are about measurement rather than about code. An optimisation measured in the wrong configuration looks worthless. AVX2 was tried at 24 threads, where the pass is limited by something else, and bought nothing; at eight threads it is worth 1.8×. Two changes that each look useless can be worth 2.2× together, and nothing but varying them together finds that. A fix applied at one layer is not applied at the layer above it. The thread pool belongs to the scheduler, so generate was still slow after the fix that was supposed to have halved it — caught only because the end-to-end number was re-measured instead of inferred from the component one. And a positive result needs a negative control. Two agents recalling a number they were told proves nothing on its own; a third agent, same capability, never told, answering something else is what makes it evidence.

The strongest case is still svm_run, and it now has a companion. svm_run's inline assembly had no input operands at all, so it read its two arguments from the wrong registers and handed VMRUN an address that was not a VMCB; nothing could have found that except running it, and nothing had run it. This session's mov ax, HANDLER_OFFSET is the same shape in miniature: correct-looking, silently assembled as something else, and visible only in a disassembly of what was actually produced. The lesson is not "review harder". It is that unexecuted code should be labelled unexecuted, which is what the pillars table has been doing all along.
